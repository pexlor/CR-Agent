# Documentation Style Guide

## 1. 总体原则

文档必须做到：

- 结论先行。
- 内容结构化。
- 减少废话和重复描述。
- 明确区分事实、推测和建议。
- 技术术语保持统一。
- 不为了显得详细而堆砌内容。

## 2. 标准结构

技术分析文档默认使用：

# 标题

## 1. 背景

说明：
- 当前是什么情况
- 为什么需要处理这个问题

## 2. 目标

明确本次需要解决什么。

## 3. 现状 / 问题

描述当前流程、限制和具体问题。

## 4. 分析

对问题进行拆解：
- 核心问题
- 原因
- 影响范围
- 边界条件

## 5. 方案

描述解决方案及关键流程。

## 6. 风险

说明：
- 潜在风险
- 兼容性
- 异常场景
- 回滚问题

## 7. 测试 / 验证

说明如何确认实现正确。

## 8. 结论

简要总结最终方案。

根据文档类型，可以删除不需要的章节。

## 3. 标题规范

最多使用三级标题：

# 一级标题
## 二级标题
### 三级标题

避免：

#### 四级标题
##### 五级标题

层级过深时改用列表。

## 4. 描述问题

描述一个问题时优先采用：

现象 → 原因 → 影响 → 解决方向

例如：

现象：
PortStatus 未更新。

原因：
Attach 成功后 GetNetworkInfo 失败，导致后续状态更新未执行。

影响：
实际网络设备已经挂载，但控制面状态仍为旧状态。

解决方向：
将设备操作结果与 PortStatus 更新解耦。

## 5. 方案描述

方案必须明确：

- 输入
- 核心处理逻辑
- 输出
- 异常处理
- 状态变化

涉及复杂流程时使用 Mermaid：

```mermaid
flowchart TD
    A[收到请求] --> B{参数是否合法}
    B -->|否| C[返回错误]
    B -->|是| D[执行业务逻辑]
    D --> E[更新状态]
    E --> F[返回结果]
