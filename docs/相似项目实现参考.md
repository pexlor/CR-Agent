# Code Review Agent 相似项目实现参考

调研日期：2026-09-10。

本文阅读 PR-Agent、Zadig Review Agent、AI Code Reviewer、reviewdog 的实现代码，说明对应功能如何工作，以及哪些部分适合本项目参考。范围依据当前《需求拆解.md》：首版同时接收 git diff、GitHub PR 链接和 GitLab MR 链接，只输出 Markdown 报告。远程回评仅作为后续扩展参考。

交付前核对时，需求确认记录已到 C-007：支持 GitHub.com／GitLab.com 私有仓库，不支持自建实例；每个平台复用一份预配置共享凭证；运行者和具备资格的用户可更新凭证，具体更新资格及生效规则仍待确认。相关实现参考补充在第 3.3 节。

这是源码调研记录，不是已批准的系统设计。文中“可借鉴／建议补齐”属于分析建议，不改变已有需求，也不决定语言、框架或数据库。

## 2. 总体能力对照

表中的“部分”表示存在相关机制，但不能直接等同于本题要求。

| 本项目能力 | PR-Agent | Zadig Review Agent | AI Code Reviewer | reviewdog |
| --- | --- | --- | --- | --- |
| 三种输入 | 有 GitHub／GitLab Provider，也有独立 diff Provider | 从本地仓库取得 workspace／commit／range diff | GitHub PR、本地工作区／暂存区／分支差异；当前 CLI 未见独立 stdin diff 入口 | 接收诊断结果并取得比较 diff；不是完整的 AI 审查输入层 |
| Markdown | plain-diff Provider 可将审查文本输出到 stdout／文件 | 独立 Report → Markdown renderer | CLI 支持 Markdown 输出 | 有评论 Markdown 格式化；不是包含预算和 trace 的完整审查报告 |
| checkpoint 恢复 | 有跨次问题状态和增量审查；未发现任务步骤恢复 | 过程保存在运行内存，结束后写报告；未发现恢复入口 | Session 明确是临时对象；跨次评论状态不保存执行步骤 | 读取已发布评论去重；不是分析任务 checkpoint |
| 逐评论 trace | 命令遥测、prompt／response 日志；未确认完整逐评论关联 | 结构化工具和模型过程记录，但缺少完整 prompt 快照及评论到调用的显式关联 | 客户端有 usage／工具记录，主结果转换没有完整保留 | 保留工具来源和诊断位置，无 LLM trace |
| 声明式工具扩展 | 命令映射；Provider 有注册 API | JSON 描述工具，但执行器仍为 switch | 工具 schema 列表，执行器仍为 if/elif | YAML Runner + 通用诊断格式；会执行配置命令 |
| 总预算 | 上下文裁剪、分块调用数限制、事后消耗统计 | 分块派发前估算预留、结束后按 usage 校正；不是逐调用硬上限 | 单请求输出限制、工具次数、GitHub 请求配额、时间限制 | 无 LLM 总预算机制 |
| 置信度 | /review 的审慎提示；/improve 有模型反思评分 | 模型给 confidence，程序按阈值及位置校验过滤 | 共识比例、模型 confidence、二轮交叉审查 | severity 是严重程度，不是置信度 |

## 3. 输入适配：优先参考 PR-Agent

### 3.1 把不同来源统一成变更文件对象

PR-Agent 用 `GitProvider` 隔离平台差异。GitHub、GitLab、plain-diff 最终均交付 `FilePatchInfo`，包含 `base_file`、`head_file`、`patch`、`filename`、`edit_type`、`old_filename` 等字段。审查器面对的是统一变更对象，而不是在 prompt 生成代码中处理多个平台 API。[统一数据结构][P-types]、[Provider 选择和注册][P-provider]

三种入口的实际处理如下：

| 来源 | 实现步骤 | 值得参考的细节 |
| --- | --- | --- |
| 独立 diff | CLI 读取 `--diff-file` 或 `--stdin` → 设置 plain-diff 配置 → `parse_unified_diff` → 统一对象 | 两种读取方式互斥；文件读取／编码错误明确失败；无仓库根目录时仅用 patch，不读取任意工作目录文件 |
| GitHub PR | Provider 取得 PR 文件 → 找 merge base → 读取 head 和 base 对应内容 → 缺失 patch 时从内容生成 diff | PR 的目标分支当前 tip 不一定是正确比较基点；重命名读取旧路径；文件过多时限制整文件读取 |
| GitLab MR | 读取 MR changes → overflow 时再请求 raw diffs → 使用 `diff_refs` 的 base/head → 转换新增、删除、重命名状态 | 平台可能返回不完整 diff，必须识别；旧路径和新路径应同时保留 |

源码：[CLI diff 入口][P-cli]、[PlainDiffGitProvider][P-plain]、[GitHub diff 获取][P-gh]、[GitLab overflow 处理][P-gl-overflow]、[GitLab 变更转换][P-gl]

边界：PR-Agent 这条 GitLab 分支在 overflow 后做了一次 raw 请求；不能据此推导所有平台截断情况都已被验证完整。plain-diff 会尝试用当前工作树补充内容，路径受限不代表补充内容一定与提交的 diff 同版本。

**对本项目的启发**：三种输入可共享审查和报告流程；输入层应同时保留变更身份、旧／新路径及覆盖完整性。独立 diff 缺少上下文时需要明确说明，不能凭空补出提交 SHA。

### 3.2 其他项目的输入方式及限制

Zadig 的 Git Client 区分工作区、单提交和 ref 范围；获取 diff 时明确使用 `--no-ext-diff`、`--no-textconv`，部分命令使用 `--end-of-options`。其 unified diff 解析器保留 hunk 以及新旧行号，适合参考本地 diff 解析与执行参数边界。[Git diff 实现][Z-git]

AI Code Reviewer 的当前 CLI `review` 从 `os.getcwd()` 构建输入，提供 `--staged`、`--base`；随后 `review_local` 与 `review_pr` 汇入 `_review_from_inputs`。`LocalGitSource` 模拟读取文件和目录树接口，从而复用上下文构建和工具逻辑。[本地 CLI][A-cli]、[共享流程入口][A-local]、[本地来源适配][A-source]

**修正上一轮 README 层面判断**：AI Code Reviewer 的 README 给出了管道 diff 示例，但本次固定版本的 CLI 主路径未读取 stdin；因此只能确认“本地 Git 差异审查”，不能确认“任意独立 diff 输入”。同理，它的本地上下文读取明确忽略传入 `ref`，读取当前工作树；若要保证上下文和审查版本一致，需另行处理。[本地 CLI][A-cli]、[LocalGitSource][A-source]

reviewdog 的核心输入是 linter／分析工具的诊断结果；另通过 `DiffService` 获取 diff 来决定哪些诊断应报告。它的 GitLab diff 适配会取得 MR 信息，再在本地执行 merge-base／git diff，所以并不是仅提供 MR 链接就可独立运行的通用输入适配。[核心接口][R-core]、[GitLab diff][R-gl-diff]

### 3.3 私有仓库凭证与平台范围

PR-Agent 在构建 Provider 客户端时读取配置。GitHub 的 user 模式读取 `github.user_token`，包装为 `Auth.Token`；另外支持 App 认证。GitLab 读取 `GITLAB.URL` 和 `GITLAB.PERSONAL_ACCESS_TOKEN`，根据 `AUTH_TYPE` 选择 OAuth 或 private token 参数；缺少必需配置时抛错。[GitHub 客户端认证][P-gh-auth]、[GitLab 客户端认证][P-gl-auth]

可参考这种“配置 → 认证客户端 → 读取变更”的分层，使审查逻辑不直接处理凭证。客户端成功构造仍不等于已证明凭证有效或具备目标仓库权限，访问失败需要明确反馈。

PR-Agent 支持的实例范围比本项目广，URL 解析主要提取仓库和 PR／MR 编号，包含 API 路径、自建部署子路径等处理。不能直接将其解析成功视为符合本项目的平台范围；本项目需按已确认要求检查 GitHub.com／GitLab.com 的准确主机名，并使用对应平台固定的可信 API 目的地。[GitHub URL 解析][P-gh-url]、[GitLab URL 解析][P-gl-url]

本次没有在上述客户端初始化路径中发现面向用户的共享凭证更新权限和生效管理机制。每平台一份凭证无需引入按仓库选择身份的复杂逻辑，但谁能更新、更新如何影响进行中的审查，仍需按本项目需求单独设计；不能借“配置可修改”推导任何用户都有更新权限。

## 4. 审查流程与结果校验

### 4.1 PR-Agent：准备变更 → 模板 → 模型 → 结构化结果

`PRReviewer._prepare_prediction` 调用 `get_pr_diff`，为 hunk 加入行号，再由 Jinja 模板生成 system/user prompt，统一经过 AI handler 调用模型。结果按 YAML 解析成 review 结构。[审查与模型调用][P-review]

`get_pr_diff` 先尝试扩展上下文；超出模型上下文容量后压缩。启用大 PR 分块时，`_prepare_chunked_prediction` 使用 `asyncio.gather(..., return_exceptions=True)` 并行审查各块，保留成功块、统计失败块，再合并结果；若所有块都没有可解析结果，会抛错或返回单次调用回退路径。[diff 压缩][P-diff]、[分块及合并][P-review]

可借鉴：统一模型入口、模板与流程分离、分块失败可保留已有结果。需要补齐：被裁剪文件和失败块必须进入本项目的明确覆盖状态，而不能仅写调试日志。

### 4.2 Zadig：受约束的工具循环 → 位置校验 → 过滤 → 汇总

Zadig 的 `runSubtask` 调用链比较清楚：

1. 检查当前块大小；较大变更可先进行无工具的计划调用。
2. `runMainLoop` 让模型选择只读上下文工具，或提交 `code_comment`、结束 `task_done`。
3. `positionFinding` 将候选问题的代码片段匹配到实际 diff，必要时再调用模型重定位。
4. `filterFindings` 给候选问题临时 ID，让过滤阶段返回要删除的 ID。
5. 本地化后再次定位，并校验路径、类别、严重程度、confidence 和变更行重叠。
6. 对合格问题计算 fingerprint，去重并按文件／行号排序。[单块流程][Z-subtask]、[问题定位][Z-position]、[过滤阶段][Z-filter]、[最终校验][Z-validate]、[去重][Z-dedup]

它没有完全信任模型输出的行号：优先匹配 `existing_code`；匹配按连续的新侧／上下文行进行，比较时去掉行首尾空白，并要求覆盖变更行。只有未提供代码片段时，才允许直接使用与变更行重叠的行号。[定位实现][Z-position]、[代码匹配实现][Z-match]

限制：这一定位机制侧重新侧变更。纯删除行、文件级和跨文件问题，不能未经扩展就假设全部支持。匹配到代码只能证明位置有依据，不能证明模型所说的逻辑缺陷成立。过滤阶段“只删除被 diff 直接证伪的候选”仍依赖模型判断，程序主要限制其输出形式。

可借鉴：让程序负责位置与类型校验，把模型负责的判断与确定性校验分开。

### 4.3 AI Code Reviewer：多个视角 → 聚合 → 交叉审查

实际主路径是 `review.py` 中的 `_review_from_inputs`：过滤忽略文件、选择 Agent、构建共享上下文，运行并聚合结果；大 PR 可分片；随后可进行第二轮交叉审查，并验证结构化修复建议。[实际主流程][A-flow]、[聚合与二轮调用][A-post]

阅读时应从调用者向下追踪。该仓库还保留 `orchestrator/aggregator.py`，但本次 CLI 主路径调用的是 `review.py::aggregate_findings`；不能把另一个聚合类里的评分公式直接当作当前 CLI 行为。

其修复校验在内存中替换文本，然后对 Python 使用 AST 解析，对 JSON／YAML／TOML 使用解析器；其他语言回退到括号计数比较。不执行修复后的代码，但这也仅是适用性和有限语法检查，不是语义正确性证明。[修复验证][A-fix]

### 4.4 reviewdog：诊断结果 → diff 过滤 → 报告适配

`Reviewdog.Run` 用 Parser 读取诊断，获取并解析 diff；`runFromResult` 规范化路径后调用 `FilterCheck`，最后交给 `CommentService` 或批量 `Flush`。[核心流程][R-core]

`DiffFilter` 构造“新路径 → 新行号 → diff 行”的索引，支持新增行、diff 上下文、变更文件和不过滤四种模式。多行诊断逐行判断：任意行符合即可报告，同时另外记录整个范围是否都在 diff 内，供发布位置和代码建议使用。[diff 索引与模式][R-diff]、[多行诊断过滤][R-filter]

可借鉴：审查判断与位置过滤相互独立。限制：在 diff 内不代表发现了真实 bug，reviewdog 不承担 LLM 判断质量。

## 5. 可恢复：要区分三类“状态”

| 项目机制 | 实际保存／复用什么 | 为什么不是本题的 checkpoint |
| --- | --- | --- |
| PR-Agent finding state | 评论 HTML 标记中的 JSON；问题 ACTIVE／RESOLVED 状态、head SHA、run ID；增量审查复用先前审查锚点 | 管理跨次审查的问题生命周期，没有保存每个模型／工具步骤的可恢复执行状态 |
| Zadig process recorder | 运行内存中的工具记录、模型结果和压缩记录；Runner 返回后形成 Report，再写文件 | 进程被强制终止时不能假定已有记录落盘；未见从报告恢复调度的入口 |
| AI Code Reviewer Session／ReviewMeta | Session 缓存文件、目录和配额；ReviewMeta 在远程评论里存 commit、次数和问题集合 hash | Session 明确不持久化；ReviewMeta 用于增量比较，不保存完成到哪个 Agent／工具步骤 |
| reviewdog posted comments | 从远程平台读取已有评论，以路径、行号和 fingerprint 判断是否已发布 | 解决重复回评的一部分，不恢复上游分析过程 |

证据：[PR-Agent 状态合并][P-state]、[Zadig Runner 收尾][Z-run]与[结束后写报告][Z-cli]、[临时 Session][A-session]与[ReviewMeta][A-meta]、[reviewdog 去重][R-dedup]

PR-Agent 有一个值得借鉴的状态约束：只有满足允许解决旧问题的条件时，才将本次未出现的问题标为 RESOLVED；不完整审查不应直接等价于“问题已修复”。[状态合并实现][P-state]

AI Code Reviewer 通过严格 hash、模糊 hash、标题和位置三级匹配比较新旧发现；这是减少重复反馈、跟踪问题的方案，不是恢复一个中途失败的 review。[delta 比较][A-delta]

**对本项目的启发**：checkpoint 需要单独设计和验证。至少要区分输入身份、已完成工作、进行中调用、调用结果未知、待重试与最终报告状态；恢复时先核对输入和配置是否仍匹配。不能用“有日志”“有缓存”“可以重跑”替代“异常后复用已完成进度”。这些是待设计方向，本文不指定存储方案。

## 6. 可观测：有日志不等于每条评论可追溯

### 6.1 Zadig 的结构化过程记录最便于参考

`processRecorder` 在工具开始／结束时生成 ID，记录文件、轮次、参数、状态、缓存命中、耗时、截断情况和输出；模型记录含 stage、attempt、文本、finish reason 和 usage。Report 将工具、模型、压缩过程分别保存在数组中。[记录器][Z-process]、[报告数据结构][Z-types]

但 `Finding` 没有直接列出来源 tool/model ID，`ModelResponse` 也没有保存完整请求 messages。因此可确认其具备结构化审查过程，不能据此确认满足“每条评论关联 diff、prompt、工具调用和模型回复”的完整链路。[Finding 与 ModelResponse 定义][Z-types]

### 6.2 PR-Agent 已有遥测和 prompt／response 日志

命令处理器设置 OpenTelemetry span 的命令名、状态等属性；Tracer 可通过批量处理器导出到 console 或 OTLP，未启用时使用 NoOp。LiteLLM handler 有 prompt 和完整 response 的调试日志。[命令遥测][P-command]、[Tracer][P-tracer]、[prompt 日志][P-prompt-log]、[response 日志][P-response-log]

这提供运行级观测基础，但还需要额外核实日志开关、存储、保留策略和逐评论关联。原始 prompt／response 日志本身也可能携带代码或 secret，不能未经出站／落盘过滤就直接复用。

### 6.3 AI Code Reviewer 的中间观测数据没有完整进入最终结果

`AnthropicClient.run_review` 收集 usage 和工具调用列表；工具列表记录名称和输入。不过 `ReviewAgent.review` 返回 `AgentReview` 时只取解析后的 findings、summary、时间等字段，没有传递全部 raw response、usage、tool_calls。现有主链不能直接提供完整逐评论 trace。[模型循环][A-client]、[工具记录][A-tool-record]、[结果转换][A-base]

**对本项目的启发**：应显式关联评论 ID、输入片段、模型调用、工具证据和校验结果；记录经过安全处理的请求和回复，并保留 prompt／规则版本。用户报告可以简洁，但其 trace 入口要能定位完整证据。追溯所需的请求、回复和证据不等同于要求模型披露内部推理过程。

## 7. 扩展：重点检查“声明”是否真正连接到执行

| 项目 | 实现方式 | 实际扩展边界 |
| --- | --- | --- |
| PR-Agent | `command2class` 将命令映射到工具类；Git Provider 有 `register_git_provider`，检查类型并防止覆盖已有注册 | Provider 注册可复用，但新增审查命令仍涉及中央映射；不是完整的声明式工具插件系统 |
| Zadig | 编译时 embed `tools.json`，反序列化为协议工具描述；`execute` 按名称 switch 到实现 | 新增 JSON 描述还不够，执行分支也要增加；工具说明与能力权限没有自动等价关系 |
| AI Code Reviewer | `TOOL_SPECS` 提供 schema；`ToolRegistry.execute` 用 if/elif 调用 read_file、glob、grep | 提供 schema 不会自动装配新实现，仍需改执行分支 |
| reviewdog | YAML Runner 声明 cmd、format、errorformat、level；通用 Parser 将输出转成统一诊断 | 已支持格式的新分析工具可只改配置，但它通过 shell 执行 cmd，不符合本项目对不可信仓库命令的约束 |

证据：[PR-Agent 命令表][P-commands]及[Provider 注册][P-provider]、[Zadig 工具声明加载][Z-tooldefs]与[执行器][Z-tools]、[AI Code Reviewer 工具分发][A-tools]、[reviewdog 配置][R-conf]与[Runner][R-runner]及[shell 构造][R-shell]

**可借鉴的组合**：工具具有统一输入／输出协议；注册时关联声明与已有实现；调用前统一执行参数、权限、预算和 trace 约束。对于本题，“实现并声明注册后不修改主流程”需要单独做新增工具验收，不能以“仓库里有 tools.json”作为通过证据。

## 8. 预算：区分上下文容量、调用次数和总消耗

### 8.1 Zadig 的“预留 → 结算”机制

Runner 使用共享 `atomic.Int64 budgetCommitted`。调度一个 chunk 之前，计算估算消耗 E：若当前 committed + E 大于 `MaxTokensBudget`，停止派发并产生 `token_budget_reached`；否则先增加 E。worker 完成后，将 `usage.TotalTokens - E` 加回 committed，把估算值替换为已报告实际值。[预算调度][Z-budget]

它采用的估算形式为：

```text
E = (diffTokens + 2000) × 7 + 700 × 7
较大变更需要计划阶段时，再加 diffTokens + 2000 + 400
```

这些常量来自实现中的平均轮数／输出假设，不是精确计费上界。[估算函数][Z-estimate]

模型调用包装器对实际尝试累加请求数和返回 usage，并对可重试错误重试；但是逐调用检查的是上下文阈值，未在这里重新查询总预算。已派发 chunk 仍可多轮调用，真实消耗可能超过预留值，所以不能承诺严格不超支。若 provider 没有返回 usage，也不能把缺失数据当成已证明零成本。[逐调用统计与重试][Z-calls]

其测试 `TestRunnerStopsDispatchBeforeProjectedTokenBudgetOverrun` 覆盖的是停止后续 chunk 派发并标记 incomplete；测试使用单 worker 和假的模型响应，不证明所有并发和估算偏差场景都满足硬预算。本文仅阅读该测试，没有执行。[预算测试][Z-budget-test]

### 8.2 PR-Agent：压缩／限制次数＋事后统计

PR-Agent 的 diff 处理根据模型上下文容量裁剪，大 PR 分块带 `max_number_of_calls` 限制。`RunDetails` 累计 token、成功 AI 调用次数、可取得的成本和按模型成本；`record_ai_call` 的明确语义是记录成功调用，没有在该函数内阻止超预算调用。[分块调用限制][P-review]、[运行统计][P-usage]

可以参考“已知费用／费用未知”的区分，以及多模型回退后的统计；不能直接将上下文 token 上限或成功调用费用报表当成总预算执行器。

### 8.3 AI Code Reviewer：多个局部约束

它分别限制 Agent 工具调用次数、仓库内容读取请求数、单文件和工具结果大小、单次最大输出、工具轮数和截止时间。`ReviewSession.github_budget` 是 GitHub 请求配额，`max_combined_context_tokens` 是上下文容量参数，二者都不是美元预算。第二轮交叉审查还会增加模型调用。[Session 配额][A-session]、[工具约束][A-tools]、[配置字段][A-config]、[模型循环][A-client]、[交叉审查调用][A-post]

**对本项目的启发**：预算口径仍须按需求确认；若要求总预算约束，要覆盖主审查、计划、压缩、重定位、复核和重试，并在统一模型入口执行预留／结算。预估误差、并发中的预留和结果未知的调用，都需要明确规则。不能默认只给主要 review 调用计费。

## 9. 置信度：分数、共识、代码证据各解决什么

### 9.1 Zadig：模型自报分数＋程序过滤

模型提交的 Finding 包含 `Confidence`；`validateFindings` 按配置阈值过滤，并检查路径、类别和变更行。报告直接展示该分数。位置匹配增加可核对性，但程序没有根据证据独立重新计算一个校准后的概率。[Finding 定义][Z-types]、[阈值校验][Z-validate]、[Markdown 输出][Z-markdown]

### 9.2 AI Code Reviewer：共识与置信分数分开

当前主路径先按同文件、行范围、类别和文本相似度聚类，再去重同一个 Agent 的重复发现。共识比例为：

```text
consensus = 报告该问题的不同 Agent 数 / 本轮 Agent 结果数
priority = 严重程度权重 × consensus × confidence
```

主路径中 `confidence` 取聚类首条 finding 的分数，并不是多个 Agent 分数的平均值；严重程度权重依次为 critical=1.0、warning=0.6、suggestion=0.3、nitpick=0.1。程序随后按严重程度设置置信阈值，没启用交叉审查时提高过滤阈值。[聚合实现][A-aggregate]、[优先级公式][A-priority]、[无复核时提高阈值][A-threshold]

可选的第二轮按问题 ID 返回 valid、rank 等评估。普通问题以实际投票者中的赞同比例决定保留，默认门槛 2/3；无人投票的发现保留但放到低优先位置；critical security 有特殊保留规则。因此不能简单描述成“所有问题必须得到三分之二 Agent 同意”。[交叉审查规则][A-cross]

这些机制适合参考去重、降噪和复核，但多 Agent 可能共享同一模型偏差，共识值不是经过校准的缺陷概率。

### 9.3 PR-Agent：不要混用 /review 与 /improve 的分数

`/review` 的 schema 包含整体风险、可选整体质量分数和问题列表，提示模型解释高影响但不确定的发现；这不等于为每条问题分配独立置信等级。`/improve` 则会进行 self-reflection，读取 `suggestion_score` 和 `why`；反思没有有效响应时还会设置默认 score=7、空理由。[review schema][P-schema]、[建议反思与默认分数][P-reflect]、[反思结果读取][P-reflect-result]

**对本项目的启发**：严重程度表示影响，置信度表示结论可信程度，两者单独存储。可以借鉴模型评分和复核，但“高置信／仅供参考”的依据还应包括代码位置、触发条件、上下文是否齐全、工具证据及反证。默认分数和无人复核不能被解释成已验证。

## 10. 安全：分别检查出站数据与执行能力

### 10.1 Secret 检测与出站脱敏不是同一功能

AI Code Reviewer 的 `scan_for_secrets` 对 diff 新增行匹配 AWS、GitHub token、私钥头及通用 key 等正则，返回 critical/security 发现，confidence 固定为 0.95。它跳过删除行和上下文行，并支持排除路径；函数只返回 findings，没有返回脱敏后的 diff。[扫描器][A-secret]

主流程先扫描，再把同一个 diff 传给 `_review_from_inputs`；后续进行的是忽略文件过滤与上下文构建，secret 告警最后加入 findings。因此，**这条调用链是在发现泄露风险，并未以该扫描器阻止原始 secret 进入模型输入**。[扫描后的调用链][A-input]、[上下文构建][A-flow]、[告警合并][A-post]

PR-Agent 的 `redact_credentials` 主要处理 URL 中的认证信息和认证头；Zadig 的配置展示可隐藏模型 API key。它们都不能自动证明 diff、额外上下文、工具输出中的业务 secret 已全部被过滤。[PR-Agent 凭证日志处理][P-redact]、[Zadig 配置脱敏][Z-config]

可借鉴：正则检测、已知凭证保护和路径排除。需要补齐：在所有模型出站数据以及 trace／报告落盘处统一执行安全处理，覆盖删除行、上下文、工具回包和模型回显。具体 secret 类型、误报处理与失败策略仍按需求确认。

### 10.2 只读工具与宿主程序边界

Zadig 不向模型暴露通用 shell；`toolExecutor` 只分发限定的读文件、搜索和 diff 工具。`safePath` 校验相对路径，并解析符号链接后检查是否仍在仓库根目录内；Git diff 命令禁用外部 diff 和 textconv。system prompt 将仓库数据标记为不可信，但真正限制文件访问的是执行器。[工具分发][Z-tools]、[路径约束][Z-path]、[Git 参数][Z-git]、[system prompt][Z-system]

AI Code Reviewer 同样将工具限制为 read_file／glob／grep，本地读取还通过 `Path.resolve` 和 `is_relative_to` 做根目录约束。需要注意，本地“按路径安全读取”与“读取指定版本”是两个不同问题，后者不能靠路径检查解决。[工具实现][A-tools]、[本地读取][A-source]

reviewdog 的 YAML Runner 将 cmd 交给 `sh -c`，Windows 下可使用 `cmd /c`。它会从子进程环境中过滤自身几个平台 token，但不是对所有 secret 的过滤，也不是禁止任意代码执行。可参考其诊断协议，不应直接让不可信仓库配置决定本项目运行的命令。[命令执行][R-shell]、[环境变量过滤][R-env]

PR-Agent 另有值得参考的配置权限隔离：仓库可修改某些审查偏好，但不能通过配置随意更改宿主技能文件路径、输出目的地或 prompt 模板片段。这说明“仓库提供配置”也需要区分偏好与宿主权限。[配置权限规则][P-security]

以上是发现的控制点，并非对任何项目作全面安全保证。

## 11. Markdown 输出与不完整结果

Zadig 的 `Report` 独立于 renderer。Markdown 展示输入模式、版本信息、覆盖规模、usage、工具索引、问题位置／证据／建议、错误和排除项；JSON 才保存更完整过程数据。CLI 在 Runner 返回后调用 reporter 写出文件，写入错误会向上返回。[报告结构][Z-types]、[Markdown renderer][Z-markdown]、[文件写入][Z-write]、[CLI 输出][Z-cli]

它将“无发现”和“执行不完整”分别表达：warnings／errors 可令 `Incomplete=true`；退出码优先检查 incomplete，不能因为 findings 为空就通过。可借鉴这一状态模型，同时应注意报告“无发现”文案不能掩盖其他位置的不完整说明。[状态汇总][Z-budget]、[不完整判定][Z-incomplete]

PR-Agent 的 plain-diff Provider 将审查器生成的文本输出到 stdout／指定文件，临时进度评论不会混入最终正文。该实现适合参考本地输出，但平台 Provider 的回评路径与本项目的“仅生成 Markdown”仍应分开。[本地报告输出][P-output]

**本项目报告可优先参考的内容**：审查对象与版本、已审查／未审查范围、完成状态、发现列表、置信等级与依据、消耗及不确定费用、逐评论 trace 入口。仅输出 Markdown 不代表内部必须只保存 Markdown，内部状态和证据形式需要在后续设计中明确。

| --- | --- | --- | --- |
| 三种输入与统一 diff | PR-Agent Providers | base/head、merge base、重命名、缺失 patch、overflow | 将当前工作树自动视为 diff 的同版本上下文 |
