# Code Review Agent 需求拆解

## 文档说明

本文只分析“要做什么”、业务约束与验收条件，不包含系统设计、技术选型、架构设计、API 设计或代码实现。

需求依据为本次提供的 Take-Home 题目。现有《开发流程.md》用于了解项目背景，其中的 MVP 建议和实现思路不自动转为已确认需求；

本文采用以下标记：

- **【明确】**：题目直接提出的能力或约束。题目中带“例如”的内容不自动成为唯一方案。
- **【隐含】**：为使明确要求形成可用、可验收闭环而识别的需求。
- **【已确认】**：由用户明确决定，或在用户授权下按“最低限度满足题目”原则完成裁决的需求。
- **C-001～C-007**：用户逐项明确确认的决定；**C-008～C-023**：用户授权按最低限度满足题目原则作出的范围裁决。
- **P0** 表示首版必须满足；未排期候选不构成首版承诺。

下文验收标准是当前确定的业务验收口径。“可演示一次”不等于已证明所有情况均满足要求。

| C-017 | 工具扩展范围 | 【已确认】首版扩展工具仅允许对已授权文本进行只读、确定性静态分析 | 不执行仓库代码，不加载仓库插件／依赖／可执行配置，不访问外部服务；用“静态模式检查工具”演示声明式注册。工具均为可选，失败后继续并标记部分验证及影响；所有工具必须遵守 trace、checkpoint、预算和安全规则 |

| C-019 | 预算耗尽规则 | 【已确认】预算按调用前预留执行硬约束，不主动突破用户设定值 | 剩余预算不足时停止新增模型调用并生成部分报告；允许用户追加预算后恢复；报告区分实际消耗、预留／不确定消耗和剩余预算；未知费用按已预留最大 token 计入 |
| C-020 | 置信度 | 【已确认】首版采用“高置信度可直接采纳”和“仅供参考”两级 | 高置信度需有直接代码证据，并经确定性工具验证或具备可直接核对的语言语义依据；模型自评分不能单独决定等级；证据不足或冲突时降为仅供参考，无可行动依据则不输出 |
| C-021 | 敏感信息规则 | 【已确认】secret、个人信息和明确标记的业务敏感数据不得发送给 LLM，也不得以明文写入报告、trace 或 checkpoint | 覆盖访问令牌、API Key、密码、私钥、连接串、云凭证和证书等已知类别；发现后脱敏并继续，无法安全脱敏则跳过相关片段并标记部分审查；无法判断时按敏感处理。脱敏后的私有源代码允许发送给已配置 LLM |
| C-022 | 仓库执行边界 | 【已确认】首版不得执行用户仓库中的任何代码或由仓库控制的执行内容 | 禁止运行脚本、构建、测试、typecheck、包管理器、钩子，以及加载仓库插件、依赖和可执行配置；仓库内容不得改变权限、预算、发布目标或安全规则，只有系统外显式用户操作可以改变这些约束 |
| C-023 | 质量与优先级 | 【已确认】FR-003～FR-009、FR-011～FR-028 全部属于 MVP/P0 | 使用至少 8 个固定样例验收，其中包括缺陷、无缺陷、恢复、预算和安全场景；所有预置高置信度缺陷须检出，干净样例不得产生高置信度误报。首版不承诺并发量或处理时长；远程回评仅作未排期候选，不设 P2 |

## 1. 需求理解

### 1.1 项目要解决什么问题

Code Review 需要审阅者理解变更、发现问题并给出可行动的反馈，具有较高价值，也容易因重复劳动与疲劳出现遗漏。项目要把输入的代码变更转化为可供人判断的 review 评论，减轻人工审阅负担。

题目不仅要求“生成评论”，还要求这项工作在失败后能够继续、结论能够追溯、能力能够扩展、成本受到约束、可信程度可区分，并遵守数据与执行安全边界。

### 1.2 谁会使用

| 使用角色 | 主要诉求 | 确定程度 |
| --- | --- | --- |
| 发起 review 的开发者／审阅者 | 提交变更，获得有依据的评论，查看任务结果 | 【已确认，C-008】首版为本机可信用户 |
| 阅读评论的代码作者／审阅者 | 理解问题位置、影响及置信程度，决定是否采纳 | 【已确认，C-008】通过本地报告和 trace 获取结果 |
| 工具扩展维护者 | 增加审查能力，无需修改主流程 | 【已确认，C-017】属于维护职责，不建设独立产品角色 |
| 验收人员 | 核对题目要求是否被满足 | 属于交付验收关系，不据此增加产品角色或管理功能 |

首版不建设账号、角色权限后台或企业组织管理。本机可信用户可启动任务、查看报告与 trace，并更新或清除共享凭证；远程回评不在首版范围。

### 1.3 核心业务目标

1. **形成审查闭环**：从受支持的变更输入产出有用的 review 评论。
2. **降低失败损失**：异常恢复时复用有效进度，不从头运行。
3. **支持核对结论**：每条评论可追溯到生成依据与过程。
4. **控制单次审查消耗**：允许设置总预算，并据此约束消耗。
5. **帮助用户判断采纳风险**：区分不同置信程度。
6. **保持扩展能力与安全边界**：工具可以声明式接入，secret 不上传 LLM，用户仓库不能触发任意代码执行。

首版不承诺节省时间比例、处理时长或并发量。评论质量按 C-023 的固定样例验收，不将样例结果推广为任意项目上的检出率或误报率保证。

### 1.4 核心使用场景

| 场景 | 用户期望 | 相关需求 |
| --- | --- | --- |
| 提交一份 git diff | 获得针对这份变更的 review 结果 | FR-001、FR-003～007 |
| 提交 GitHub PR 或 GitLab MR 链接 | 审查指定变更，明确访问失败或内容缺失 | FR-002～007 |
| 阅读 review 结果 | 查看问题依据、置信等级和 trace | FR-006、FR-009、FR-015～016、FR-023～024 |
| 执行发生异常后恢复 | 沿用有效进度，明确未完成部分 | FR-011～014 |
| 设置一次 review 的预算 | 消耗受约束，耗尽后获得如实的结果说明 | FR-020～022 |
| 增加一个审查工具 | 通过声明式注册接入并受同样约束 | FR-017～019 |
| 输入中包含 secret 或诱导执行的内容 | 不泄露 secret，不触发任意代码执行 | FR-025～028 |
| 将结果直接回评到远程平台（首版不纳入） | 评论发布到正确对象，失败或重试不造成重复 | FR-010、FR-014 的发布相关部分；留作后续候选场景 |

## 3. 每条需求说明

### E1 变更输入与范围确认

#### FR-001 接收 git diff

- **需求描述**：【已确认，C-001、C-009】MVP 支持以 UTF-8 unified diff 文本或文件提交 git diff；一次任务只接受一种输入。
- **正常流程**：用户提交支持范围内的非空 diff → 系统确认接收 → 该 diff 成为本次审查对象。
- **异常场景**：内容不是 diff、内容不完整、编码无法识别、输入不可读取时，进入输入异常处理。
- **边界条件**：空 diff 返回“无变更”；支持纯删除和文件重命名；二进制内容不分析并列为未审查；最大 1 MiB、200 个文件或 10,000 个变更行，任一超限即拒绝。
- **验收标准**：文本和文件形式的有效 unified diff 均能被接收且内容一致；空 diff、纯删除、重命名、二进制和三类超限样例均按上述规则处理，不静默丢弃后声称完整审查。

#### FR-002 接收 GitHub PR／GitLab MR 链接

- **需求描述**：【已确认，C-001、C-003～C-010】MVP 必须同时支持 GitHub.com PR 链接和 GitLab.com MR 链接，包括需要访问授权的私有仓库；首版不支持企业自建 GitLab 或 GitHub Enterprise Server。私有仓库访问凭证由运行者预先配置，用户每次审查不重复提供；每个平台仅使用一份共享只读凭证，所有本机可信用户均可更新或清除该凭证。
- **正常流程**：运行者预先配置有效访问凭证 → 用户提交支持的平台链接 → 使用已有授权在允许范围内获取对应变更 → 向用户明确本次审查对象；需要更换凭证时，由运行者或具备相应资格的用户更新共享凭证。
- **异常场景**：链接无效、对象不存在、共享凭证未配置、失效或权限不足、平台不可用、获取内容不完整，或链接指向自建实例时，反馈对应失败，不将其当作无变更。
- **边界条件**：首版不支持按用户、组织或仓库切换凭证，也不在共享凭证失败时自动尝试其他身份。所有本机可信用户均可更新或清除凭证；更新只影响之后启动的任务，以及恢复任务中尚未发起的平台请求。支持打开状态和 Draft 对象；不支持已关闭或已合并对象。任务固定启动时的提交版本；完整 diff 无法取得时失败。GitHub.com 与 GitLab.com 之外的平台域名不属于首版范围。
- **验收标准**：运行者为 GitHub 和 GitLab 各完成一次只读凭证配置后，用户无需在每次审查中再次提供凭证；本机可信用户能更新或清除凭证，新凭证按上述规则生效；两平台各自的公开、私有、打开及 Draft 样例均能获取正确且完整的固定版本变更；关闭、合并、变更获取不完整、凭证未配置／失效／权限不足及平台不支持的样例均明确失败。

#### FR-003 校验输入并反馈不可处理原因

- **需求描述**：【已确认，C-009～C-010、C-023】在无法开展有效审查时，向用户给出具体原因，避免产生看似正常但基于错误输入的报告。
- **正常流程**：检查输入是否属于支持范围 → 接受有效输入，或告知不可处理原因及可由用户纠正的条件。
- **异常场景**：同时提供链接和 diff、缺少输入、内容损坏、仅部分输入可用。
- **边界条件**：空 diff 返回“无变更”；一次任务同时提供多种输入时拒绝，不推断优先级。
- **验收标准**：约定的错误输入样例均得到可区分的原因；输入未被接受时，不输出“已完成审查且未发现问题”。

#### FR-004 明确本次审查对象与范围

- **需求描述**：【已确认，C-010、C-012、C-023】用户可以确认本次审查对应的固定输入版本，以及已审查、未审查和不可处理部分；审查可按需只读同一版本仓库中的相关文本文件。
- **正常流程**：确认输入对应的内容版本与范围 → 开展审查 → 在结果中说明实际覆盖范围及限制。
- **异常场景**：无法确认输入完整性、内容在任务期间变化、部分文件不可处理。
- **边界条件**：独立 diff 以所提交内容标识，不强求提交编号；平台输入固定启动时提交版本。只读上下文限于相关文本文件，不读取二进制文件；上下文不足不代表变更无问题。
- **验收标准**：结果可核对其对应输入；未处理部分明确可见；审查期间源变更变化时，不把旧内容结论冒充为新版本结论。

### E2 审查与结果交付

#### FR-005 基于变更识别审查问题

- **需求描述**：【已确认，C-011、C-023】对 Python、JavaScript 和 TypeScript 变更审查正确性、安全、可靠性及明显性能问题；仅在影响行为或维护风险时评论可维护性，不输出纯格式或个人偏好型风格评论。
- **正常流程**：读取受支持的变更及允许使用的上下文 → 判断是否存在值得反馈的问题 → 形成有依据的候选评论。
- **异常场景**：分析失败、模型回复无法形成有效结论、依赖证据缺失、内容超出支持范围。
- **边界条件**：只评论由本次变更引入或明显加剧的问题；既有且未被变更影响的问题不纳入。不能把“必须产出评论”理解为每个输入都必须发现缺陷。
- **验收标准**：使用至少 8 个固定标注样例覆盖三种语言、缺陷和干净变更；所有预置高置信度缺陷均被发现，干净样例不产生高置信度误报。结果仅说明该样例集，不宣称保证发现全部问题。

#### FR-006 提供可定位、可核对的评论

- **需求描述**：【已确认，C-012、C-023】每条评论说明代码位置、问题、触发条件或证据、可能影响和修复建议。
- **正常流程**：形成问题结论 → 关联代码位置与依据 → 生成用户可理解的评论。
- **异常场景**：位置无法准确确定、依据不足、评论与对应代码不一致。
- **边界条件**：优先关联变更行；删除行、跨文件或文件级问题允许使用对应旧行、文件或多个文件定位，不得虚构精确行号。
- **验收标准**：对包含单文件、删除行及跨文件问题的约定样例，用户可找到所指内容并核对依据；无法准确定位时明确说明局限，不错误绑定无关代码。

#### FR-007 区分无发现与审查不完整

- **需求描述**：【已确认，C-013、C-023】结果区分“完整且无发现”“完整且有评论”“部分完成”和“失败”，避免将失败或未审查理解为代码无问题。
- **正常流程**：结束本次执行 → 说明完成情况 → 交付已有评论或无发现说明，并列明未完成原因。
- **异常场景**：预算耗尽、工具或模型失败、输入部分不可处理、安全拦截导致审查中止。
- **边界条件**：零条评论可能对应正常无发现，也可能对应尚未审查；“无发现”不能承诺不存在缺陷。
- **验收标准**：正常无发现、分析失败、预算中止三个样例呈现不同结果说明；部分结果不得标记为完整结果，已有有效结果必须保留在部分报告中并列明未完成原因。

#### FR-008 确定受支持的输出方式

- **需求描述**：【已确认，C-002】首版仅以 Markdown 报告交付 review 评论，三种输入均适用，不提供远程回评。
- **正常流程**：按已确认支持的交付方式开展任务 → 将结果交付到对应位置。
- **异常场景**：用户请求未支持方式，或所选方式无法交付。
- **边界条件**：提交平台链接不代表授权远程发布；报告交付失败不能自动转为远程回评。
- **验收标准**：三种输入均可通过 Markdown 报告完成交付闭环；请求远程回评时明确反馈首版不支持，不向 MR／PR 发布评论。

#### FR-009 交付 Markdown 报告

- **需求描述**：【已确认，C-002】首版交付可阅读的 Markdown，包含 review 评论，并承载已确认的范围、完成情况、置信度和 trace 关联要求。
- **正常流程**：获得审查结果 → 形成报告 → 告知用户报告位置或提供报告内容。
- **异常场景**：报告无法交付、内容生成不完整、结果中的 trace 无法关联。
- **边界条件**：零评论仍生成报告；每个新任务使用唯一任务标识生成独立报告；同一任务恢复时更新该任务报告，不覆盖其他任务报告；报告的可取得位置随任务结果返回。
- **验收标准**：用户能取得并阅读报告；每条评论的置信度和 trace 可识别；无发现与部分完成样例符合 FR-007；不含禁止交付的敏感内容。

#### FR-010 直接回评 MR／PR

- **需求描述**：【已确认首版不纳入，C-002、C-023】保留为未排期候选需求：将评论提交到正确 MR／PR。发布授权和评论形式不属于当前需求基线。
- **正常流程**：明确目标及已获授权的发布行为 → 发布对应评论 → 告知发布结果。
- **异常场景**：缺少发布权限、远程平台拒绝、部分发布成功、请求结果未知、评论位置已失效。
- **边界条件**：源对象新增提交或关闭、无发现时是否回评等规则留待该能力未来重新立项；不得将读取权限视为发布授权。
- **验收标准**：在已授权的样例对象上，发布内容与审查结果一致且目标正确；部分失败可区分已发布与未发布内容；重复恢复遵守 FR-014。

### E3 异常恢复与结果一致性

#### FR-011 保留 checkpoint

- **需求描述**：【已确认，C-014、C-023】执行期间自动保留可恢复进度，至少覆盖输入获取、单个文件审查和单个工具执行单元；checkpoint 在任务结束后保留 7 天。
- **正常流程**：执行产生阶段性有效进度 → 该进度成为异常后可复用的 checkpoint。
- **异常场景**：进度保留失败、保留中途发生中断、已有 checkpoint 不可读取。
- **边界条件**：第一个 checkpoint 在输入校验和输入获取完成后形成；在此之前中断允许重新开始。最多重做一个尚未完成的审查或工具单元，不能要求不存在的已完成进度被恢复。
- **验收标准**：在约定的多个中断位置停止执行后，仍能识别此前有效 checkpoint；保存失败不得被报告为“进度已保存”。

#### FR-012 从有效进度恢复

- **需求描述**：【已确认，C-014、C-023】用户使用同一任务标识手动发起恢复，系统自动加载有效 checkpoint，复用已完成工作并继续未完成部分。
- **正常流程**：原异常条件解除 → 恢复同一任务 → 复用有效已完成部分 → 继续未完成部分并交付结果。
- **异常场景**：checkpoint 缺失或损坏、恢复时依赖仍不可用、恢复再次中断。
- **边界条件**：未完成工作可能需要重做；“可恢复”不等于任意时刻均零损失，也不等于所有外部操作都必然只执行一次。
- **验收标准**：分别模拟模型超时／限流、工具失败、平台临时失败、进程退出和机器重启；在持久进度仍可读取的情况下，以同一任务标识恢复后复用已完成单元，最多重做一个未完成单元，且不丢失已保留评论。

#### FR-013 识别恢复条件变化

- **需求描述**：【已确认，C-015、C-023】任务固定输入版本与审查规则；恢复时不得混合其他输入版本或规则产生的结果。
- **正常流程**：恢复前确认当前条件与已有进度的适用关系 → 继续有效部分，或明确说明不能按原条件恢复。
- **异常场景**：diff 已变化、关键审查规则或工具能力变化、原访问权限失效。
- **边界条件**：输入或审查规则变化必须创建新任务；原任务仍按其固定版本恢复。允许追加 token 预算，追加前的累计消耗不清零。工具或模型不再可用时，按部分完成规则处理，不将不同规则下的结果混合为完整结果。
- **验收标准**：输入变化样例不能静默沿用旧结论作为新结论；预算变化样例不能把历史消耗清零；其他条件按确认后的失效规则验收。

#### FR-014 处理执行结果不明与重复产出

- **需求描述**：【已确认，C-015、C-019、C-023】对于中断时结果不明的模型调用和报告交付，恢复时不假定其未发生，避免重复产出并如实计算预算。
- **正常流程**：恢复时辨认已完成、未完成及结果不明的工作 → 按已确认的处理规则继续 → 交付一致的结果和消耗说明。
- **异常场景**：平台已收到评论但任务未收到确认；模型可能已经计费但回复未取得；部分结果已交付后中断。
- **边界条件**：模型调用结果不明时不自动重试，将预留的最大 token 计入不确定消耗并暂停；用户显式恢复且预算仍允许时才可重试。报告通过任务标识核对已有结果，同一任务只更新自己的报告；不承诺外部调用结果无法核实时绝对零重复计费。
- **验收标准**：已确认成功的评论在恢复后不重复交付；结果不明样例被明确识别，并符合确认后的规则；已知费用不漏计，不确定费用不按零计冒充确定事实。

### E4 评论可追溯

#### FR-015 每条评论关联 trace

- **需求描述**：【明确】每条最终 review 评论都能关联到其生成过程的 trace。首版验收 Markdown 报告中的评论；远程回评关联要求留待未来纳入该渠道时适用。
- **正常流程**：评论形成并交付 → 用户通过评论关联信息查到对应 trace。
- **异常场景**：trace 缺失、关联错误、关联内容不可访问。
- **边界条件**：不同评论可共享部分过程，但仍需区分各自依据；Markdown 报告为每条评论展示 trace ID 和摘要；完整 trace 仅供本机可信用户查看并保留 7 天。
- **验收标准**：逐条核对交付评论，均能找到与该评论相符的 trace；仅展示一个无法查到记录的编号不算满足可追溯要求。

#### FR-016 核对评论生成过程

- **需求描述**：【已确认，C-016、C-021、C-023】trace 记录输入身份、脱敏后的 diff、实际发送给模型的 prompt、模型回复、工具调用与结果、预算、错误和 checkpoint 事件；不记录模型内部思维过程。
- **正常流程**：查看评论 trace → 核对实际使用的变更内容、工具及相关结果、模型输入输出 → 理解评论依据。
- **异常场景**：工具失败、调用中断、模型回复缺失、部分材料因安全要求不能展示。
- **边界条件**：未使用工具时如实说明，不虚构工具验证；输入来源内容与实际送入模型的内容可能因安全处理不同，应能区分；不要求获取模型未提供的内部思维过程。
- **验收标准**：选取包含工具调用、失败调用、敏感内容处理的样例，trace 与实际行为一致，能识别缺失或受限材料；“原始 diff”如何满足安全规则须先确认，不能以可观测为由泄露 secret。

### E5 工具能力扩展

#### FR-017 新工具声明式注册

- **需求描述**：【明确】新增工具通过声明式注册接入，不修改主流程。允许新增工具本身的能力内容；题目并未要求“不写任何代码即可创造新能力”。
- **正常流程**：维护者提供一个符合已确认接入要求的新工具并完成声明 → 工具在适用审查中可用 → 结果参与 review。
- **异常场景**：声明不完整、工具不可用、身份重复、工具不满足接入要求。
- **边界条件**：首版扩展仅限对已授权文本做只读、确定性静态分析；typecheck 因可能执行仓库控制的配置、插件或依赖而不纳入。修改编排或核心审查流程即视为修改主流程。
- **验收标准**：通过声明接入一个原先不存在的“静态模式检查工具”并完成审查演示，能核对其调用和结果；接入前后不修改主流程；工具不执行仓库内容或访问外部服务。

#### FR-018 识别不可用工具及失败影响

- **需求描述**：【已确认，C-017、C-023】扩展工具均为可选；不可用或失败时继续其他审查，在报告和 trace 中说明部分验证及其影响，不将失败工具标为已验证。
- **正常流程**：工具成功时使用其结果；不可用或失败时说明原因及缺失的验证。
- **异常场景**：工具超时、返回结果无效、缺少前置条件、声明无效。
- **边界条件**：工具失败不单独终止任务；如果缺少该工具使某条评论证据不足，则评论降为“仅供参考”或在无可行动依据时不输出。
- **验收标准**：故意使工具失败，报告和 trace 不显示该工具“验证通过”；结果完成情况和置信度反映证据缺失，并符合确认后的继续规则。

#### FR-019 扩展工具遵守共同约束

- **需求描述**：【已确认，C-017、C-021～C-023】新增工具必须遵守安全、预算、可追溯和恢复要求；声明注册不授予任意执行或数据发送权限。
- **正常流程**：工具在已允许范围内执行 → 相关行为纳入 trace、恢复语义及适用预算口径。
- **异常场景**：工具要求执行未授权仓库内容、尝试额外发送敏感数据、产生未被允许的收费行为。
- **边界条件**：首版工具无外部服务和独立计费，仅能读取已授权文本；未来增加收费工具或外部服务属于范围变更，需重新明确预算和数据边界。
- **验收标准**：扩展工具的安全禁止行为被阻止；成功及失败行为可核对；工具涉及的消耗不绕过已确认的预算口径；中断后遵守对应恢复规则。

### E6 审查预算

#### FR-020 设置单次审查总预算

- **需求描述**：【已确认，C-018、C-023】单次任务 CNY 金额上限及当前模型每百万 token 综合单价来自本地配置，不依赖 CLI 或调用方参数注入。
- **正常流程**：加载金额和单价配置 → 使用 Decimal 向下取整换算 token 硬授权 → 按该约束开展审查。
- **异常场景**：金额或单价非正数、非有限值、换算不足 1 token 或超过安全 token 上限。
- **边界条件**：当前只支持 CNY 和单一综合单价，换算授权最大 1,000,000 token；同一 PR/MR 的不同新任务预算独立，同一任务恢复沿用启动时授权和累计消耗。
- **验收标准**：不同有效金额/单价配置能确定性换算；无效配置明确反馈；CLI 不接受 token 预算参数；报告同时展示 token 与 CNY 口径。

#### FR-021 约束继续消耗

- **需求描述**：【已确认，C-019、C-023】预算通过调用前预留实施硬约束；剩余预算不足时停止新增模型调用，保留已有结果并生成部分报告，可追加预算后恢复。
- **正常流程**：在继续发生计入预算的消耗前确认其符合预算限制 → 可以继续则执行，否则按约定停止或缩减审查范围。
- **异常场景**：费用无法确定、调用结果不明、重试再次产生消耗、实际消耗与预期不同。
- **边界条件**：模型输入、输出、失败调用及重试均计入；调用前按输入与允许最大输出预留，已知实际用量结算；结果不明时按预留上限计入不确定消耗。本地无计费工具不计入；用户未追加预算前不得提高上限。
- **验收标准**：覆盖预算充足、不足、耗尽和重试样例；只有调用的最大预留 token 不超过剩余预算时才允许发起，首版不设置超限容差；受预算影响的未完成部分明确标注。若外部服务返回的可信实际用量异常超过预留值，如实登记实际值与超出量，冻结同一任务的后续模型调用并在部分报告中披露；只有用户追加授权使其覆盖当前已知实际、不确定消耗和活动预留、显式恢复并重新通过固定 Provider 的硬预算能力验证后才能解除冻结，下一调用仍须独立通过预留门禁。

#### FR-022 展示累计消耗及剩余预算

- **需求描述**：【已确认，C-018～C-019、C-023】用户可核对任务总预算、实际消耗、预留或不确定消耗及剩余预算；恢复和重试沿用任务累计消耗。
- **正常流程**：消耗发生并被确认 → 累计计入任务 → 在任务结果中说明消耗、单位及是否为估算。
- **异常场景**：费用信息缺失、请求是否计费不明、消耗记录与外部账单不一致。
- **边界条件**：首版不进行金额换算；失败调用和重试按可获得的 token 用量累计，未知调用按其预留上限列为不确定消耗，剩余预算不得冒充精确实际费用。
- **验收标准**：使用可核对消耗的样例，累计值与确认口径一致；恢复后已知消耗不归零；授权、活动预留、已知实际、不确定消耗、超出量、授权赤字和冻结状态明确区分，超额不得通过把剩余预算截断为零而隐藏。

### E7 置信度分级

#### FR-023 为每条评论标注置信等级

- **需求描述**：【已确认，C-020、C-023】每条评论使用“高置信度可直接采纳”和“仅供参考”两级；该标签描述结论可信程度，不触发自动修改或合并。
- **正常流程**：形成评论 → 按统一分级规则判定 → 在交付内容中显示该评论等级。
- **异常场景**：缺少分级所需证据、无法判定等级、等级缺失。
- **边界条件**：置信度描述结论可信程度，不等于问题影响严重程度；“可直接采纳”不自然赋予自动修改或合并权限。
- **验收标准**：每条评论都有已定义的置信等级；不同证据强度样例按确认规则分类；不以严重程度标签替代置信度标签。

#### FR-024 给出分级依据并反映证据不足

- **需求描述**：【已确认，C-020、C-023】每条评论说明分级依据。高置信度要求直接代码证据，并经确定性工具验证或具有可直接核对的语言语义依据；模型自评分不能单独决定等级，工具验证不是所有高置信度评论的必需条件。
- **正常流程**：结合实际可用依据进行分级 → 说明支持该等级的事实及结论限制。
- **异常场景**：证据相互矛盾、工具验证失败、关键上下文缺失。
- **边界条件**：高置信度不等于保证正确；证据不足或冲突时降为“仅供参考”，完全没有可行动依据时不输出。
- **验收标准**：每个等级均有可核对判定条件；证据不足及冲突样例不被无依据标为高置信度；分级依据与 trace 一致。

### E8 安全边界

#### FR-025 secret 不上传 LLM

- **需求描述**：【已确认，C-021、C-023】访问令牌、API Key、密码、私钥、连接串、云凭证、证书、个人信息和明确标记的业务敏感数据不得发送给 LLM；适用于 diff、上下文、工具结果及其他模型输入。
- **正常流程**：确认拟发送内容符合敏感信息规则 → 仅符合规则的内容允许提供给 LLM。
- **异常场景**：发现 secret、无法判定是否敏感、安全检查不可完成、工具结果携带 secret。
- **边界条件**：新增行、删除行和上下文均需遵守规则；发现敏感内容时脱敏后继续，无法安全脱敏则跳过相关片段并标记部分审查；无法判断时按敏感内容处理。仅承诺覆盖已定义类别和验收样例，不宣称识别所有未知形式。
- **验收标准**：在双方确认的敏感信息样例集上，核对所有 LLM 实际接收内容，禁止上传的原值均不出现；规则不可执行时不得绕过限制继续发送。有限样例通过不等于证明识别所有未知 secret。

#### FR-026 防止留痕与交付造成敏感信息泄露

- **需求描述**：【已确认，C-016、C-021、C-023】敏感信息保护覆盖 Markdown 报告、trace、checkpoint 和错误说明；禁止持久化明文敏感值。完整 trace 仅供本机可信用户查看并保留 7 天。
- **正常流程**：生成留痕与交付材料 → 根据已确认的数据规则提供可核对内容 → 告知必要的安全处理限制。
- **异常场景**：敏感内容出现在错误信息、模型回复或工具结果中；完整原始记录与保护规则冲突。
- **边界条件**：脱敏后的私有源代码允许发送给已配置 LLM；个人信息和明确标记的业务敏感数据按敏感信息处理。用户最初提供的原始输入可在当前任务内读取，但不得复制为持久明文记录。
- **验收标准**：核对包含模拟 secret 的任务全部留痕和交付材料，未向不允许的对象暴露禁止内容；对因安全限制缺失的原始证据明确说明，不将处理后的内容冒充完整原文。

#### FR-027 不在用户仓库执行任意代码

- **需求描述**：【已确认，C-017、C-022～C-023】首版只允许读取和静态分析已授权文本，不得执行用户仓库中的代码，也不得加载由仓库控制的插件、依赖或可执行配置。
- **正常流程**：仅在确认允许的行为范围内完成审查及工具检查。
- **异常场景**：仓库脚本、配置、依赖或工具请求触发未允许的执行行为。
- **边界条件**：禁止运行脚本、构建、测试、typecheck、包管理器和钩子；工具名看似安全不构成执行授权。仅纯文本解析和确定性静态检查属于首版允许行为。
- **验收标准**：使用含模拟恶意脚本、配置诱导和未授权执行请求的固定样例，不发生禁止执行行为；被阻止的检查不显示为成功；只有纯文本解析和确定性静态检查可标记为允许行为，不能仅按工具名称判断。

#### FR-028 不因仓库内容改变授权边界

- **需求描述**：【已确认，C-022～C-023】代码、注释、diff、仓库说明和工具返回内容均视为不可信数据，不能授予权限、提高预算、改变发布目标或放宽安全规则。
- **正常流程**：将输入内容用于理解变更 → 后续行为始终遵守用户授权及已确认约束。
- **异常场景**：输入包含“忽略规则”“上传密钥”“执行脚本”或“发布到另一地址”等诱导内容。
- **边界条件**：只有本机可信用户在系统明确提供的任务操作中作出的变更才有效；输入文本或仓库内容中的声明一律不能改变授权、预算和安全边界。
- **验收标准**：加入针对数据发送、代码执行、预算和发布目标的模拟诱导内容，禁止行为均未发生；正常代码内容仍可在安全范围内被审查。

### 5.1 原模糊点及裁决

所有原待确认项均已裁决。具体行为以 C-001～C-023 和对应 FR 为准。

| 主题 | 已确定口径 |

| Trace | 每条评论关联 trace ID；保存脱敏 diff、实际 prompt／回复、工具、预算、错误和恢复事件；保留 7 天，不要求逐字重放 |
| 工具 | 只允许只读确定性文本静态分析；用静态模式检查演示扩展；typecheck、仓库代码执行和外部服务不纳入 |
| 预算 | 配置单次 CNY 上限与模型每百万 token 综合单价，Decimal 向下取整为不超过 1,000,000 token 的硬授权；调用前硬预留；耗尽交付部分报告；实际超预留时冻结，足额追加、显式恢复和 Provider 能力重验证后可在原任务继续 |
| 置信度 | 两级；高置信度必须有直接证据及工具验证或可直接核对的语言语义依据；模型自评分不能单独决定 |
| 敏感信息 | 已定义 secret、个人信息及明确业务敏感数据先脱敏；无法安全处理则跳过；明文不得进入 LLM 或持久记录 |
| 权限与提示注入 | 仓库内容不具备授权能力；只接受本机可信用户通过明确任务操作作出的权限、预算或规则变更 |

### 5.2 冲突点

| 冲突或张力 | 为什么成立 | 需要确认的业务裁决 |
| --- | --- | --- |
| 原始 diff／prompt／回复留痕与 secret 保护 | 原始材料自身可能包含敏感信息，复制到 trace 会扩大暴露范围 | 已裁决：trace 仅保留脱敏材料；明文敏感值不持久化，无法安全处理的片段跳过 |
| “token 预算”与“10 元／MR” | token 数与金额不是同一单位 | 已裁决：首版只支持 token 预算，不做金额换算 |
| 固定预算与完整审查 | 预算可能不足以覆盖全部变更及必要证据 | 已裁决：停止新增模型调用、交付部分报告，允许追加预算后恢复 |
| 声明式工具扩展与禁止任意代码执行 | 新工具可能要求执行仓库配置、脚本或依赖 | 已裁决：首版工具仅执行只读确定性文本分析，typecheck 不纳入 |
| 异常恢复与外部操作结果不明 | 超时不代表未计费，重试可能重复消耗 | 已裁决：不自动重试，按预留上限记录并暂停，由用户显式恢复 |
| 高置信度“可直接采纳”与证据不足 | 只有 diff 时可能缺少足够上下文，工具失败也会减少证据 | 已裁决：需直接证据和额外验证；证据不足或冲突降级，无可行动依据则不输出 |
| 本地流程文件建议的最小路径与已确认输入范围 | 本地流程建议仅支持 diff，用户现已要求三种输入全部支持 | 输入冲突已由 C-001 裁决，以三种输入为准；输出已由 C-002 确认为仅 Markdown |

上述张力均已按安全优先、结果如实、范围最小的原则裁决。

### 5.3 隐含需求

以下隐含需求均已确认为 MVP/P0，用于使题目明确能力形成可验收闭环：

| 隐含需求 | 如果缺失会怎样 | 对应需求 |
| --- | --- | --- |
| 输入有效性与完整性反馈 | 可能把无法读取误报为无问题 | FR-003～004 |
| 评论位置、依据与影响 | 用户无法核对或采取行动 | FR-006 |
| 完成情况与覆盖范围说明 | 预算或失败导致的遗漏不可见 | FR-007 |
| 恢复条件与未知结果处理 | 旧结果混用、重复评论或遗漏费用 | FR-013～014 |
| trace 实际可查与真实记录 | 有编号但无法解释评论来源 | FR-015～016 |
| 工具失败不能冒充成功 | 错误增加结论可信度 | FR-018 |
| 扩展工具继承既有约束 | 新能力成为安全或成本缺口 | FR-019 |
| 累计消耗与不确定费用说明 | 无法核对预算，恢复可能绕过限额 | FR-022 |
| 分级可解释 | 置信度标签无法验收 | FR-024 |
| 留痕与交付的敏感信息规则 | secret 未进模型却可能出现在报告或 trace | FR-026 |
| 输入不能自授权限 | 仓库内容可能诱导越界行为 | FR-028 |

## 6. 需求裁决原则

1. 对题目明确能力保留要求，对示例保留选择空间；“例如 typecheck”不等于必须内置 typecheck。
2. 对题目未给出的范围采用能够完成端到端验收的最小集合；必要阈值和默认值以 C-008～C-023 为准。
3. 所有明确要求及其必要闭环需求均列为 P0；远程回评不纳入首版且不承诺排期。
4. 具体凭证格式、存储介质等实现问题留到技术选型，不作为未解决的业务需求。
5. 安全目标与可证明范围应分别说明；不能以一组样例通过宣称覆盖一切 secret 或一切恶意代码。

## 9. 最核心的需求、最大的需求风险与关键裁决

### 9.1 最核心的需求

**将一份明确的代码变更转化为有依据、可供人判断的 review 评论，并完成交付。** checkpoint、评论 trace、声明式扩展、预算、置信度和安全是这个闭环的必备约束；不能以生成了一份报告替代这些约束的满足。

### 9.2 最大的需求风险

**最大风险是敏感信息识别只能对已定义类别和固定样例给出可验证保证，无法证明覆盖所有未知 secret。** 因此发现疑似敏感内容时采用保守处理：先脱敏，无法安全处理则跳过并将报告标为部分完成；trace 只保存脱敏材料。工具扩展同样限定为只读确定性文本分析，避免扩大执行风险。

其他高影响风险是：遗漏已确认的三种输入之一、把支持平台链接误解为必须直接回评、混淆 token 与金额预算、将外部操作超时理解为未发生，以及置信等级缺少共同判断标准。

### 9.3 原最需确认的 5 个问题及最终结论

1. **用户和凭证权限**：首版面向本机可信用户；所有系统使用者均可发起任务、查看报告与 trace，并更新或清除每个平台的一份共享只读凭证。
2. **安全边界**：定义的 secret、个人信息及明确业务敏感数据不得进入 LLM 或持久记录；先脱敏，无法安全处理则跳过；禁止执行任何仓库代码及仓库控制的配置、插件或依赖。
3. **预算口径**：首版仅使用单任务 token 硬预算；覆盖输入、输出、失败和重试；耗尽后停止新增调用并交付部分报告，允许追加预算恢复。
4. **恢复保证**：覆盖模型、工具、平台临时失败、进程退出和机器重启；最多重做一个未完成单元；输入或规则变化创建新任务；未知模型调用不自动重试。
5. **有效审查与高置信度**：支持 Python、JavaScript、TypeScript，聚焦正确性、安全、可靠性和明显性能问题；高置信度必须有直接证据及工具验证或可直接核对的语言语义依据，并通过固定样例验收。
