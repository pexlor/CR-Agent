## 2. 架构目标

系统架构优先满足以下目标：

1. 模块之间保持低耦合，每个模块具有单一且清晰的职责；
2. 新增输入源、模型供应商、审查工具或报告输出时能够快速开发；
3. 核心业务不依赖 CLI、第三方 SDK、存储或具体模型实现；
4. 可恢复、预算、安全和 Trace 等约束不能被适配器或扩展绕过；
5. 保持本地单进程 MVP 的简单性，不提前设计 Web、多用户或分布式架构。

## 3. 已确认技术选型

| 层级 | 选择 | 用途 |
| --- | --- | --- |
| 语言与运行时 | Python 3.12 | CLI、业务编排和外部能力接入 |
| 项目与依赖管理 | uv、`pyproject.toml`、`uv.lock` | 可复现安装、构建和命令入口 |
| CLI | Typer、Rich | 命令、参数校验、进度和错误展示 |
| 数据模型与配置 | Pydantic v2、pydantic-settings、TOML | 领域数据、外部结果和配置校验 |
| 模型适配 | LangChain ChatModel adapters | OpenAI、Anthropic 和 OpenAI-compatible 接入 |
| 平台适配 | PyGithub、python-gitlab、受限 HTTPX | GitHub/GitLab 输入和固定版本上下文读取 |
| Diff 解析 | unidiff + 项目严格校验层 | diff 结构解析和完整性校验 |
| 持久化 | Python `sqlite3` | 任务、checkpoint、预算、Trace 和结果存储 |
| 凭证 | keyring | 操作系统账号级凭证存储 |
| Secret 检测 | detect-secrets + 项目自有规则 | 出站与落盘前检查 |
| 审查工具运行时 | 声明式 TOML/JSON 规则 + 系统自有受限解释器 | 在单进程内提供不可获得 Python 执行、网络或文件系统能力的确定性分析 |
| 报告 | Jinja2 | 确定性生成 Markdown |

| 用户目录 | platformdirs | 跨平台配置、数据和报告目录 |

首版不引入 Web 框架、后台任务队列、PostgreSQL、Docker、LangChain Agent、LangGraph、向量数据库或多租户权限系统。完整选择理由和替代方案见《Code Review Agent 技术选型设计》。

## 4. 总体架构方向

系统采用 **模块化单体 + 端口／适配器 + 显式工作流**。

系统作为一个 Python CLI 进程运行，但按照业务能力划分独立模块。核心模块只依赖项目定义的数据契约和端口；GitHub、GitLab、模型、SQLite、凭证和 Markdown 等外部能力通过适配器接入。

```text
CLI 接口层
    ↓
任务编排层
    ↓
┌──────────────── 核心业务模块 ────────────────┐
│ 输入标准化  审查规划  审查执行  发现处理       │
│ 任务状态    预算控制  安全策略  Trace  报告模型 │
│ 受限工具运行时                               │
└─────────────────────────────────────────────┘
    ↓ 通过端口调用
┌──────────── 外部适配器与声明式资源 ────────────┐
│ 输入源  模型  规则包  SQLite  凭证  Markdown │
└──────────────────────────────────────────────┘
```

选择该方案是因为它能够隔离核心业务与技术实现，为四类已确认扩展提供稳定边界，同时避免把所有流程阶段都做成动态插件所带来的恢复、预算和安全复杂度。

## 5. 模块划分与职责

### 5.1 CLI 接口模块

负责接收命令、参数和用户输入，并展示进度、结果及错误。

CLI 只调用应用用例，不参与输入解析、预算判断、审查分析或状态管理。未来增加 Web/API 时，可以增加新的接口适配器，而不改变核心业务模块。

### 5.2 任务管理模块

负责创建、恢复、查询、追加预算和清理任务，并维护任务生命周期。

任务管理模块拥有任务状态变更权。其他模块返回执行结果或领域事件，但不能自行推进任务状态。

### 5.3 审查编排模块

负责通过显式工作流组织一次完整审查：

```text
获取输入 → 安全处理 → 制订审查计划 → 执行审查
→ 验证发现 → 汇总结果 → 生成报告
```

该模块只负责步骤顺序、状态协调和失败边界，不实现各步骤内部的业务逻辑。恢复任务时，它根据已保存状态从下一个未完成工作单元继续执行。

### 5.4 输入模块

负责校验输入类型、内容和规模，并将 diff、GitHub PR、GitLab MR 统一转换为稳定的变更集模型。

平台 SDK、网络请求、分页和平台异常均封装在输入适配器中，不泄漏到其他模块。

### 5.5 审查规划模块

负责根据标准化变更集生成可独立保存、执行和恢复的审查工作单元，并标识已审查、未审查和不可审查范围。

该模块不调用模型，也不关心变更来自哪个输入平台。

### 5.6 审查执行模块

负责执行一个审查工作单元，协调模型和确定性工具，并产生候选发现。

所有模型请求只能通过模型端口发出；所有工具只能通过工具端口执行。审查执行模块不直接依赖具体模型 SDK 或工具实现。

### 5.7 发现处理模块

负责候选发现的结构校验、位置验证、证据核对、去重、置信度分级和最终合并。

该模块不直接调用模型，避免未经验证的模型结果进入最终报告。

### 5.8 预算模块

负责预算初始化、调用前预留、调用后结算、不确定消耗、预算异常、预算追加和剩余额度判断。

模型适配器不能自行决定是否允许发起调用，也不能绕过预算模块修改消耗记录。

如果供应商报告的实际 usage 超过调用前预留值，预算模块必须如实登记实际值和超出量，把任务标记为预算异常并冻结后续模型调用。该情况不能被折算、截断或伪装为正常的“预算耗尽”；只有用户追加足以覆盖累计消耗及下一次预留的预算并显式恢复后，才能继续调用。

### 5.9 安全模块

负责敏感信息识别、脱敏、跳过策略、仓库内容信任边界和安全日志边界。

模型出站、模型响应、工具输入与输出、Trace、checkpoint、日志、错误信息和报告落盘都必须经过安全模块；安全检查不是调用方可以关闭的可选能力。外部响应进入领域模型、Trace 或持久化之前必须先通过入站安全门禁，不能先保存原始响应再异步清理。

安全模块拥有安全策略，通过扫描端口使用具体检测能力；detect-secrets 等第三方实现位于外围适配器，不进入领域核心。

应用只允许通过统一安全日志端口写入结构化、已脱敏事件。第三方 SDK 的请求／响应调试日志默认关闭；必须保留的第三方错误先在适配器边界转换为白名单字段，再进入安全日志端口。安全扫描器不可用或处理结果不确定时，相关数据不得出站或落盘，任务按安全边界失效停止。

### 5.10 Trace 模块

负责记录实际审查过程，并建立任务、工作单元、模型调用、工具调用和最终评论之间的关联。

Trace 模块记录事实，不决定业务流程，也不接收或保存未经安全处理的数据。

Trace 与 checkpoint 使用统一的数据生命周期策略：未结束任务的恢复有效期按最近有效 checkpoint 计算；任务进入终态后，完整 Trace 和 checkpoint 至少保留七天。清理由任务管理用例显式发起，通过持久化端口以幂等事务删除关联数据；清理失败必须可观察且不得留下可被误认为完整 Trace 的残缺集合。

### 5.11 报告模块

负责把结构化任务结果转换为与输出格式无关的报告模型，再交给输出适配器生成最终产物。

未来增加 JSON 等无外部副作用的本地产物时，只增加相应 Output Adapter，审查模块不感知具体格式。远程回评具有外部副作用、发布授权和幂等要求，不属于当前 Output Adapter 的扩展承诺；引入时必须新增独立交付用例、发布状态模型和权限设计。

### 5.12 扩展与适配器模块

系统提供四类独立扩展点：

- **Input Provider**：增加新的输入来源；
- **Model Provider**：增加新的模型供应商；
- **Review Tool**：增加新的确定性审查工具；
- **Output Adapter**：增加新的输出方式。

扩展通过声明和注册接入。注册器只负责扩展发现、元数据校验和能力约束，不承载业务流程。

Input Provider、Model Provider 和 Output Adapter 是由应用维护者安装并信任的基础设施代码，因为它们按职责需要网络、凭证或文件交付能力。Review Tool 的受限能力属于安全边界，不能仅依赖 Python 接口约定：MVP 只加载声明式规则包，由系统自有的受限工具运行时解释执行，不导入或执行扩展包中的 Python 模块、回调、仓库配置或其他可执行内容。

### 5.13 基础设施模块

负责 SQLite、keyring、文件系统、平台 SDK、HTTP 客户端和其他第三方库的具体接入。

基础设施模块实现核心层定义的端口，但核心业务模块不能反向依赖基础设施模块。

## 6. 依赖规则

1. CLI 接口层只能依赖应用层公开的用例；
2. 应用层可以依赖领域模块和端口，但不能依赖具体适配器；
3. 领域模块之间通过稳定的数据契约协作；
4. 领域层不能依赖 Typer、Rich、SQLite、LangChain、PyGithub、python-gitlab、HTTPX、keyring 或 Jinja2；
5. 外部适配器依赖核心端口，核心不能反向依赖适配器；
6. 应用启动时由唯一的组合入口选择并装配适配器；
7. 模块之间不得共享可变全局状态、数据库连接或第三方 SDK 对象；
8. 所有模型调用必须经过统一模型网关，并强制执行预算、安全、Trace 和调用状态规则；
9. 所有模型出站和持久化内容必须经过安全边界；
10. 每类扩展只能获得完成职责所需的最小能力：Input/Model Provider 只获得对应平台或供应商的定向网络与凭证能力，Output Adapter 只获得当前任务的受限交付目标，Review Tool 规则包不获得数据库、凭证、网络、环境变量、进程或文件系统能力；
11. 模型调用的预算流水、调用状态、脱敏 Trace 和 checkpoint 必须通过同一持久化工作单元提交，不能由不同模块各自独立提交后再依赖补偿保持一致；
12. 所有外部响应必须先通过入站安全门禁，再进入领域模型、日志、Trace、checkpoint 或报告；
13. Review Tool 扩展只允许提供声明式规则数据，由系统受限运行时执行；注册器不得导入或调用扩展提供的任意 Python 代码。

## 7. 正常审查主流程

一次审查由应用编排层按照以下阶段组织：

```text
接收命令
  → 创建任务
  → 获取并固定输入
  → 安全处理与输入标准化
  → 生成审查计划
  → 逐个执行审查单元
  → 验证与合并发现
  → 原子确定审查结果状态
  → 生成并交付报告
  → 记录报告交付状态
```

### 7.1 接收命令

CLI 将用户参数转换为统一的审查请求，完成输入互斥、必填参数和预算范围等基础校验。

CLI 不访问平台、不调用模型，也不直接写入任务状态。

### 7.2 创建任务

任务管理模块生成任务标识，并固定本次任务使用的输入身份、模型及供应商、Token 总预算、审查规则版本、工具声明版本，以及配置和凭证引用。

此阶段只保存任务元数据，不持久化未经安全处理的原始代码。

### 7.3 获取并固定输入

审查编排模块根据输入类型选择对应的 Input Provider：独立 diff、GitHub PR 或 GitLab MR。

输入模块取得完整输入并固定本次审查对象。平台输入固定 base/head SHA；独立 diff 固定内容摘要。无法证明获得完整输入时，任务在输入阶段失败，不进入后续审查阶段。

### 7.4 安全处理与输入标准化

输入模块把原始内容交给安全模块处理，再转换为统一变更集。处理结果分为安全、已脱敏和必须跳过。

只有经过安全处理的数据才能发送给后续模块或写入持久存储。必须跳过的内容需要降低任务覆盖状态，不能被视为已完整审查。

### 7.5 生成审查计划

审查规划模块根据标准化变更集生成可以独立保存、执行和恢复的审查工作单元，并标识已审查、未审查和不可审查范围。

审查计划同时确定每个单元适用的确定性工具。计划生成后，源 PR/MR 的后续变化不得混入当前任务。

### 7.6 逐个执行审查单元

审查编排模块串行执行审查工作单元：

```text
读取固定版本上下文
  → 安全处理
  → 执行适用的确定性工具
  → 安全处理工具结果
  → 组装并再次检查模型请求
  → 原子预留预算、创建调用记录和请求 Trace
  → 调用模型
  → 安全处理模型响应
  → 产生候选发现
  → 原子结算预算、保存候选结果和 checkpoint
```

所有模型请求只能通过统一模型网关发出。模型网关在请求发出前强制完成安全检查、预算预留、Trace 记录和调用状态变更；响应返回后必须先完成入站安全处理，再允许领域校验或持久化。安全处理失败时不得保存原始响应，并把调用转为可审计的安全失败状态。

调用开始前，预算预留、调用记录和脱敏请求 Trace 在同一事务中写入；外部 I/O 开始前先把调用标记为 `running`。响应处理完成后，脱敏响应、usage 结算、调用终态、单元结果和 checkpoint 在另一事务中原子提交。进程在 `running` 与完成事务之间中断时，恢复逻辑一律按 `unknown` 保守处理。

模型不得动态授予工具能力。工具的选择和可用能力由审查计划及系统配置决定。

### 7.7 验证与合并发现

发现处理模块对候选发现执行结构校验、位置验证、证据核对、范围判断、去重、置信度分级和结果合并。

未经验证或缺少可行动依据的模型输出不能进入最终报告。

### 7.8 生成报告

在生成报告前，任务管理模块先根据实际覆盖范围原子写入带版本的审查结果快照：完成、无变更、部分完成、失败或结果不确定。恢复执行可以生成后续版本，但已发布版本不原地改写。报告模块从最新的已持久化快照生成与输出格式无关的报告模型，再交给 Output Adapter 生成最终产物。

报告落盘前必须经过安全检查。输出适配器使用“临时文件完整写入后原子替换”的方式更新当前任务的报告，不能覆盖其他任务结果。

### 7.9 记录报告交付状态

任务分别维护审查结果状态和报告交付状态。报告成功写入后，交付状态变为 `succeeded`；写入失败时变为 `failed`，但不得回滚或改写已经确定的审查结果。恢复时可以只重试报告生成与交付。

“完整审查后无发现”与“审查未完成”必须明确区分。无发现和部分完成场景仍需生成 Markdown 报告。

### 7.10 主流程约束

1. 只有审查编排模块决定步骤顺序；
2. 只有任务管理模块能够推进任务状态；
3. 各阶段通过稳定的数据契约协作，不传递第三方 SDK 对象；
4. 每个审查工作单元完成后立即保存进度；
5. 输入、模型、工具和输出适配器不能绕过预算、安全、Trace 或 checkpoint；
6. 同一任务必须固定输入版本、模型、审查规则和工具声明版本；
7. 审查结果状态与报告交付状态相互独立，报告失败不得把已完成审查改写为审查失败。

## 8. 中断与恢复流程

恢复能力由任务管理模块、审查编排模块、预算模块、Trace 模块和持久化端口共同保证：

```text
用户执行 resume TASK_ID
  → 加载任务快照
  → 校验恢复条件
  → 核对未完成状态
  → 处理不确定调用
  → 找到下一个工作单元
  → 继续正常审查流程
  → 重新生成报告
```

### 8.1 Checkpoint 粒度

至少为输入获取与标准化、审查计划生成、单个文件或分块审查、单个工具执行、单次模型调用、结果汇总和报告生成设置独立 checkpoint。

已完成单元直接复用。中断后最多重新执行一个尚未完成的工作单元。

### 8.2 状态保存原则

每个工作单元采用“执行前记录、执行后确认”的状态模型：

```text
pending → running → succeeded
                  → failed
                  → unknown
```

- `pending`：尚未开始；
- `running`：已经开始但尚未保存最终结果；
- `succeeded`：结果已经安全持久化；
- `failed`：已知失败原因；
- `unknown`：外部调用可能已经完成，但本地无法确认结果。

任务状态、调用状态和预算流水需要保持一致，避免出现任务显示未执行但预算已经消耗的情况。

#### 8.2.1 持久化工作单元

应用层通过统一的持久化工作单元端口提交跨模块状态，SQLite 适配器在一个数据库事务中完成对应写入。领域模块只产生状态变更意图，不各自提交事务。

模型调用至少包含以下原子边界：

1. **调用准备事务**：写入预算预留、调用记录、脱敏请求 Trace 和所属工作单元关系；
2. **调用开始标记**：在外部请求前把调用置为 `running`；该标记存在而完成事务不存在时，恢复为 `unknown`；
3. **调用完成事务**：写入经过安全处理的响应或标准错误、usage 结算、调用终态、候选结果和 checkpoint；
4. **预算异常完成事务**：实际 usage 超过预留时，用调用完成事务同时写入实际消耗及超出量、调用终态、后续调用冻结标记和部分完成结果。

任何事务提交失败都按持久化完整性错误处理，立即停止新的外部调用。不得通过“稍后补写 Trace”或“稍后对账预算”把不一致状态当作正常成功。

### 8.3 恢复条件校验

恢复时必须确认：

- 任务标识存在且 checkpoint 未超过七天；
- 输入身份和固定版本没有变化；
- 模型供应商及模型没有变化；
- 审查规则和工具声明版本没有变化；
- 已有预算记录可以继续累计；
- 持久化状态没有损坏。

输入或规则变化时不能恢复原任务，必须创建新任务。更新后的凭证只影响尚未发起的平台请求。

### 8.4 中断状态处理

| 中断位置 | 恢复策略 |
| --- | --- |
| 尚未开始的工作单元 | 正常执行 |
| 已成功保存的工作单元 | 直接复用 |
| 本地确定性处理过程中断 | 重新执行该单元 |
| 工具执行过程中断 | 重新执行该工具单元并记录新尝试 |
| 模型请求发出前中断 | 释放未使用预留后重新执行 |
| 模型请求发出后结果不明 | 标记为 `unknown`，保留最坏预算，不自动重试 |
| 结果已保存但报告未完成 | 复用结果并重新生成报告 |
| 报告写入过程中断 | 丢弃未完成临时文件，从结构化结果重新生成 |

### 8.5 不确定模型调用

模型调用结果不明时，原调用保留为 `unknown`，对应预留 Token 计入不确定消耗，系统暂停继续调用模型，并在报告中说明当前完成范围和暂停原因。

只有用户显式执行 `resume` 后，系统才允许创建一次新的调用尝试。新尝试必须重新预留预算，且不能覆盖原预算流水。

### 8.6 预算耗尽恢复

预算不足时不再创建新的模型调用，但保留已有结果并生成部分报告。

用户追加预算后仍使用原任务标识恢复。历史实际消耗、预留消耗和不确定消耗继续累计，不能重新计算为零。

### 8.7 恢复后的报告一致性

恢复始终更新原任务对应的报告：

- 不创建重复任务；
- 不覆盖其他任务报告；
- 已完成评论按稳定标识复用和去重；
- 报告反映最新完成范围、累计预算和不确定调用；
- 报告生成失败不撤销已经完成的审查结果。

### 8.8 恢复职责边界

- CLI 接口模块只接收任务 ID、预算追加等用户指令；
- 任务管理模块校验任务是否允许恢复；
- 审查编排模块决定从哪个工作单元继续；
- 预算模块恢复累计账本并判断能否创建新调用；
- Trace 模块记录中断、恢复和重试事实；
- 持久化适配器提供原子状态读写；
- 报告模块根据当前结构化状态重新生成报告。

### 8.9 保留与清理

- 未结束任务的 checkpoint 自最近一次有效写入起七天内允许恢复；超过有效期后任务保留为不可恢复状态，不静默创建新任务；
- 任务进入终态后，其 checkpoint 和完整 Trace 至少继续保留七天，二者使用同一个明确的 `expires_at` 基准；
- 清理操作用例按任务关联关系删除 checkpoint、模型与工具调用、预算流水、Trace 和中间状态，但不删除用户仍需保留的 Markdown 报告，并保留仅含任务 ID、最终状态、过期时间和报告路径的脱敏墓碑记录；
- 清理在单一事务中执行并且幂等。失败时保留原数据并记录脱敏错误，不能留下“部分 Trace 已删除但仍显示为完整”的状态；
- `status` 与 `trace show` 必须明确区分可用、已过期、清理失败和不存在。

## 9. 四类扩展接入机制

系统提供四类独立扩展，但不提供能够访问所有系统能力的通用插件接口。Input Provider、Model Provider 和 Output Adapter 是受信任的应用代码，通过端口接入；Review Tool 是不含可执行代码的声明式规则包。

```text
受信任适配器：实现端口 → 声明身份、版本和能力 → 组合入口装配
Review Tool：提供规则包 → 注册器只读取并校验数据 → 受限运行时执行
两类结果均转换为内部模型后交给应用层
```

增加 Input Provider、Model Provider 或 Output Adapter 时，实现对应端口、提供扩展声明、完成注册和配置，并通过该端口的合约测试。增加 Review Tool 时只提供符合受限规则格式的声明与规则数据。两种方式均不修改审查工作流或其他业务模块。

### 9.1 输入源扩展

Input Provider 负责识别和校验自己支持的输入，获取 diff、元数据及允许读取的上下文，固定输入身份和版本，证明输入完整性，并转换为统一变更集。

新增输入源时只增加新的 Input Provider。审查规划和执行模块仍然只接收标准化变更集。

输入适配器不能决定预算、审查规则、输出方式或任务状态。无法证明输入完整时，必须返回标准化失败结果。

### 9.2 模型供应商扩展

Model Provider 负责把统一模型请求转换为供应商请求，声明结构化输出、Token 计算和 usage 等能力，调用模型并返回统一响应，以及把供应商异常转换为标准调用结果。

Model Provider 必须由统一模型网关包装。预算预留、安全检查、Trace、调用状态和重试策略不属于 Provider，新增模型供应商不能绕过这些规则。

任务创建时固定 Provider、Provider 版本和模型，恢复期间不自动切换。

### 9.3 审查工具扩展

Review Tool 扩展负责声明名称、版本、支持语言、规则集合和资源上限。扩展包是数据而不是可执行插件；系统自有的受限工具运行时接收已经授权并完成安全处理的文本，执行只读确定性分析，并返回统一工具结果和证据。

工具通过独立 Tool Registry 加载。注册器只读取并校验固定格式的 TOML/JSON 声明与规则数据，不导入扩展模块，不解析任意对象路径，也不执行安装脚本、回调、模板表达式或仓库配置。规则语言只提供有限的字面量、文本和 Token 模式操作，不接受通用正则表达式或任意表达式求值；运行时实施输入大小、输出大小和步骤数上限，使执行时间由输入与步骤上限共同约束。

受限运行时不向规则提供数据库、凭证、网络、环境变量、通用文件系统、进程创建、动态导入或任务状态修改能力。新增工具只增加声明与规则数据，不修改审查编排代码；规则越权、超限或无效时被拒绝，且只影响对应验证范围，不能使其他工具或模型调用失去 Trace 和 checkpoint。

### 9.4 输出方式扩展

MVP 的 Output Adapter 负责把统一报告模型转换为无外部副作用的本地产物，例如 Markdown；未来可按相同端口增加 JSON。

报告内容、完成状态、置信度和预算信息由报告模块决定。Output Adapter 只负责格式化和交付，不能重新解释业务结果。

远程回评、消息发送或其他具有外部副作用的交付不属于当前 Output Adapter。未来引入时必须重新设计发布授权、目标固定、幂等键、部分成功和不确定结果，并由独立的发布用例协调；不能仅注册一个 Output Adapter 即获得外部写权限。

### 9.5 扩展声明

每个扩展至少声明：

- 稳定名称和版本；
- 扩展类型；
- 支持的输入、语言或模型能力；
- 输入输出契约版本；
- 所需系统能力；
- 超时和规模限制；
- 失败对任务完整性的影响。

Review Tool 还必须声明规则格式版本、确定性能力、最大步骤数和资源上限。包含可执行代码、动态导入目标、外部 URL、文件路径或未知规则操作的声明必须在加载阶段拒绝。

任务快照保存实际选择的扩展及其版本，确保恢复时不会静默使用另一版本。

### 9.6 注册与装配

系统分别维护 Input Provider Registry、Model Provider Registry、Review Tool Registry 和 Output Adapter Registry。

注册器只负责发现、校验和选择，不执行工作流。唯一的应用组合入口负责把选中的适配器装配到应用层。

Review Tool Registry 只发现规则包元数据和数据资源，不通过 Python entry point 导入工具实现。其他三类适配器属于受信任的应用基础设施，其安装或升级视为应用代码变更，并经过正常依赖锁定、审查和发布流程。

适配器之间不能直接调用。例如，GitHub Input Provider 不能直接调用模型，Model Provider 不能直接生成 Markdown。

### 9.7 扩展边界

并非所有新功能都需要插件化：

- 新增输入、模型或本地输出实现：通过现有端口扩展；
- 新增确定性审查工具：增加声明式规则包，由受限工具运行时执行；
- 新增业务规则：修改对应领域模块；
- 新增工作流阶段：更新应用编排和状态模型；
- 新增权限类型：先更新安全能力模型，再允许扩展使用。

该边界避免为“任何变化都不修改核心代码”进行过度抽象，同时保证四类常见能力可以快速接入。

## 10. 错误传播与降级原则

### 10.1 统一错误边界

第三方 SDK、网络、文件系统和数据库的原始异常必须在适配器边界转换为项目定义的错误类型。核心业务模块不依赖第三方异常，也不解析第三方错误文本。

业务模块返回结构化结果或领域错误。只有审查编排模块决定继续、暂停或结束任务；适配器不能自行修改任务状态或触发隐藏重试。

所有向用户、日志、Trace、checkpoint 和报告传递的错误信息必须先经过安全处理，不能包含凭证或未脱敏代码。

### 10.2 错误分类

| 类别 | 含义 | 工作流决定 |
| --- | --- | --- |
| 输入拒绝 | 输入不受支持、损坏、超限或不完整 | 结束任务，不调用模型 |
| 可修复配置错误 | 缺少凭证或配置，且修正不会改变任务固定条件 | 暂停任务，修正后允许显式恢复 |
| 固定能力不兼容 | 已选模型或扩展不具备硬预算、安全或结构化结果所需能力 | 结束任务，修改选择后创建新任务 |
| 临时外部失败 | 平台、模型或网络暂时不可用且结果明确失败 | 暂停任务，允许显式恢复 |
| 不确定外部结果 | 请求可能执行成功但本地无法确认 | 标记 `unknown` 并暂停，不自动重试 |
| 可降级失败 | 可选工具失败、部分内容不可分析或安全策略要求跳过 | 继续处理其他范围，最终标记部分完成 |
| 预算不足 | 新模型调用无法完成预算预留 | 停止新增模型调用，生成部分报告 |
| 预算异常 | 供应商报告的实际 usage 超过调用前预留值 | 如实登记实际值和超出量，冻结后续模型调用，生成披露异常的部分报告 |
| 持久化完整性错误 | 无法可靠保存状态、预算或 Trace | 立即停止，禁止继续外部调用 |
| 输出失败 | 结构化审查结果已保存，但报告交付失败 | 保留审查结果并将交付状态标记为失败，允许恢复后只重新生成报告 |

### 10.3 降级规则

系统仅在仍能如实说明审查范围时降级继续：

- 单个可选工具失败：继续审查，但相关发现不能获得依赖该工具的高置信度；
- 二进制或不支持语言：跳过对应内容并列入未审查范围；
- 敏感内容无法安全处理：跳过对应片段并降低覆盖状态；
- 必需审查单元发生可恢复失败：保留已完成结果并暂停任务；仅当恢复条件失效时结束任务，并在报告中列为未完成范围；
- 预算耗尽：停止新增模型调用并生成部分报告；
- 实际 usage 超过预留：记录预算异常并冻结后续模型调用，不把负余额或超出量隐藏为零；
- 模型结构化输出无效：记录该单元失败，不通过隐藏模型调用自动修复。

输入不完整、固定版本无法确认、安全边界失效或持久化状态不可信时不得降级为“正常审查”，必须停止。

### 10.4 重试规则

所有重试由应用层显式创建新的执行尝试，并记录独立 Trace、调用状态和预算流水。第三方库自动重试必须关闭。

确定性本地处理可以在恢复时重做当前未完成单元；外部请求只有在明确失败且策略允许，或用户对 `unknown` 状态执行显式恢复后才能重新尝试。

### 10.5 用户可见结果

CLI 和报告使用同一组已持久化状态。审查结果至少区分完成、无变更、部分完成、失败和结果不确定；执行控制状态至少区分运行、暂停和终止；报告交付状态至少区分待生成、成功和失败。不同维度不得互相覆盖，例如报告写入失败应显示“审查完成、报告交付失败”，不能显示为“审查失败”。

错误展示包含发生阶段、影响范围、是否可以恢复和用户可采取的下一步，但不暴露底层凭证、未脱敏输入或无关调用栈。

## 11. 模块级测试与验收边界

### 11.1 领域模块测试

任务状态、预算、安全决策、审查计划、发现验证、置信度和报告模型通过纯单元测试验证，不依赖网络、真实模型或 SQLite。

重点验证状态只能合法前进、系统不会主动发起预留值超过剩余预算的调用、供应商实际 usage 超过预留时会冻结后续调用并披露异常、未验证发现不能进入报告，以及不完整覆盖不能显示为完整审查。

### 11.2 端口合约测试

每类端口维护一套所有实现必须通过的共享合约测试：

- Input Provider：输入身份、固定版本、完整性和统一变更集；
- Model Provider：能力声明、统一响应、usage 和错误映射；
- Review Tool：声明式规则格式、越权声明拒绝、资源限制、确定性结果和失败影响；
- Output Adapter：内容一致性、目标隔离和交付状态；
- Persistence Adapter：事务、原子状态变更和恢复一致性。

新增适配器时复用对应合约测试，不为每个实现重新定义行为标准。

### 11.3 应用工作流测试

使用 fake 端口验证完整工作流，不连接真实平台或模型。覆盖正常完成、无变更、输入失败、工具降级、模型失败、预算耗尽、部分完成和恢复等路径。

工作流测试需要证明已完成工作单元不会重复执行，单次中断最多重做一个未完成单元，不确定模型调用不会自动重试。

### 11.4 适配器集成测试

SQLite、文件写入、keyring、diff 解析、平台 SDK、HTTP 和模型适配器在外围分别验证。

默认自动测试使用 fake 或固定响应，不依赖真实凭证。真实 GitHub/GitLab 私有仓库和真实模型调用作为独立手动验收。

### 11.5 安全与故障注入测试

所有出站和落盘路径必须覆盖敏感内容样例，包括 diff、上下文、工具结果、模型响应、错误消息、第三方 SDK 日志、应用日志、Trace 和报告。测试必须证明模型或工具回显的敏感值在进入领域模型、日志、Trace、checkpoint 或报告之前已经被处理；安全扫描器不可用时不得继续出站或落盘。

在预算预留、外部请求开始、入站安全处理、响应保存、usage 结算、工作单元完成和报告交付等边界注入中断，验证状态、预算、Trace 和恢复结果一致。另用供应商返回的实际 usage 超过预留值的样例，验证系统冻结后续调用并披露超出量。

时间推进测试必须证明未结束任务的恢复有效期、任务终态后的七天保留期，以及 Trace/checkpoint 的幂等清理行为。

### 11.6 扩展性验收

分别增加一个测试用 Input Provider、Model Provider、声明式 Review Tool 规则包和 Output Adapter，验证只通过受支持的声明与注册机制即可接入，审查编排和其他核心模块无需修改。

若扩展能够绕过安全、预算、Trace、任务状态或能力限制，则扩展性验收失败。Review Tool 验收还必须包含带 Python 回调、动态导入、外部 URL、文件路径和未知规则操作的恶意声明，并证明它们在加载阶段被拒绝且没有执行任何扩展代码。

### 11.7 架构约束测试

通过静态检查或依赖测试验证领域层没有导入 CLI、SQLite、LangChain、GitHub/GitLab SDK、HTTPX、keyring、Jinja2 或具体适配器。

同时检查适配器之间不存在直接依赖，第三方对象没有越过适配器边界，模块之间没有共享可变全局状态；并检查 Review Tool Registry 不存在动态导入、对象路径解析或执行扩展回调的代码路径。

### 11.8 端到端验收

使用《验收清单.md》定义的固定样例验证三种输入、三种语言、Markdown 输出、缺陷和干净变更、恢复、预算、安全及 Trace。

端到端验收验证用户可观察结果；单元、合约和故障注入测试负责证明内部架构约束与失败语义。

## 12. 需求与架构映射

| 需求能力 | 主要负责模块 | 关键保证 |
| --- | --- | --- |
| 三种输入与固定版本 | 输入模块、Input Provider | 统一变更集、完整性校验、版本固定 |
| 审查评论与范围 | 审查规划、审查执行、发现处理 | 工作单元、证据校验、范围汇总 |
| Markdown 报告 | 报告模块、Output Adapter | 结构化报告、任务隔离、安全交付 |
| Checkpoint 与恢复 | 任务管理、审查编排、持久化适配器 | 已完成单元复用、显式恢复、结果一致性 |
| 评论 Trace | Trace 模块 | 任务、调用、工具、证据和评论关联 |
| 工具扩展 | Tool Registry、受限工具运行时 | 声明式规则接入、不可执行扩展代码、资源限制、失败隔离 |
| Token 预算 | 预算模块、模型网关 | 调用前预留、调用后结算、硬约束 |
| 置信度 | 发现处理模块 | 证据与确定性验证共同决定等级 |
| Secret 保护 | 安全模块、安全扫描适配器 | 出站和落盘统一处理 |
| 禁止执行仓库代码 | 安全模块、工具能力边界 | 仓库内容仅作为不可信数据 |

其中 Trace/checkpoint 的七天保留、模型与工具响应的入站安全门禁、安全日志、预算异常冻结、跨模块原子提交和报告交付状态均属于上述能力的强制验收项，不能作为实现阶段的可选细节省略。

当前 27 条 MVP/P0 需求均能映射到明确模块及工作流阶段，不依赖未规划的 Web、队列或分布式基础设施。

## 13. 架构演进边界

MVP 只为新增输入源、模型供应商、审查工具和输出方式建立扩展点。

以下变化超出当前架构承诺，需要重新评估系统边界：

- Web 服务或常驻后台进程；
- 多用户、组织和细粒度权限；
- 并发任务和分布式执行；
- PostgreSQL、消息队列或远程对象存储；
- 自动修复、提交或合并代码；
- 从受审仓库动态加载工具或配置；
- 允许执行仓库测试、构建或 typecheck；
- 远程回评的发布幂等性和权限模型。

如果未来服务化，领域模块、端口和结构化状态可以继续复用，但任务调度、持久化、凭证、并发控制和交付幂等需要作为新的架构设计处理。

## 14. 最终架构结论

Code Review Agent 采用 **Python 3.12 本地单进程 CLI + 模块化单体 + 端口／适配器 + 自有显式工作流**。

任务管理模块拥有状态，审查编排模块拥有流程，各领域模块拥有各自业务规则；外部平台、模型、存储和输出只通过受控端口接入，审查工具以声明式规则包进入系统自有的受限运行时。预算、安全、Trace 和 checkpoint 是不可绕过的系统约束，不作为可选插件实现。

该架构在不引入服务化和通用插件平台复杂度的前提下，满足当前 MVP 的输入、审查、恢复、追溯、扩展、预算、置信度和安全需求，并为四类已确认扩展提供稳定接入边界。

## 15. 模块详细设计顺序

模块详细设计按依赖方向和实现前置条件依次开展：先确定任务状态及不可绕过的横切约束，再设计核心审查流水线，最后补齐编排、扩展、基础设施和用户入口。具体顺序如下：

| 顺序 | 模块 | 排序依据 |
| --- | --- | --- |
| 1 | 任务管理模块 | 先确定任务标识、生命周期、状态变更、checkpoint、恢复和清理边界，为其他模块提供稳定的任务上下文。 |
| 2 | 安全模块 | 尽早固定所有出站、入站和落盘路径必须遵守的安全门禁，避免后续模块形成不可接受的数据路径。 |
| 3 | 预算模块 | 确定模型调用前预留、调用后结算、预算异常冻结和追加预算规则，为审查执行建立硬约束。 |
| 4 | Trace 模块 | 确定任务、工作单元、模型调用、工具调用、证据和评论之间的追溯契约。 |
| 5 | 输入模块 | 在任务、安全和 Trace 契约明确后，设计三类输入的校验、版本固定和统一变更集。 |
| 6 | 审查规划模块 | 基于统一变更集定义可保存、执行和恢复的审查工作单元及覆盖范围。 |
| 7 | 审查执行模块 | 在安全、预算、Trace 和工作单元契约齐备后，设计模型与确定性工具的受控调用。 |
| 8 | 发现处理模块 | 基于候选发现设计结构校验、位置验证、证据核对、去重、置信度和合并规则。 |
| 9 | 报告模块 | 在最终发现和任务结果稳定后，设计格式无关的报告模型及本地交付契约。 |
| 10 | 审查编排模块 | 汇总前述模块的公开契约，设计主流程、中断恢复、错误传播、降级和原子提交边界。 |
| 11 | 扩展与适配器模块 | 在核心端口稳定后，定义四类扩展的声明、注册、能力约束和合约测试。 |
| 12 | 基础设施模块 | 根据已确定的端口设计 SQLite、keyring、文件系统、平台 SDK、HTTP 和模型适配器实现。 |
| 13 | CLI 接口模块 | 最后基于稳定的应用用例设计命令、参数、进度、结果、错误展示和退出码。 |

每个模块独立完成详细设计与评审。当前模块确认后再进入下一个模块；后续设计若需要修改已确认的上游契约，必须明确记录变更原因、影响模块和兼容处理。
