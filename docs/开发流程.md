# Code Review Agent 开发流程

本文记录字节跳动 Code Review Agent Take-Home 的开发流程，作为后续调研、设计、实现、验证和交付的执行依据。具体技术栈及模块设计在完成需求验收清单后确定。

## 1. 题目与目标

开发一个 Code Review Agent：输入 GitLab MR / GitHub PR 链接，或者 git diff；输出远程 review 评论，或者 Markdown 报告。

必须覆盖以下要求：

- **可恢复**：通过 checkpoint 保存进度，异常后不从头运行。
- **可观测**：每条评论能够追溯到相关工具调用、diff、prompt 和模型回复。
- **可扩展**：新增工具通过实现和声明式注册接入，无需修改主流程。
- **预算控制**：支持设置总预算，并在调用过程中执行预算约束。
- **置信度分级**：区分高置信度建议与仅供参考的建议，提供分级依据。
- **安全**：避免 secret 外传，不在用户仓库执行任意代码。

题目还要求使用 AI 完成开发，并自行判断应向 HR 提交哪些材料，证明 AI 使用能力。

## 2. 总体原则

先把要求转化为可验证的标准，再围绕关键风险做最小实验，尽早完成端到端闭环。实现过程中持续记录设计取舍、验证结果和 AI 协作证据。

### 2.1 AI 使用原则

1. 每次任务先明确目标、输入、输出、约束和验收方式。
2. 一次委派一个边界清晰、可独立验收的工作单元。例如，实现一个模块并补充测试可以属于同一个任务。
3. 持久化重要规则、设计决策和当前进度，并避免重复文档产生冲突。
4. AI 完成任务时必须提供可复现的验证证据；AI 自检不能保证正确性。
5. 高风险结果需要独立验证，重点包括敏感信息外传、仓库代码执行、预算失控，以及远程评论重复发布。
6. AI 生成的方案和代码，必须由开发者理解后接受，能够解释其取舍、失败场景和实现边界。
7. 持续记录有代表性的 AI 协作过程，包括纠错和拒绝不合适方案的依据。

### 2.2 最小工程规范

快速开发阶段不引入复杂规范，但需要明确：

- 格式化、静态检查和测试命令。
- 模块边界与依赖方向。
- 错误处理、日志和配置的基本约定。
- secret、diff、prompt、模型回复和 trace 的脱敏与存储规则。
- 每个任务的完成标准。

可观测性设计必须同时考虑敏感信息保护，不能无条件记录所有原始数据。

## 3. 执行流程

### 阶段 1：保存原题，拆解需求

保留原始题目，将每项要求转化为具体行为和可演示的验收场景。区分题目明确要求、实现假设和可选增强。

**产出**：原题记录、需求验收矩阵、待确认问题。

### 阶段 2：定义 MVP、非目标和交付物

建议首版范围：输入本地 git diff 和可选的只读代码上下文，输出 Markdown 报告，完整演示六项要求。

GitHub/GitLab 接入和远程回评作为后续增强，是否实现根据时间和核心功能完成度决定。平台接入涉及认证、分页、行号映射及发布幂等性，需要单独评估。

MVP 的具体范围应在需求阶段确定，并记录暂不实现的内容。

**产出**：MVP 范围、非目标清单、成功标准、交付物清单。

### 阶段 3：制定 AI 协作与工程规范

基于本文原则，明确任务模板、验证要求、文档更新规则和最低工程检查项。

**产出**：可执行的协作约定、任务完成标准、基础检查命令。

### 阶段 4：限时调研与技术选型

围绕直接影响实现的问题调研，避免把学习完整技术栈当作开发前提：

- 如何获取 diff 和必要的代码上下文？
- review 分为哪些步骤，哪些结果需要持久化？
- 如何计算预算，在哪里阻止超支？
- 哪些数据允许发送给模型，哪些工具允许执行？
- 评论如何定位代码，并追溯到生成过程？

调研类似项目时，记录其解决的问题、可借鉴部分、不适合本题的原因。为调研设置时间边界，并将结论用于技术选型。

**产出**：简短调研记录、候选技术栈对比、选择理由。

### 阶段 5：验证关键风险

正式铺开开发前，优先做最小实验：

- 中断后的状态恢复与已完成结果复用。
- 敏感数据出站过滤。
- 模型调用前的预算检查与拦截。

实验结果用于修正架构。需要尽早明确：

- 金额预算与 token 预算不同，金额控制需要模型价格配置和计费口径。
- 置信度不能只依赖模型自报分数，应结合代码证据、工具验证和明确规则。
- 声明式注册不等于自动获得执行权限，工具能力与权限应分别约束。
- 对中断时仍在进行的外部调用，需要明确恢复语义，不能假设一定没有产生调用费用。

**产出**：风险实验结果、关键边界与限制、更新后的设计决策。

### 阶段 6：编写精简设计文档，拆分任务

初期建议维护以下文档，按需创建：

| 文档 | 内容 |
| --- | --- |
| README.md | 目标、运行方式、范围和验收入口 |
| DESIGN.md | 主流程、状态模型、数据结构、预算及安全边界 |
| DECISIONS.md | 关键取舍、候选方案和选择理由 |
| TASKS.md | 开发任务、验收方式和进度 |

模块详细设计只针对难点，例如 checkpoint 状态机、预算预留与结算、工具权限。普通模块优先通过接口和测试表达。

每个开发任务应包含：目标、依赖、变更范围、验收方式和完成证据。

**产出**：精简设计文档、可独立验收的任务列表。

### 阶段 7：完成端到端流程，逐项补齐能力

先打通输入 diff、执行 review、生成报告的最小流程，再逐项实现六项要求。每完成一个任务，同步进行必要验证并更新进度。

**产出**：可运行的 MVP、对应验证结果、持续更新的任务记录。

### 阶段 8：持续验证并记录 AI 协作证据

验证与开发同步进行，不能全部留到结束。保留少量代表性协作记录：

> 任务目标 → 提供给 AI 的上下文 → AI 的方案 → 人工判断与修正 → 验证结果。

重点记录方案取舍、发现并修正 AI 错误的过程、范围控制及验证策略。无需提交全部聊天记录，提交材料前应检查敏感信息。

**产出**：任务级验证证据、精选 AI 协作记录。

### 阶段 9：整体测试与质量评估

使用固定样例验证功能、故障恢复、安全边界和评论质量，至少覆盖：

- 正常生成报告及评论代码定位。
- 超时、限流和异常模型输出。
- 中断重启后是否重复调用或重复产出。
- 预算耗尽时能否按设计结束或降级。
- diff 含假 secret 或提示注入内容。
- 恶意仓库内容无法触发未授权代码执行。
- 对预先标注缺陷的样例，统计发现情况和误报，检查评论是否有可核对的证据。

**产出**：测试与评估报告、已知限制、可复现的演示样例。

### 阶段 10：整理交付材料

面向 HR 和技术面试官整理：

- 可运行的源代码、依赖说明和配置示例。
- README 与快速运行步骤。
- 系统设计、关键取舍及已知限制。
- 六项要求的验收结果及评论质量评估。
- 演示报告、必要的录屏或截图。
- 精选 AI 协作案例，展示任务拆解、上下文组织、人工判断和纠错验证能力。

交付前按照 README 在干净环境中验证运行步骤，并检查材料中没有真实 secret。

**产出**：可直接审阅和复现的提交包。

## 4. 初始需求验收矩阵

以下为初始建议，后续在需求设计阶段细化为可执行用例。

| 要求 | 验收场景 |
| --- | --- |
| 可恢复 | 在某一步故意中断，重启后复用已完成结果，并按既定语义处理进行中的调用 |
| 可观测 | 从评论的 trace ID 找到相关 diff、工具记录、prompt 和模型回复；敏感数据按策略处理 |
| 可扩展 | 新增工具实现和声明后能够加载，主流程代码无需修改 |
| 预算控制 | 每次模型调用前检查并预留预算；不足时停止或降级，报告消耗及计费口径 |
| 置信度分级 | 根据代码证据、工具验证等规则分级，并展示分级理由 |
| 安全 | 用假 secret 验证出站脱敏；恶意仓库内容不能诱导命令执行或绕过工具权限 |

## 5. 当前下一步

编写一页明确的“MVP 范围 + 需求验收矩阵”，确定实现边界和成功标准，再推进技术调研与设计。
