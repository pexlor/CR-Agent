## 1. 可恢复性（Checkpoint / Resume）

### 测试流程
1. 构造一个 3 个 work unit 的审查任务，在第 3 个单元执行时人为抛出异常，模拟中断。
2. 用新的 `LocalDiffReviewService` 实例调用 `resume()`，验证只重跑第 3 个单元，第 1、2 单元的评论直接复用。
3. 验证 checkpoint 与 `input_digest` + `rules_config_digest` 绑定：改变输入或规则配置后再 resume，应拒绝。
4. 验证 checkpoint 损坏（篡改 payload）、过期（`expires_at` 已过）两种情况下会拒绝续跑，而不是静默重来。
5. 验证 `UNKNOWN`（无法确认模型是否已被调用）状态的执行结果，resume 时必须显式传 `confirm_unknown_retry=True` 才能重试，防止误重复计费。
6. 验证 checkpoint 写入失败时，任务状态显式标记为 `partial`，不会伪装成功。

### 检查项
| 检查项 | 预期行为 |
| --- | --- |
| 中断后 resume | 只重跑未完成单元，已完成单元评论原样复用 |
| checkpoint 绑定 | 输入/规则/价格配置变化 → `checkpoint_binding_mismatch` |
| checkpoint 损坏 | → `checkpoint_corrupt` |
| checkpoint 过期 | → `checkpoint_expired` |
| UNKNOWN 状态重试 | 未确认 → `unknown_retry_confirmation_required`；确认后可重试 |
| checkpoint 写失败 | 任务状态为 `partial`，不伪装成功 |

## 2. 可观测性（Trace 关联）

### 测试流程
1. 写入一条 trace 事件并关联一个工件（`PersistedTraceArtifactView`，代表 prompt/diff/response），验证事件序号连续、可原子读回。
2. 验证相同 `idempotency_key` 重放返回同一结果，冲突 payload 会被拒绝（防止 trace 被覆盖篡改）。
3. 验证 trace summary 字段的白名单机制：嵌套对象、`reasoning`、`chain_of_thought`、`raw`、`response` 等字段一律拒绝写入，防止内部推理过程或原始敏感内容混入可查询摘要。
4. 构造一条评论（finding）的 trace 链：input 事件 → 该 work unit 的 model 调用事件 → finding 校验事件，用 `link_finding_trace` 关联后，通过评论的 `trace_id` 能精确查出这条链，且不包含其他 work unit 的事件。
5. 验证工件摘要（digest）校验失败时整条写入原子回滚，不留脏数据。

### 检查项
| 检查项 | 预期行为 |
| --- | --- |
| 事件+工件原子写入 | 序号连续，可读回，工件内容与摘要一致 |
| 幂等重放 | 相同 key 相同 payload → 返回同一事件；冲突 payload → 拒绝 |
| 敏感字段过滤 | `reasoning`/`raw`/`response` 等字段禁止进入 summary |
| 评论→Trace 关联 | 按评论 `trace_id` 能查到其对应 work unit 的 model 请求/回复/工具调用 |
| 摘要校验失败回滚 | 事件与工件均不落库 |

## 4. Token 预算

### 测试流程
1. 创建预算账户（如 100 token 额度），预留 70 token，验证再预留 40 token 时因超额被拒绝（`insufficient_budget`），但账户状态仍为 `OPEN`（普通不足不冻结账户）。
2. 模拟实际用量超过预留量的场景（预留 20，实际用了 30），验证账户被冻结为 `FROZEN_OVERAGE`，且冻结后新的预留请求立即被拒绝（`budget_frozen`）。
3. 杀掉进程重启 `BudgetService`（从 SQLite 恢复），验证冻结状态、已知消耗、不确定消耗均正确恢复，且恢复后依然拒绝新预留。
4. 校验配置层：`max_cost_per_review_cny`、`price_per_million_tokens_cny` 的精度、缺失、上限约束（本次测试中发现并修复了 4 个配置层 bug，详见下方"发现问题"）。

### 检查项
| 检查项 | 预期行为 |
| --- | --- |
| 预算不足 | 拒绝当次预留（`insufficient_budget`），账户保持 `OPEN` |
| 实际超支 | 账户冻结为 `FROZEN_OVERAGE`，拒绝后续预留（`budget_frozen`） |
| 重启恢复 | 冻结/消耗状态从 SQLite 正确恢复，不会"重置放行" |
| 配置显式化 | 预算相关字段缺失应报错，不能静默用默认值 |
| 配置精度 | 超精度价格（如 15 位小数）应被拒绝 |
| 配置上限 | `max_tokens` 不能超过预算引擎硬编码上限（1,000,000） |

### 发现问题与修复
测试过程中发现 `tests/unit/test_config.py` 中 6 个测试用例失败，定位为 `src/code_review_agent/config.py`（本分支未完成的进行中改动）存在真实 bug，已修复：

| 问题 | 原因 | 修复 |
| --- | --- | --- |
| 超精度价格未被拒绝 | 校验逻辑接受 `float` 输入，但 TOML 裸数字字面量在被 `tomllib` 解析为 Python float 时已丢失精度，校验为时已晚 | `_positive_decimal` 改为只接受 `Decimal`/`str`/`int`，拒绝 `float`；新增小数位数上限校验（6 位） |
| 预算字段缺失未报错 | `from_file` 对缺失字段使用默认值兜底 | 改为强制要求 `[budget]` 显式声明 `max_cost_per_review_cny`/`price_per_million_tokens_cny`，缺失报 `config_missing_cost_budget`/`config_missing_model_price` |
| `max_tokens` 绝对上限未拦截 | 只判断 `>0`，未与预算引擎的硬上限对齐 | 改为 `1 <= max_budget_tokens <= 1_000_000`，与 `domain/budget/models.py` 的 `MAX_AUTHORIZATION` 常量一致 |
| `format_cost_cny_for_tokens` 方法缺失 | 测试引用的方法名与实现方法名（`cost_cny_for_tokens`）不一致，是改名未同步 | 新增该方法，返回未做小数截断的精确成本字符串 |

修复后回归：
```

```

**结论：通过（含 4 处配置层缺陷修复）。**

4. 验证 Markdown 报告模板正确渲染 `Confidence` 和 `Confidence basis` 字段。

### 检查项
| 检查项 | 预期行为 |

| 判定依据留痕 | 每条 finding 必须有非空 `confidence_basis` |
