## 1. 可恢复性 — 真实中断验证

**测试流程：**
1. 构造一个真实 3 文件 diff（含 SQL 注入、`os.system` 命令注入、除零风险等真实代码问题）
2. 执行 `code-review-agent review`，模型请求刚发出（trace 记录到 `model.call_started`）后用 `kill -9` 真实杀掉进程
3. 重启后执行 `code-review-agent resume <task_id>`

**结果：**
- 第一次 resume 被拒绝：`unknown_retry_confirmation_required`（因为无法确认被杀掉的那次调用是否已经成功调用了模型，防止重复计费）
- 加 `--confirm-unknown-retry` 后成功续跑：`result=complete_with_findings`
- trace 显示：第一个 work unit 有两次 `model.call_started`（kill 前一次、resume 后重试一次），另外两个 work unit 各只跑了一次
- 最终 3 个 work unit 全部 `reviewed`，产出 8 条真实发现

**结论：真实中断场景下，只重跑受影响的部分，不会从头开始，也不会静默重复扣费。通过。**

---

## 2. 可观测性 — 真实 trace 验证

**测试流程：**
直接用 `sqlite3` 读取本地状态库 `state/reviews.sqlite3` 中持久化的原始工件（不通过报告或 CLI 包装），核对每条评论关联的 trace 内容。

**结果：**
- 每条 finding 的 `Trace: <id>` 可用 `trace show` 反查到对应 work unit 的完整链路：`input.normalized` → `model.call_started` → 工具执行 → `model.call_succeeded`/`response_accepted` → `finding.validated`
- 直接从 sqlite 读出发给模型的原始请求体（`review_trace_artifacts` 表），确认 trace 里保存的 diff 内容是脱敏后版本，不含原始密钥

**结论：评论到工具/diff/prompt/模型回复的关联链路真实可查。通过。**

## 3. 可扩展性 — 真实新增工具跑通生产 runtime

**测试流程：**
没有跑现成的契约测试文件，而是现场手写一个全新工具「调试用 print 语句检测器」（`debug-print-detector`），仅用 TOML 声明（现算 `resource_digest`），从生产环境实际调用路径 `ToolRegistry.from_builtin()` 追加注册，再用生产用的 `RestrictedToolRuntime` 去执行，对真实代码行 `print("debug value:", x)` 做检测。

**结果：**
```
newly added tool ids: {'debug-print-detector'}
execution state: succeeded
evidence rule ids: ['python-print-debug']
```
全程未修改任何 `.py` 源码文件。

**结论：新工具通过纯声明式注册即可在生产 runtime 上生效。通过。**

## 4. Token 预算 — 真实模型触发真实预算拒绝

**测试流程：**
把 `max_cost_per_review_cny` 调到 `0.00001` 元（预算引擎折算约 10 token 额度），用真实两文件 diff 跑 `review`。

**结果：**
```
task result=partial
scope_...: unreviewed (budget_reservation_rejected)
scope_...: unreviewed (budget_reservation_rejected)
```
trace 中**没有出现任何 `model.call_started` 事件**——说明预算门禁在请求真正发给千帆之前就拦截了，没有产生调用也没有产生费用。

**结论：预算限制在真实调用发出前生效，不是发出后再补救。通过。**

---

## 5. 置信度分级 — 真实模型输出的真实分级结果

**测试流程：**
统计本次全部真实 review（21 条真实发现）中每条 finding 的 `Confidence` 和 `Confidence basis`。

**结果：**
全部 21 条发现均为 `Confidence: advisory`，`confidence_basis` 均为 `"direct changed-code evidence plus language semantics"`。原因：本次配置里只有内置的危险模式检测工具（无真正的 typecheck/lint 工具接入），"工具验证成功"分支从未命中，只能走"语言语义支持"分支得到 `advisory`，与代码里 `direct and (tool_verified or semantic_verified)` 的判定条件一致。

**结论：真实模型输出下分级机制按预期工作，且如实反映了"当前工具链尚不能把任何发现判定为 HIGH"这一真实限制，没有被伪装成虚假的高置信度。通过。**

## 6. 安全 — 真实密钥的真实脱敏验证

**测试流程：**
构造含真实格式的 Stripe 密钥（形如 `sk_live_` 开头的伪造测试串，从未激活或真实存在）和 MySQL 连接串（含虚构密码）的 diff，跑真实 review。之后**直接从 SQLite 读出发给千帆的原始 HTTP 请求体**（不是看报告，是看最底层持久化数据）。

**结果：**
实际发给模型的请求体中：
```json
"STRIPE_SECRET_KEY = \"<REDACTED:CREDENTIAL:01>\""
"DATABASE_URL = \"<REDACTED:CONNECTION_STRING:02>"
```
对报告、trace、sqlite 全库 `grep` 原始密钥字符串和密码字符串，均为零匹配。模型基于脱敏后的上下文依然准确识别出"硬编码敏感凭据"问题，报告质量未受影响。

**结论：真实密钥确认从未发送给外部模型。通过。**
