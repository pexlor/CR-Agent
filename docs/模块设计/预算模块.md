# Code Review Agent 预算模块详细设计

## 1. 文档状态

- 日期：2026-09-10
- 状态：设计完成，待复审
- 适用范围：本地 CLI、单进程、单机 SQLite、单任务单执行者
- 用户预算单位：`CNY`
- 领域账本单位：`token`
- 默认配置示例：10 CNY/次、20 CNY/百万 token，即 500,000 token
- 单任务累计授权上限：1,000,000 token

本文定义预算模块的领域对象、精确计算口径、模型调用预算状态、公开契约、事务边界、恢复和清理语义。SQLite 物理表及 migration SQL 由基础设施模块设计，但不得改变本文不变量。

## 2. 设计结论

预算模块采用“只追加账本 + 当前账户投影 + 调用级预留”方案：

1. `BudgetAccount` 是单个任务唯一的预算账户；
2. `BudgetLedgerEntry` 记录不可变的授权与消耗事实；
3. 每次模型调用必须先绑定一个 `BudgetReservation`；
4. `BudgetProjection` 从已提交账本计算当前状态，不作为第二事实源；
5. 重试必须使用新的调用 ID、新预留和新流水；
6. 可信实际用量超过预留时，账户进入 `frozen_overage`，任务暂停并形成 `partial` 结果；
7. 用户追加足额预算、显式恢复并重新验证 Provider 硬预算能力后，同一任务可解除冻结并继续；
8. 预算模块只产生变更意图，不自行提交跨模块事务。

不采用可变的单行“已用 token”计数器，因为它无法准确表达活动预留、未知调用、重试、超额和追加授权。也不采用完整事件溯源；预算账本只负责预算事实，不重建任务状态。

## 3. 目标与非目标

### 3.1 目标

- 外部模型请求发出前已有完整、可核对且已提交的预算预留；
- 新调用的最大承诺消耗不得超过当前可用授权，不设置容差；
- 已知实际、不确定消耗、活动预留、超额和余额采用互斥口径；
- 中断、失败、重试和恢复不会漏记或重复计算 token；
- 真实超额不被截断或伪装为普通预算耗尽；
- 预算、调用状态、Trace、checkpoint、任务状态和结果快照原子一致；
- 幂等重放和并发写入不重复授权、预留或结算。

### 3.2 非目标

- 不支持 CNY 之外的货币、输入/输出/缓存 token 差异化单价、账单支付和账户余额管理；
- 不自动追加预算、切换 Provider 或模型；
- 不生成 prompt、调用模型、处理发现或推进任务状态；
- 不统计本地无计费确定性工具的 CPU、内存和时间；
- 不为缺少硬预算能力的 Provider 提供软预算模式；
- 不实现跨进程或跨主机的分布式预算账户。

## 4. 模块边界

预算模块拥有账户、初始与追加授权、调用级预留、已知实际消耗、不确定消耗、预留释放、超额、冻结及解除冻结事实，以及 Provider 硬预算能力证据引用。

任务生命周期、模型调用业务状态、请求和响应正文、Trace、checkpoint、结果快照及报告由其他模块拥有。预算模块仅保存其稳定标识、安全摘要或不透明引用。其他模块不得直接写预算表，只能提交预算模块产生的类型化 Intent。

## 5. 领域模型

### 5.1 `TokenAmount`

`TokenAmount` 是非负整数。用户输入的初始和追加授权必须是正整数，单任务累计授权不得超过 1,000,000。所有计算使用整数，不使用浮点数或货币单位。

### 5.2 `BudgetAccount`

每个任务恰好绑定一个预算账户：

| 字段 | 含义 |
| --- | --- |
| `account_id` | 预算账户标识 |
| `task_id` | 唯一所属任务 |
| `unit` | 固定为 `token` |
| `state` | `open / frozen_overage / closed` |
| `revision` | 乐观并发版本 |
| `last_sequence` | 最新账本序号 |
| `active_freeze_id` | 当前冻结记录，可空 |
| `provider_capability_baseline_ref` | 初始硬预算能力证据 |
| `last_revalidation_ref` | 最近恢复验证证据，可空 |
| `retention_group_id` | 与任务一致的保留组 |

- `open`：满足余额和能力条件时可创建新预留；
- `frozen_overage`：禁止新预留，但允许查询、追加授权、生成/交付部分报告和执行恢复校验；
- `closed`：不再接受授权或预留，清理前仍可查询。账户进入 `closed` 的唯一触发是任务终态后的清理事务：任务保留期到期、执行清理时，任务模块在删除预算详细记录前先把账户状态置为 `closed` 并追加 `account_closed` 账本与 Trace 事件，随后在同一清理事务中删除全部预算明细；任务正常运行或暂停期间账户保持 `open`/`frozen_overage`，不提前关闭。

普通预算不足不是账户状态，只是本次预留被拒绝。

### 5.3 `BudgetAuthorization`

授权分为 `initial` 和 `additional`，至少包含 `authorization_id`、`account_id`、`request_id`、`kind`、`amount`、`authorized_by`、`created_at`、`expected_task_version` 和 `request_fingerprint`。

约束：

```text
1 <= initial_authorization <= 1,000,000
1 <= additional_authorization
sum(all authorizations) <= 1,000,000
```

只有本机可信用户通过明确用例可以追加授权。追加不修改旧记录，不清零消耗，也不自动解除冻结。

### 5.4 `ProviderHardBudgetCapability`

Provider 在首次调用和预算异常恢复前必须证明：

1. 可对最终序列化请求精确计数，或给出不会低于真实输入 usage 的安全上界；
2. 能强制执行明确的最大输出 token；
3. 实际发送 body 与安全扫描、计数和摘要的 prepared request 完全一致；
4. usage 可归一化且字段映射可信；
5. Provider、模型、origin、适配器版本与任务固定条件一致；
6. SDK、transport 和 Provider 自动重试已关闭；
7. 能力验证本身不产生未预留的计费调用。

证据记录 Provider/模型/适配器身份、计数方法、输出限制、usage 映射、自动重试策略、固定配置摘要、验证时间和结果。异常后原证据不再足以授权后续调用，必须重新验证。若通过验证需要更换任务固定的 Provider、模型或 origin，则返回 `new_task_required`。

### 5.5 `BudgetReservation`

对最终待发送请求定义：

```text
I_bound = 输入 token 精确值或安全上界
O_max   = Provider 强制执行的最大输出 token
R       = I_bound + O_max
```

要求 `I_bound >= 0`、`O_max >= 0`、`R > 0`。计数后请求 body、模型、工具定义、输出 schema 或最大输出参数发生变化，原计算失效，必须重新准备和预留。

每个 `model_call_id` 最多一个预留。预留保存 `reservation_id`、任务/账户/工作单元/调用标识、`I_bound`、`O_max`、`R`、prepared request 摘要、能力证据和 `active / released / settled_known / settled_uncertain` 状态；当结算无法获得可信 actual usage 时，预留同时记录独立的 `usage_state = missing / untrusted`（`settled_known` 且 usage 可信时缺省为 `known`），该字段随预留持久化并纳入 `BudgetSummary` 输出，供报告和 Trace 展示 usage 可信度。

### 5.6 `NormalizedActualUsage`

可信实际用量统一为：

```text
actual_usage = input_usage + output_usage
```

两项均为非负整数。供应商子分类若已包含在父级字段中不得重复相加；无法证明字段互斥或可信时，不形成实际值，按不确定消耗处理。响应正文被安全模块拒绝不免除可信 usage 的结算。

### 5.7 `BudgetFreeze`

当 `actual_usage > reservation.amount` 时创建冻结记录，保存触发调用、预留、实际值、超额、冻结时赤字、旧能力证据和解除证据：

```text
overage_amount = actual_usage - reservation.amount
```

解除冻结不会删除或抵销历史超额。

## 6. 精确预算公式

`ledger_version` 定义为账户 `budget_ledger` 中最新已提交账本序号（即 `BudgetAccount.last_sequence`），用于快照一致性读取：`get_summary(task_id, ledger_version)` 返回该序号及之前全部已提交账本条目投影出的状态。它与乐观并发版本 `BudgetAccount.revision` 解耦：`revision` 只表示账户行的写入版本并用于并发冲突检测，`ledger_version` 表示账本事实的前缀序号，两者各自单调递增，不互相覆盖；账本追加成功后 `last_sequence` 单调前进，`revision` 也在同一事务中递增。Trace、报告和任务模块引用该版本号时，都指代同一个"最新已提交账本序号"口径。

在某一已提交账本版本定义：

```text
A        = 全部初始和追加授权之和
K        = 全部可信已知 actual usage 之和
U        = 全部不确定消耗之和：unknown/不可信 usage 按 `unknown_committed` 事件携带的 amount 计入（常规场景为预留 R，不可信报告值超过 R 的保守场景为报告值）
R_active = 全部活动预留之和
O        = 全部调用级 overage_amount 之和
C        = K + U + R_active
B_signed = A - C
D        = max(0, C - A)
```

可用于新预留的余额：

```text
B_spendable = max(0, B_signed), account.state = open
B_spendable = 0,                account.state = frozen_overage or closed
```

报告展示 `remaining_budget = max(0, A - C)`，同时必须展示 `authorization_deficit = D`，不能用截断为零隐藏赤字。

`O` 仅用于披露“实际相对预留的超出量”，不再加到 `C`；超额已经包含在 `K` 中，重复相加会重复计费。

新调用 `R_new` 只有在以下条件全部成立时获准：

```text
account.state = open
无待处理不可信超额能力重验（即不存在未完成的 pending_revalidation 阻塞，见 8 节）
A >= K + U + R_active + R_new
ProviderHardBudgetCapability = valid
prepared_request_digest = token_counted_request_digest
```

冻结后，解除冻结只要求授权覆盖已有承诺；此时下一请求通常尚未完成最终序列化，因此不把未知的下一次预留作为解除冻结条件。创建下一调用时再按最终请求计算并覆盖下一预留：

```text
A_after_add >= K + U + R_active
A_after_add >= K + U + R_active + R_next  # 创建下一预留时
```

### 6.1 普通预算不足

账户为 `open` 但 `R_new > B_spendable` 时返回 `insufficient_budget`：不创建预留或调用，不产生消耗，并返回“停止外部调用、需要确定性结果收敛”的意图。编排在发现处理模块完成已有候选和覆盖的收敛后，才由任务模块创建 `partial` 快照并暂停。追加授权后可显式恢复，不需要进入 `frozen_overage`。

## 7. 账本事件

每条 `BudgetLedgerEntry` 包含稳定事件 ID、账户/任务、严格递增序号、类型、Intent ID、请求指纹、关联调用或授权 ID、非负 token 字段、UTC 时间、预期及提交后版本、关联 Trace 事件和安全原因码。

| 类型 | 投影影响 |
| --- | --- |
| `authorization_initial` | `A += amount` |
| `authorization_added` | `A += amount` |
| `reservation_created` | `R_active += R` |
| `reservation_released` | `R_active -= R` |
| `usage_settled` | `R_active -= R; K += actual` |
| `unknown_committed` | `R_active -= R; U += amount`（amount 为该事件携带的 token 字段：常规不可信/unknown 场景 amount=R，不可信报告值超过 R 的保守场景 amount=报告值） |
| `usage_overage_recorded` | `O += actual - R`，不再次增加 `K` |
| `freeze_applied` | 账户进入 `frozen_overage` |
| `freeze_cleared` | 账户恢复 `open` |
| `account_closed` | 账户进入 `closed` |

账本只追加，不覆盖。更正通过新的纠正事件表达，不删除历史。

## 8. 调用状态与预算结算

Provider 调用状态由审查执行模块的 `ModelCallAttempt.provider_state` 唯一拥有和迁移。预算模块不保存第二份调用状态，只消费统一工作单元中已核对的 Provider 状态与 usage，并产生预留释放、实际结算、不确定消耗、超额和冻结 Intent：

```text
reserved -> running -> succeeded
                    -> failed_known
                    -> unknown
```

预算异常不是调用终态；一次调用可以 `succeeded`，同时预算账户为 `frozen_overage`。

响应安全与业务解析状态由审查执行模块独立记录为 `accepted/invalid_output/security_rejected/not_available`。预算只依据 Provider 状态、usage 和预留结算；Provider 成功但响应被拒绝或 schema 无效时，调用仍可为 `succeeded`。

- **请求明确未发送**：预留可释放；
- **可信 actual <= R**：预留转为 `settled_known`，`K += actual`，差额自动回到可用余额；
- **可信 actual > R**：同一完成事务写 `usage_settled`、`usage_overage_recorded` 和 `freeze_applied`，调用按真实结果收敛并禁止新外部调用；FindingSet 确定性收敛后任务再暂停并形成 `partial`；
- **明确失败且有可信 usage**：按实际结算；
- **Provider 已确认成功但 usage 缺失/不可信**：调用保持 `succeeded`，预留完整转为 `U`，并记录独立的 `usage_state = missing / untrusted`；响应是否可用仍由执行模块的响应处理状态表达。若供应商返回的 usage 报告值大于 `R`（即使字段不可信无法归一为实际值），不得直接按 `U += R` 丢弃超出信号：按 `U += max(R, 报告值)` 的保守口径计入不确定消耗，并触发一次 Provider 硬预算能力重新验证，避免真实超额被隐藏后账户仍继续发起新调用；重新验证通过前账户进入 `pending_revalidation` 阻塞（等价于禁止创建新预留），重验失败且固定条件无需变化时保持阻塞并拒绝新预留（返回 `provider_revalidation_failed`），重验失败且必须改变固定条件时返回 `new_task_required`；
- **请求是否送达或 Provider 是否处理结果确实不明**：预留完整转为 `U`，调用为 `unknown`，不得自动释放或重试；
- **重试**：总是新调用、新预留和新 Trace，不覆盖旧尝试。

## 9. 公开契约

预算核心提供以下领域操作，返回可加入统一工作单元的 Intent：

```text
validate_initial_authorization(task_spec, requested_tokens)
  -> CreateBudgetAccountIntent

prepare_reservation(account, prepared_request, capability_evidence,
                    model_call_id, expected_revision)
  -> ReserveBudgetIntent | ReservationDenied

release_unsent_reservation(reservation_id, proof, expected_revision)
  -> ReleaseReservationIntent

settle_known_usage(reservation_id, normalized_usage, expected_revision)
  -> SettleKnownUsageIntent [+ FreezeForOverageIntent]

settle_uncertain_usage(reservation_id, reason, expected_revision)
  -> MarkUncertainUsageIntent

add_authorization(task_id, token_delta, trusted_user_action,
                  expected_revision)
  -> AddAuthorizationIntent

evaluate_unfreeze(account, revalidation_evidence,
                  trusted_resume_action, expected_revision)
  -> UnfreezeBudgetIntent | UnfreezeDenied

get_summary(task_id, ledger_version)
  -> BudgetSummary
```

每个 Intent 包含稳定 `intent_id`、请求指纹、任务/账户标识、预期账户版本、关联业务标识和安全摘要。相同 Intent ID 与相同指纹重放返回原结果；同 ID 不同指纹返回 `intent_conflict`。

## 10. 原子事务

预算模块不持有数据库连接，也不单独提交跨模块事务。

### 10.1 任务创建事务

原子提交任务、固定规格、预算账户、初始授权、创建 Trace 和创建请求幂等记录。

### 10.2 调用准备事务

原子提交安全证明、预算预留、`reserved` 调用记录、请求 Trace 和工作单元关系。事务成功后才可把调用标为 `running`。

### 10.3 调用完成事务

原子提交安全处理后的响应或标准错误、预算结算、调用终态、Trace、业务结果和 checkpoint。

### 10.4 超额冻结事务

在调用完成事务中额外原子提交实际 usage、超额、账户冻结、调用/执行结果、Trace、checkpoint 和“需要确定性收敛”的意图。该事务不创建 ResultSnapshot，也不释放仍用于本地收敛的审查租约。随后编排禁止所有新外部调用，运行发现处理，原子提交 FindingSet、范围、逐发现 TraceLink、`partial` 快照、任务 `paused` 和租约释放。任一事务失败都停止新外部调用；CandidateFinding 不得直接进入快照。

### 10.5 追加与恢复

追加授权只允许任务为 `ready` 或 `paused`、无有效租约、未过期且未清理时进行。追加事务写授权、任务版本和 Trace，但不自动解冻。

显式恢复先确认授权已覆盖 `K + U + R_active`，并重新验证 Provider 硬预算能力，再原子提交 `freeze_cleared`、任务恢复许可、Trace 和新的执行租约。恢复校验只证明账户可以重新尝试准备调用；每次真实调用仍须基于最终请求计算 `R_next` 并重新执行预留门禁。若余额不足以覆盖 `R_next`，任务按普通 `insufficient_budget` 再次暂停，不恢复冻结状态。

## 11. 并发与幂等

- 账户 `revision` 使用乐观锁，账本 `(account_id, sequence)` 唯一；
- 预留与 `model_call_id` 一一对应；
- 授权 `request_id` 唯一；
- 结算同一 reservation 最多成功一次；
- 执行面写入携带任务版本、有效租约 ID 和 fencing token；任务创建、预算追加、清理等本机可信用户控制面写入不要求执行租约，但必须证明当前无有效租约，并携带预期任务版本、显式用户操作凭据、请求幂等键和请求指纹；
- 版本或 fencing 不匹配时不应用任何预算、Trace 或任务变更；
- 恢复不得重新结算已结算调用，也不得复用旧 reservation。

## 12. 错误模型与恢复

| 错误码 | 行为 |
| --- | --- |
| `invalid_budget` | 创建或追加前拒绝 |
| `authorization_limit_exceeded` | 拒绝会使累计授权超过上限的追加 |
| `insufficient_budget` | 不创建调用，任务暂停并形成部分结果；对应任务模块暂停原因 `budget_exhausted` |
| `provider_hard_budget_incompatible` | 不允许调用；固定能力不兼容时需新任务 |
| `prepared_request_mismatch` | 预留失效，禁止发送 |
| `usage_untrusted` | 按完整预留转不确定消耗 |
| `external_result_unknown` | 按完整预留计入 `U`，暂停且不自动重试 |
| `budget_overage` | 记录实际与超额，冻结并形成部分结果 |
| `unfreeze_budget_insufficient` | 保持冻结 |
| `provider_revalidation_failed` | 冻结场景保持冻结；不可信超额（未冻结）场景保持 `pending_revalidation` 阻塞并拒绝新预留；固定条件需变化则返回 `new_task_required` |
| `budget_revision_conflict` | 整个事务不生效，调用方重新读取 |
| `budget_integrity_error` | 立即停止新外部调用，不通过补账伪装成功 |

错误只含稳定码、阶段、范围、可恢复性、固定下一步和安全关联标识，不包含第三方异常、请求正文、代码或凭证。

## 13. 安全约束

1. 只有最终、已安全处理且不可变的 prepared request 可以计数和预留；
2. 计数对象、Trace 指向对象和实际发送对象必须是同一字节摘要；
3. Provider usage 只能由受信任适配器和固定映射归一化，模型文本无权声明；
4. 仓库内容、模型输出和工具结果不能提高预算、解冻或触发恢复；
5. 响应被安全拒绝仍按可信 usage 或保守预留结算；
6. 账本和错误不保存 prompt、响应、源码、凭证或第三方异常原文；
7. 安全门禁与预算门禁相互独立，预算不足不能跳过安全处理。

## 14. 查询、报告和清理

`BudgetSummary` 至少提供账本版本、累计授权 `A`、已知实际 `K`、不确定消耗 `U`、活动预留 `R_active`、已释放预留累计（`reservation_released` 事件的 amount 汇总，供报告展示）、累计超额 `O`、剩余预算、授权赤字、账户状态、冻结原因、最近能力验证引用，以及 usage 可信度汇总（`missing`/`untrusted` 状态预留计数与 `pending_revalidation` 阻塞标记），供报告和 Trace 展示 usage 可信度。

Trace 只引用权威账本条目 ID、账本版本和当时的展示快照；预算账本始终是决策事实源。

预算明细与任务、调用、Trace、checkpoint 和安全证明使用相同保留组。清理用例在一个事务中删除全部详细记录并留下最小脱敏墓碑；失败时全部保留。报告文件不由预算模块删除。

## 15. 持久化逻辑结构

基础设施至少实现以下逻辑集合：

| 集合 | 写入模式 | 关键约束 |
| --- | --- | --- |
| `budget_accounts` | 条件更新 | `task_id` 唯一，revision 乐观锁 |
| `budget_authorizations` | 只追加 | `request_id` 唯一，累计授权不超上限 |
| `budget_reservations` | 状态受控迁移 | `model_call_id` 唯一 |
| `budget_ledger` | 只追加 | `(account_id, sequence)` 唯一 |
| `budget_freezes` | 只追加并显式解决 | 同账户至多一个 active freeze |
| `provider_budget_capabilities` | 只追加 | 证据摘要不可改写 |

物理投影缓存可以存在，但必须能由账本核对，不能成为独立写入口。

## 16. 关键不变量

1. 一个任务恰好一个预算账户；
2. 每次模型尝试恰好一个独立预留；
3. 外部请求前预留已经提交；
4. 新预留不得超过可用授权；
5. 活动预留结算后只能进入已知实际或不确定消耗之一；
6. unknown 不自动释放、不自动重试；
7. 只有明确未发送的请求可释放预留；
8. 超额完整计入 `K`，`O` 只披露、不重复计费；
9. 冻结时不能创建新预留；
10. 追加授权不自动解冻、不改写历史；
11. 解冻需要授权覆盖已有承诺消耗、用户显式恢复和 Provider 重新验证；下一调用仍必须另行覆盖其最终预留；
12. 预算、调用、Trace、任务和 checkpoint 事务全有或全无；
13. 仓库及外部内容不能改变预算授权；
14. 不同任务的账户和流水不能串写。

## 17. 测试设计

### 17.1 领域与性质测试

- 默认、边界和非法预算；
- `R = I_bound + O_max` 及请求摘要变化导致预留失效；
- actual 小于、等于和大于 reservation；
- usage 缺失、不可信、字段重叠和响应安全拒绝；
- 不可信 usage 报告值大于 `R` 时按 `U += max(R, 报告值)` 保守计入、触发 Provider 硬预算能力重新验证、重验通过前拒绝新预留（`pending_revalidation`），重验失败且固定条件需变化时返回 `new_task_required`；
- Hypothesis 生成事件序列，证明 `C = K + U + R_active`、不重复计费和授权上限；
- 冻结时 `B_spendable = 0`；
- 追加不足保持冻结，追加足额但未显式恢复仍冻结；
- 足额追加、重新验证和显式恢复后解冻；
- 固定 Provider/模型必须变化时要求新任务。

### 17.2 幂等与并发测试

- 相同授权/预留/结算 Intent 重放不重复写入；
- 同标识不同指纹冲突；
- 两连接竞争预留时只有满足最终余额的一方成功；
- 旧任务版本、旧账户 revision 和旧 fencing token 被拒绝；
- 同一 reservation 不可同时结算为 known 与 uncertain。

### 17.3 故障注入与合约测试

- 准备事务提交前后崩溃；
- `running` 标记后、响应完成事务前崩溃；
- 超额结算、冻结及其第一阶段 Trace/checkpoint 全有或全无；第二阶段任务暂停、`partial` 快照或租约释放失败时，第一阶段已提交的冻结与超额保持且停止新外部调用，而不是回滚第一阶段；
- 追加授权成功但恢复校验失败时授权保留、账户仍冻结；
- 清理中断不留下部分账本；
- 报告预算摘要与指定账本版本一致。

## 18. ADR

### ADR-BUDGET-001：采用只追加账本和调用级预留

- **决定**：预算事实只追加，当前状态通过投影得到。
- **原因**：准确表达未知调用、重试、超额和追加授权，支持审计与恢复。
- **代价**：查询需要投影或缓存，并增加幂等约束。

### ADR-BUDGET-002：超额采用可恢复冻结

- **决定**：可信实际 usage 超过预留时暂停同一任务并冻结预算账户，不终止任务。
- **原因**：保留固定输入、checkpoint 和已完成结果，同时继续如实披露 Provider 硬预算异常。
- **保护条件**：授权覆盖已有承诺消耗、显式恢复和 Provider 硬预算能力重新验证缺一不可；下一调用另行执行硬预留门禁。
- **代价**：任务状态、预算冻结状态和恢复许可必须保持正交。

### ADR-BUDGET-003：预算与 Trace 共享原子工作单元

- **决定**：预算模块产生 Intent，由统一 `PersistenceUnitOfWork` 与调用、任务、Trace 和 checkpoint 共同提交。
- **原因**：避免补账、孤立 Trace 和恢复歧义。
- **代价**：基础设施事务适配器需要验证更多跨模块约束。

## 19. 后续模块契约

- 审查执行模块必须在发送前使用最终 prepared request 请求预留；
- Model Provider 必须提供硬预算能力证据、关闭自动重试并返回规范化 usage；
- Trace 模块引用预算账本而非维护第二套余额；
- 任务模块将预算异常表达为 `paused + budget_anomaly`，不得进入 `terminated`；解除冻结以覆盖已有承诺为准，下一调用的预留在最终请求形成后独立校验；
- 报告模块展示授权、已知实际、不确定消耗、活动预留、超额、赤字和冻结状态；
- SQLite 适配器必须实现账户 revision、唯一键和跨模块原子提交。
