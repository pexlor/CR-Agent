# Code Review Agent 输入模块详细设计

## 1. 文档状态

- 日期：2026-09-10
- 状态：设计完成，待复审
- 上游依据：《需求拆解.md》《验收清单.md》《技术选型.md》《架构设计.md》《模块设计/任务模块.md》《模块设计/安全模块.md》
- 适用范围：本地 CLI、单进程、UTF-8 unified diff、GitHub.com PR、GitLab.com MR

本文设计输入固定、完整性证明、统一变更集和固定版本上下文读取。CLI 参数、平台 SDK 实现、SQLite 物理表和审查算法不在本文范围内。

## 2. 设计结论

输入模块采用“受信任 Input Provider + 双阶段固定 + 统一 `ChangeSet` + 可核对完整性证明”：

1. 任务创建时固定输入意图；获取成功后先固定实际版本（base/head SHA 或 diff 摘要），再在标准化成功后通过 `InputBinding` 一次性落盘绑定该版本；
2. 平台输入固定 base/head SHA，独立 diff 固定规范化内容摘要，不伪造提交 SHA；
3. 只有完整输入能进入规划阶段，截断、缺页、溢出或版本漂移必须失败；
4. 原始内容仅存在于受控内存，跨模块和持久化只传 `SanitizedArtifactRef`；
5. 上下文只能按明确许可从固定版本按需读取，不枚举全仓库；
6. 输入获取和标准化分别形成 checkpoint，模块只提交 `TaskTransitionIntent`。

## 3. 目标与非目标

目标：统一三种输入语义；处理空 diff、纯删除、重命名和二进制；强制 1 MiB、200 文件、10,000 变更行上限；固定并证明平台版本；支持公开及只读授权私有仓库；使范围和限制可报告、可恢复。

非目标：混合输入、GitHub Enterprise、自建 GitLab、仓库克隆、Git/脚本/构建执行、全仓索引、预算判断、任务状态修改、工作单元生成或报告生成。

## 4. 模块边界

```text
审查编排 → 输入核心 → InputProviderPort
                    → SecurityBoundaryPort
                    → PersistenceUnitOfWork
```

领域核心不得依赖 Typer、PyGithub、python-gitlab、HTTPX、unidiff、SQLite 或 keyring。Provider 可获得定向网络和凭证能力，但不能访问模型、预算、报告或任务状态。

## 5. 领域模型

### 5.1 InputIdentity

- 独立 diff：输入类型、规范化内容摘要、摘要算法、规范化规则版本；
- 平台对象：Provider 身份与版本、平台、仓库稳定身份、PR/MR 编号、base/head SHA；
- 共同字段：schema 版本、安全显示名和身份摘要。

URL 只用于识别，进入领域前移除 userinfo、query 和 fragment；API 主机只能是对应官方主机。

### 5.2 ChangeSet

`ChangeSet` 是不可变、可规范序列化的统一输入聚合：

- `change_set_id`、`schema_version`、`InputIdentity`；
- `CompletenessProof`；
- 有序 `ChangedFile[]`；
- 实际字节数、文件数、变更行数和适用上限；
- 可审查、不可审查、安全跳过范围摘要；
- 安全处理后的内容引用、规范化规则版本和创建时间。

### 5.3 ChangedFile、Hunk 与 Line

`ChangedFile` 包含稳定文件 ID、旧/新规范路径、变更类型、语言、文本/二进制属性、hunk、统计和不可审查原因。`Hunk` 包含旧/新范围、有序行及摘要。`Line` 包含行类型、旧/新行号、顺序、内容安全引用和安全处理状态。

新增行只能有新侧定位，删除行只能有旧侧定位，上下文行可同时有两侧定位。脱敏不得改变 hunk 行数、行类型或行号映射；无法保持结构时必须跳过对应范围或拒绝输入。

### 5.4 CompletenessProof

完整性证明至少记录输入身份、Provider 与获取尝试、固定版本、分页连续性、平台计数与实际计数、规模统计、截断/折叠/溢出/漂移检查、二进制集合、ChangeSet 摘要、规则版本和结论。

只有 `complete` 能创建 `InputBinding`。该证明是获取过程的可审计证据，不宣称平台数据的密码学真实性。

## 6. 稳定标识与版本

- `ChangeSetId`：输入身份、固定版本、规范化规则和 schema 主版本的摘要；
- `FileId`：ChangeSet、变更类型、旧/新路径摘要；
- `HunkId`：文件、旧/新范围和 hunk 摘要；
- `LineId`：hunk、行类型、行号、顺序和处理后内容摘要。

规范序列化固定为 UTF-8、稳定键顺序和领域分隔摘要。内容 ID 用于完整性和恢复，不用于授权。跨模块 schema 使用 `major.minor`：主版本不兼容，次版本只能增加具有确定默认值的可选字段；持久化记录不得静默改写。

## 7. 三类输入规则

### 7.1 独立 diff

文本与文件入口的相同内容产生相同身份。文件路径只是读取来源，不属于审查身份。严格 UTF-8；空 diff 形成完整空 ChangeSet；纯删除保留旧侧定位；重命名保留路径关系；二进制保留文件级事实并标记不可审查。损坏、危险路径和任一超限均拒绝整个输入，不截断继续。独立 diff 默认没有可信仓库上下文读取能力。

### 7.2 GitHub PR

仅接受 `github.com` 的 Open 或 Draft PR；完整遍历文件分页；固定 base/head SHA；后续文本读取使用固定 commit。关闭、合并、无权限、缺页、patch 不完整、计数不一致、跨主机重定向或超限均失败。

### 7.3 GitLab MR

仅接受 `gitlab.com` 的 Open 或 Draft MR；完整遍历 diff 分页并固定 SHA。出现 `collapsed`、`too_large`、`overflow`、缺页、截断或版本不一致即失败，不依赖已弃用且不能证明完整性的接口。

## 8. 获取、固定与恢复

```text
输入意图 → 选择 Provider → 固定版本 → 完整获取
→ 安全处理 → input_acquired checkpoint
→ 解析与结构校验 → ChangeSet + CompletenessProof
→ InputBinding + input_normalized checkpoint
```

两个 checkpoint 都须通过统一持久化工作单元原子提交安全证明、Trace 和任务转换意图。版本固定在 `input_acquired` checkpoint 完成（写入获取到的 base/head SHA 或 diff 摘要），`InputBinding` 仅在标准化成功时写入一次；标准化重做以获取 checkpoint 的固定版本核对。相同绑定幂等，不同绑定返回 `fixed_condition_mismatch`。

恢复时：已完成且摘要、schema、Provider、规范化规则、安全证明均可核对的阶段直接复用；本地确定性解析可重做；平台请求明确失败可由应用层新建尝试；结果不明不得拼接旧响应；已绑定版本变化必须新建任务。

## 9. 固定版本上下文读取

`ReadFixedContext` 只接受编排层签发的许可，许可包含任务、InputBinding、固定 SHA、规范路径、用途和大小上限。仅平台输入可读取；不得使用默认分支、当前 head、目录通配或本地工作树。返回内容先经安全门禁，再形成带摘要和来源证明的上下文引用。二进制、超限、路径越界、版本不符或安全不确定均拒绝。

## 10. 公开端口

- `InputProviderPort`：规范化身份、获取固定 diff、读取固定版本文本、返回标准错误；
- `DiffParserPort`：把安全文本解析为严格结构，不决定完整性；
- `SecurityBoundaryPort`：处理原始输入和上下文并返回安全证明；
- `InputArtifactRepository`：按稳定引用读取不可变输入产物；
- `PersistenceUnitOfWork`：原子提交输入记录、Trace、checkpoint 和转换意图；
- `Clock`、`IdGenerator`、`SecurityLogPort`。

## 11. 错误与降级

稳定错误至少包括：`input_unsupported`、`input_invalid_utf8`、`input_malformed`、`input_too_large`、`input_incomplete`、`input_version_changed`、`input_closed`、`input_merged`、`credential_unavailable`、`permission_denied`、`platform_temporarily_unavailable`、`context_not_authorized`、`security_boundary_failed`、`persistence_integrity_failed`。

输入整体不完整、固定版本不可信、安全边界失败或持久化失败不得降级。二进制、不支持语言和可安全跳过片段可作为不可审查范围继续，但必须降低覆盖状态。

## 12. 关键不变量

1. 一个任务只有一个输入意图和至多一个 InputBinding；
2. ChangeSet 的所有内容属于同一固定版本；
3. 未证明完整的输入不能进入规划；
4. 原始输入、凭证和 SDK 对象不跨越适配器边界；
5. 所有持久化 payload 都有可核验安全证明；
6. Provider 不修改任务、预算或输出；
7. 上下文读取不扩大输入身份且只读取固定版本；
8. 相同规范输入产生相同稳定内容 ID；
9. 输入阶段失败不能被表达为“完整且无发现”。

## 13. 测试与需求映射

- 领域测试：路径、行号、稳定 ID、规模、空/删除/重命名/二进制、schema 兼容；
- Provider 合约：分页、固定 SHA、Draft、私有权限、漂移、截断、官方主机限制和错误映射；
- 安全测试：diff、上下文、URL、异常和模拟 secret；
- 故障注入：获取、扫描、解析、绑定和 checkpoint 各边界；
- 性质测试：相同输入确定性、任一文件不重不漏、统计与结构一致。

主要覆盖 FR-001～FR-004、FR-011～FR-014、FR-025～FR-028。

## 14. 设计决策

- 选择双阶段固定而非一次性大事务：隔离外部获取与本地标准化，并提供可恢复边界；
- 选择完整失败而非平台截断后部分审查：避免把未知遗漏冒充已知范围；
- 选择按需固定版本读取而非克隆仓库：满足只读上下文且缩小执行和泄露面；
- 选择领域 ChangeSet 而非透传 SDK 模型：保证平台无关和可测试性。

## 15. 设计结论

输入模块将三类来源统一为固定、完整、可安全持久化的 `ChangeSet`，以完整性证明、稳定标识和双 checkpoint 保证恢复一致性，并通过受限固定版本读取支持后续审查而不扩大仓库执行权限。
