# Code Review Agent 审查规划模块详细设计

## 1. 文档状态

- 日期：2026-09-10
- 状态：设计完成，待复审
- 上游依据：《架构设计.md》《模块设计/任务模块.md》《模块设计/安全模块.md》《模块设计/输入模块.md》
- 适用范围：本地单进程、首版串行审查

## 2. 设计结论

采用“文件优先切分 + hunk 装箱 + 超大 hunk 行块降级 + 不可变冻结计划”：

1. 先建立完整覆盖清单，再为可审查范围生成工作单元；
2. 可容纳时一文件一单元，超限时保持完整 hunk 分组，单 hunk 仍超限才按行边界切块；
3. 工作单元身份与执行顺序分离；首版串行不成为领域假设；
4. 规划只校验单次上下文容量，不预留或审批任务 token 预算；
5. 工具选择来自任务固定声明，仓库内容不能授予工具能力；
6. 计划原子冻结，恢复复用，不根据当前环境重新规划。

## 3. 目标与非目标

目标：范围不重不漏；稳定切分；每单元可独立执行、持久化和恢复；明确不可审查原因；确定工具适用性；相同固定条件产生相同计划指纹。

非目标：输入获取、上下文实际读取、模型调用、预算决策、工具执行、发现处理、任务状态修改、自动重规划或并发调度。

## 4. 输入契约

`PlanningRequest` 包含 task、InputBinding、ChangeSet 安全引用、固定任务规格摘要、规划策略、模型容量摘要和固定工具目录。规划视图只暴露规范路径、变更类型、语言、hunk/line 结构、内容摘要、安全引用、不可读取标记和固定上下文能力，不接收裸代码、SDK 对象或仓库配置。

## 5. 领域模型

### 5.1 ReviewPlan

不可变 `ReviewPlan` 包含 `plan_id`、`plan_version`、task/InputBinding、策略/模型容量/工具目录摘要、`CoverageScope[]`、`WorkUnit[]`、计划指纹和安全证明。MVP 一个任务只有一个有效计划，版本为 1；未来重规划必须创建新版本，不改写旧计划。

### 5.2 CoverageScope

范围是规划和结果共同使用的最小覆盖单位，包含稳定 ID、文件身份、旧/新行区间、范围类型、内容摘要、父范围及规划处置：

- `planned`：恰好被一个工作单元覆盖；
- `unreviewable`：二进制、不支持语言、安全跳过、不可读取或不可安全切分；
- `no_review_required`：无文本审查对象的元数据变化。

“已审查”不是规划事实。最终 `reviewed/unreviewed/unreviewable/unknown` 由冻结计划和执行记录联合投影。规划处置到最终覆盖状态的投影规则如下，由发现处理模块在生成 CoverageSnapshot 时统一执行：

- `planned` 且对应执行事实成功 → `reviewed`；
- `planned` 但单元未执行或执行失败 → `unreviewed`；
- `planned` 但执行结果为 `unknown` → `unknown`；
- `unreviewable`（含安全跳过片段）→ `unreviewable`；
- `no_review_required` → `reviewed`（该范围无文本审查对象，视为已如实完成覆盖，不产生任何发现）。

投影结果必须保持范围坐标守恒：任一范围恰好投影到一个最终状态，遗漏或重复都视为持久化完整性错误。

### 5.3 WorkUnit

工作单元包含 `work_unit_id`、计划、类型、文件身份、有序 scope ID、行区间、内容安全引用、上下文请求声明、工具选择、容量估计、`execution_rank` 和 fingerprint。

类型只有 `file`、`hunk_group`、`line_block`。一个单元只属于一个逻辑文件；跨文件关系由执行时的受控上下文和发现处理表达，不创建隐式全仓单元。

### 5.4 ToolSelection

工具选择包含固定 tool ID/版本、声明和规则摘要、适用原因、资源上限、失败影响及顺序。失败影响为 `evidence_degraded` 或 `coverage_degraded`。选择工具不代表工具已运行或验证成功。

## 6. 稳定身份与排序

所有 fingerprint 使用领域分隔的规范 JSON + SHA-256，仅用于完整性和确定性。

- `ScopeId`：文件身份、范围类型、旧/新区间和内容摘要；
- `WorkUnitId`：plan、类型、文件身份、有序 scope 和切分策略版本；
- 工作单元 fingerprint：scope、内容摘要、上下文声明、工具选择、规划策略和模型容量；
- 计划 fingerprint：输入绑定、策略、容量、工具目录、全部范围和工作单元语义。

`execution_rank`、时间、尝试和 checkpoint 不参与身份。文件按规范主路径、次路径、变更类型和文件 ID 排序；hunk 按旧/新范围和摘要排序；未来调整调度顺序不改变工作单元身份。

## 7. 切分算法

1. 校验 ChangeSet 完整性和结构；
2. 为每个文件建立 CoverageScope；
3. 不可审查范围直接记录原因；
4. 对可审查文件估算固定开销、变更内容、预留上下文和最大输出占用；
5. 文件可容纳则生成 `file` 单元；
6. 否则以完整 hunk 按稳定顺序首次适配装箱为 `hunk_group`；
7. 单个 hunk 超限时，以行边界生成连续 `line_block`，保留最小重叠锚点但覆盖身份不重叠；重叠锚点行只作为模型上下文，不进入 CoverageScope 的旧/新坐标和范围身份，因此不破坏发现处理 3.3 的"范围坐标两两互斥且与计划坐标集合完全一致"约束；
8. 任何块仍无法容纳时标记 `unreviewable/context_capacity_exceeded`；
9. 校验每个 planned scope 恰好属于一个单元后冻结计划。

容量估算使用模型固定能力和保守 tokenizer/字节上界；它只保证请求可能装入上下文。实际预算预留由执行阶段预算模块完成。

## 8. 上下文声明

规划可声明 `ContextRequest`，包括用途、当前文件、允许的相关路径类别、单文件/总字节上限和选择规则，但不实际读取。路径必须由固定 ChangeSet 或受信任规则确定；代码注释、README 和模型输出不能新增路径或扩大许可。独立 diff 没有固定仓库来源时不声明外部上下文。

## 9. 计划冻结与恢复

计划、工作单元、覆盖范围、工具选择、安全证明、Trace 和 `plan_created` checkpoint 在统一事务中提交，并产生阶段到 `planned` 的 `TaskTransitionIntent`。事务失败不得暴露半个计划。

恢复时必须核对 plan fingerprint、InputBinding、策略、模型容量、工具目录和安全证明。匹配则直接复用；不匹配返回 `plan_integrity_error` 或 `new_task_required`，不得静默重算并复用旧执行结果。

## 10. 公开端口

- `ReviewPlanner.plan(PlanningRequest) -> PlanningResult`；
- `PlanningArtifactResolver`：解析用途匹配的安全输入视图；
- `ToolCatalogPort`：读取任务固定的声明式工具快照；
- `CapacityEstimatorPort`：提供确定性保守容量估算；
- `PlanRepository`：按 task/plan 读取不可变计划；
- `PersistenceUnitOfWork`：原子保存计划、Trace、checkpoint 和转换意图。

## 11. 错误模型

稳定错误包括 `changeset_integrity_error`、`planning_schema_incompatible`、`capacity_profile_invalid`、`tool_catalog_mismatch`、`unsafe_artifact`、`plan_already_exists`、`plan_integrity_error`、`persistence_integrity_failed`。

单个范围不可审查是可报告处置；ChangeSet 不完整、固定条件不一致、安全证明无效或计划覆盖不守恒是整体失败。

## 12. 关键不变量

1. 每个 planned scope 恰好属于一个工作单元；
2. unreviewable scope 不进入模型或工具输入；
3. 一个工作单元只属于一个逻辑文件；
4. 工作单元身份不包含执行顺序；
5. 计划冻结后不可修改；
6. 规划不读取任务剩余预算、不创建模型调用；
7. 工具只能从固定目录中选择，且不得扩大能力；
8. 相同固定语义产生相同 fingerprint；
9. 恢复不自动重规划；
10. 计划产物均具有安全证明。

## 13. 测试与需求映射

- 单元/性质测试：范围守恒、稳定排序、文件/hunk/行块边界、容量极值、顺序不影响身份；
- 安全测试：仓库内容不能改变工具、上下文或容量规则；
- 恢复测试：计划复用、摘要冲突、schema/工具变化；
- 故障注入：冻结事务前后不产生半计划。

主要覆盖 FR-004～FR-005、FR-011～FR-014、FR-017～FR-019、FR-021、FR-027～FR-028。

## 14. 设计决策

- 文件优先兼顾评论上下文和简单性；hunk/行块只在容量需要时启用；
- 覆盖身份与执行顺序分离，为未来并发保留边界但不引入调度复杂度；
- 冻结计划而非恢复时重算，确保 checkpoint、预算和发现可复用；
- 工具在规划期固定，禁止模型动态授权。

## 15. 设计结论

审查规划模块把固定 ChangeSet 转换为覆盖守恒、容量可执行且可恢复的不可变计划；它明确“计划覆盖”与“实际完成”的差异，并为执行、发现和报告提供统一范围坐标系。
