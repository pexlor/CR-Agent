# Code Review Agent 发现处理模块详细设计

## 1. 文档状态

- 日期：2026-09-10
- 状态：设计完成，待复审
- 上游依据：《架构设计.md》及输入、规划、执行、任务、安全模块设计
- 核心流水线：`CandidateFinding → ValidatedFinding → FinalFinding → FindingSet`

## 2. 目标与边界

本模块保证只有结构完整、位置真实、证据可核对、属于本次变更且可行动的发现进入结果。它是纯确定性领域逻辑，不调用模型、网络或工具，不修改任务/预算/checkpoint（即不改写任务状态、预算余额或既有 checkpoint；它只产生新的 `findings_consolidated` checkpoint 事实与任务转换意图，由统一持久化工作单元原子提交，checkpoint 只追加不覆盖），不渲染报告。

严重度和置信度独立；模型自评分不具有裁决权。高置信度必须有直接代码证据，并有成功的确定性工具验证或可直接核对的语言语义依据。

## 3. 领域模型

### 3.1 ValidatedFinding

包含 contributing candidate、task/InputBinding/plan、规范化问题/影响/建议、触发条件、主/关联位置、证据、范围因果、可行动性、归一严重度、置信度输入、临时 fingerprint、验证 Trace 和策略版本。

### 3.2 FinalFinding

包含 `finding_id`、稳定 fingerprint、category、severity、confidence、标题、问题、证据摘要、触发条件、影响、建议、位置、证据引用、trace ID、来源候选和策略版本。`finding_id` 是任务作用域的稳定身份：由 `(task_id, fingerprint v1)` 派生（fingerprint v1 不含 task，故必须并入 task 作用域），或按任务内显式分配；不同任务、同一任务不同 FindingSet 版本中对同一 fingerprint 复用同一 `finding_id`，基础设施"finding fingerprint 唯一"约束限定为"同一任务/同一 FindingSet 版本内唯一"。

置信度仅允许：

- `high`：高置信度可直接采纳；
- `advisory`：仅供参考。

“可直接采纳”只表达证据强度，不授权自动修改、合并或发布。

`FinalFinding` 本身就是报告中的最终评论，不另设 `Comment` 聚合或 `comment_id`。TraceLink 以 `finding_id` 为唯一评论身份，并关联 contributing candidate、模型/工具尝试、证据、验证事件和 consolidation checkpoint，避免 Finding 与 Comment 双重身份。

### 3.3 FindingSet

不可变、版本化集合，包含 task/InputBinding/plan、最终发现、确切 `CoverageSnapshot` 引用、拒绝和冲突摘要、来源 checkpoint、汇总 Trace、内容摘要和安全策略证明。恢复可创建新版本，不改写旧集合。

`CoverageSnapshot` 是不可变、版本化的覆盖事实唯一来源，至少包含：`snapshot_id`、`task_id`、`snapshot_version`、来源 `plan_id`、`input_binding_id`、来源 `checkpoint_id`（即 `execution_fact_boundary_id`，锚定生成快照所用的执行事实边界）、按计划范围坐标穷尽且两两互斥的 scope 明细（`reviewed`/`unreviewed`/`unreviewable`/`unknown` 四态之一及原因码）、四类统计计数、内容摘要和安全策略证明。scope 明细的坐标集合必须与冻结计划的范围坐标集合完全一致（不多不少），任一坐标缺失或重复视为持久化完整性错误。FindingSet 内联保存自身的最终发现等内容，同时以引用形式（稳定 ID、版本、task ID、schema 版本、内容摘要和安全证明）引用 CoverageSnapshot，不复制 CoverageSnapshot 的四类覆盖范围；提交时必须证明该覆盖快照与 FindingSet 引用同一 `execution_fact_boundary_id`。

## 4. 验证流水线

按固定顺序执行：

1. schema、字段长度、枚举和安全引用校验；
2. task、InputBinding、plan、work unit 和尝试引用一致性；
3. 位置解析；
4. 证据真实性、适用范围和安全语义校验；
5. 本次变更因果判断；
6. 可行动性判断；
7. 文本与类别规范化；
8. 去重、冲突归并；
9. 严重度归一；
10. 两级置信度判定；
11. 定型 `FinalFinding`：把验证通过的发现固化为主键 `finding_id`（稳定 fingerprint v1 派生或显式分配）、最终类别、严重度、置信度和证据引用，并生成其 `TraceLink`；`finding_id` 在此步骤首次赋值，fingerprint v1 作为其稳定语义指纹，报告中的评论身份即该 `finding_id`；
12. 稳定排序并生成 FindingSet。

任一步拒绝均产生结构化 `FindingRejection` 和 Trace 事实，但拒绝文本不得泄露未安全内容。

## 5. 位置模型

统一位置支持：

- `changed_line/new`：固定 diff 新侧行；
- `deleted_line/old`：删除前旧侧行；
- `file`：文件整体、缺失行为或无法精确到行；
- `cross_file`：一个主位置及 cause/effect/supporting 关联位置。

路径必须来自固定 ChangeSet。行号必须解析到对应 hunk；无法精确定位时降级到有证据的文件级位置，不得绑定邻近无关行。重命名的新侧使用新路径、删除侧使用旧路径。跨文件主位置选择最直接引入问题且最适合修复的位置；无法唯一选择时采用稳定排序并明确局限。

## 6. 证据模型

证据类型：`changed_code`、`context_code`、`deterministic_tool`、`language_semantics`、`change_relation`、`absence`。每条证据包含 claim、subject、产物/尝试/Trace 引用、位置、工具或语义规则身份、状态、强度和限制。

强度为 `direct`、`corroborating`、`contextual`、`weak`、`contradicting`。最终发现至少一条 direct 证据；模型复述不是独立证据。

工具证据仅在尝试成功、版本/规则/输入摘要匹配、实际覆盖对应范围且 claim 足够时有效。工具失败、未运行或仅“适用”不能显示为验证成功。

语言语义证据必须记录语言、规则 ID/版本、成立前提及直接代码依据；依赖未知配置、框架约定、外部服务、未读调用方、命名猜测或需执行测试才能确认的内容不能支撑 high。

## 7. 范围和可行动性

范围关系为 `introduced`、`aggravated`、`exposed`、`pre_existing`、`unrelated`、`indeterminate`。只有前三者在因果清楚时可继续；必须证明“本次变更事实 → 行为/约束变化 → 具体风险”。既有或无关问题拒绝。

可行动性为 `actionable`、`conditionally_actionable`、`not_actionable`。最终发现必须有可核对位置、触发机制、具体影响和与证据一致的修复方向。`not_actionable` 拒绝；conditionally actionable 最多为 advisory。

任务覆盖由冻结计划和执行事实汇总到不可变 `CoverageSnapshot`，不能因“没有候选”推断为已审查。FindingSet 只能引用该快照，不能维护第二份范围明细。

本模块作为规划 5.2 投影规则的统一执行方，生成 CoverageSnapshot 时按下表把规划处置与执行事实投影为最终覆盖状态，任何范围恰好投影到一个最终状态（遗漏或重复视为持久化完整性错误）：

| 规划处置 | 执行事实 | 最终覆盖状态 |
| --- | --- | --- |
| `planned` | WorkUnitExecution 成功（`succeeded` 且范围真实完成） | `reviewed` |
| `planned` | 单元未执行、`failed`、`partial`，或 `succeeded + invalid_output/security_rejected` | `unreviewed`（原因码区分） |
| `planned` | `unknown` | `unknown` |
| `unreviewable` | 含安全跳过片段 | `unreviewable` |
| `no_review_required` | 无文本审查对象 | `reviewed`（如实完成覆盖，不产生发现） |

`no_review_required → reviewed` 是规划期确定性判定（无文本审查对象），不违反“不因无候选推断已审查”；`planned` 范围的 `reviewed` 只由执行事实成功驱动，不由候选有无驱动。

## 8. 去重与冲突

fingerprint v1 由固定输入身份、类别、受控缺陷机制、主/关联语义主体和变更关系规范摘要产生；不含 task、候选、尝试、模型、时间、措辞和置信度。

同 fingerprint 候选合并贡献来源、证据和位置，选取信息最完整且证据最强的安全文本。相同位置但缺陷机制不同不合并；相同根因但需要独立修复且影响独立可保留多个发现。

冲突处理：

- 一方证据失效：拒绝失效方；
- 证据可兼容：合并并记录限制；
- 关键事实冲突且无法确定：降为 advisory；
- 冲突使问题本身不可行动：全部拒绝。

## 9. 严重度与置信度

### 9.1 严重度

严重度是影响程度，枚举为 `critical/high/medium/low`，依据可达性、影响面、数据/安全后果和恢复成本确定，不决定证据强度，也不参与置信度判定。

### 9.2 置信度

置信度是证据强度等级，枚举为 `high/advisory`，与严重度相互独立（见 3.2）。置信度 `high` 必须同时满足：

1. 属于本次变更；
2. 精确或诚实受限的位置；
3. 至少一条直接代码证据；
4. 确定性工具正向验证或可直接核对的语言语义；
5. 无未解决关键冲突；
6. 完全 actionable；
7. 关键证据范围未因安全脱敏、上下文缺失或工具失败受损。

其他仍成立且可行动的发现为 advisory。完全无直接依据、范围不明或不可行动者不输出。严重度等于 `high` 的发现若无上述证据强度，仍只能为 advisory，不得仅因影响大而提升置信度。

## 10. 稳定排序与结果提交

最终发现按 severity、confidence、规范路径、位置种类、行号、category、fingerprint 排序。FindingSet 内容摘要覆盖规范化发现和完整 `CoverageSnapshot` 引用；覆盖内容摘要由 CoverageSnapshot 自身负责。

CoverageSnapshot、发现集合、每条 FinalFinding 的 TraceLink、`comment.finalized`/`comment.trace_link_created` 事实、验证/拒绝 Trace、`findings_consolidated` checkpoint 和任务转换意图通过统一持久化工作单元提交。模块不创建 ResultSnapshot，但输出快照所需的不可变 CoverageSnapshot 与 FindingSet 引用。

### 10.1 停止后的确定性收敛

预算不足、预算异常、结果不明、用户中断或其他停止条件出现时，调用阶段不得直接创建可报告快照。编排先禁止新的外部调用，再调用本模块对所有已安全持久化的 CandidateFinding 和执行覆盖事实做纯确定性收敛：

1. 验证并合并停止前已有候选；
2. 将未开始、未完成和 unknown 单元投影为相应覆盖状态；
3. 生成不可变 CoverageSnapshot、引用它的 FindingSet、TraceLink 和 `findings_consolidated` checkpoint；
4. 再由任务模块创建 `partial` 或 `unknown` ResultSnapshot；
5. 快照成功后才能开始报告交付。

该收敛不读取新上下文、不运行工具、不调用模型、不追加预算。若连确定性收敛都因安全或持久化完整性失败而无法完成，不得把 CandidateFinding 直接放入报告。

## 11. 输入契约

`FindingProcessingRequest` 是不可变、版本化的收敛请求，至少包含：

- `request_id`、请求指纹和契约版本；
- `task_id`、`expected_task_version`、审查执行租约 ID 和 fencing token；
- `execution_fact_boundary_id`：不可变边界标识，锚定生成本次收敛所依据的 checkpoint sequence 和事实摘要；
- 固定 `InputBinding`、`ReviewPlan`、ChangeSet 身份及版本；
- 已安全持久化的 CandidateFinding、工具/模型执行事实和覆盖事实引用；
- 停止原因、预算状态、unknown 尝试集合及待收敛范围；
- 安全策略基线、相关安全证明引用和 provenance 摘要；
- 目标 consolidation checkpoint 的前驱引用。

所有引用必须直接锚定同一 `execution_fact_boundary_id`，并属于同一任务、同一冻结计划、同一输入版本；仅指向"最新投影"而非该边界的引用视为无效。安全证明必须满足任务基线。预期版本、租约或 fencing 不匹配、引用摘要不一致、引用跨越不同边界、请求重复但指纹不同，均拒绝整个请求；相同 `request_id` 和指纹返回原收敛结果。该请求只允许读取已持久化事实，不读取新上下文、不调用模型或工具、不追加预算。

输出为 `CoverageSnapshot`、`FindingSet`、Finding TraceLink、`findings_consolidated` checkpoint 和任务转换意图；这些意图必须通过同一 `PersistenceUnitOfWork` 原子提交。

## 12. 公开端口

- `FindingProcessor.process(FindingProcessingRequest)`；
- `ChangeSetEvidencePort`：解析固定位置和代码证据；
- `ExecutionEvidencePort`：读取候选、工具和模型尝试事实；
- `TraceReferencePort`：核对并产生发现级关联；
- `FindingRepository`：读取/保存不可变集合；
- `PersistenceUnitOfWork`。

## 13. 错误与拒绝原因

整体错误：`finding_input_integrity_error`、`schema_incompatible`、`evidence_store_inconsistent`、`security_attestation_invalid`、`persistence_integrity_failed`。

候选拒绝：`invalid_structure`、`location_not_found`、`evidence_not_found`、`evidence_mismatch`、`outside_change_scope`、`pre_existing_issue`、`not_actionable`、`duplicate_merged`、`unresolved_conflict`、`unsafe_content`。

单候选拒绝不使整个集合失败；权威引用损坏、安全失效，或无法证明 FindingSet 与 CoverageSnapshot 来自同一事实边界时必须整体失败。

## 14. 关键不变量

1. 未验证候选不能进入 FindingSet；
2. 每条发现至少有一个真实位置和一条 direct 证据；
3. 只评论本次变更新增或明显加剧的问题；
4. 置信度与严重度独立；
5. 模型自评分不决定等级；
6. 工具失败不冒充验证成功；
7. 同 fingerprint 在同一 FindingSet 至多一条；
8. 删除行、文件级和跨文件定位不虚构新侧行号；
9. 每条发现拥有可查询 Trace；
10. 覆盖不完整不能显示为完整审查。
11. 停止条件出现后必须先完成确定性收敛，再创建可报告快照；
12. `FinalFinding.finding_id` 是最终评论和 TraceLink 的唯一身份。
13. `CoverageSnapshot` 是详细覆盖事实的唯一来源，FindingSet 不复制覆盖范围。

## 15. 测试与需求映射

- 位置测试覆盖新行、旧行、文件、重命名和跨文件；
- 证据测试覆盖工具成功/失败、语义规则、冲突、脱敏和上下文缺失；
- 性质测试覆盖候选重排、恢复重复、fingerprint 稳定和去重幂等；
- 置信度决策表穷举关键条件；
- 范围守恒测试证明 partial 不会变 complete；
- 安全测试证明拒绝和最终文本无敏感原值。

主要覆盖 FR-005～FR-007、FR-014～FR-016、FR-018、FR-023～FR-028。

## 16. 设计决策与结论

选择纯确定性后处理而非二次模型裁决，避免额外预算、不确定调用和模型自证；选择语义 fingerprint 而非标题/行号哈希，使恢复和证据补充保持身份稳定；选择拒绝不可行动候选而非填充报告数量。

该模块是模型输出与用户结论之间的信任边界：只有可定位、可证明、在范围内且可行动的问题成为 FinalFinding，并与真实覆盖和 Trace 一起形成不可变 FindingSet。
