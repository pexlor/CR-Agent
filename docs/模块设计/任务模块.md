# Code Review Agent 任务管理模块详细设计

## 1. 文档状态

- 日期：2026-09-10
- 状态：已按复审意见修订，待用户复审
- 上游依据：《需求拆解.md》《验收清单.md》《架构设计.md》《Code Review Agent 技术选型设计》《Code Review Agent 系统架构设计》
- 适用范围：本地 CLI、单机 SQLite、同一任务单执行者

本文只设计任务管理模块及其公开契约。安全、预算、Trace、输入、审查规划、审查执行、报告和 SQLite 适配器的内部算法由各自模块详细设计负责；本文只固定它们与任务生命周期交互时必须遵守的边界。

## 2. 设计目标

任务管理模块必须保证：

1. `Task` 是任务生命周期的聚合根，只有任务管理模块可以改变任务状态；
2. 任务创建时固定影响审查语义的选择，恢复时不得静默切换输入、模型、规则或工具；
3. checkpoint、结果快照和执行尝试可独立保存、核对和恢复；
4. 同一任务同一时间只有一个执行者，失效执行者不能继续提交状态；
5. 执行状态、审查结果和报告交付状态互不覆盖；
6. 中断后复用所有已确认完成的工作，最多重做一个未完成工作单元；
7. 清理是原子、幂等且可观察的，并长期保留最小脱敏墓碑；
8. 任何未经过安全处理的代码、模型响应、工具结果、错误或凭证都不能进入任务存储。

## 3. 非目标

本模块不负责：

- 决定审查阶段的执行顺序；该职责属于审查编排模块；
- 计算 token 预留、结算或剩余额度；该职责属于预算模块；
- 生成审查工作单元；该职责属于审查规划模块；
- 选择模型、调用工具、验证发现或生成报告内容；
- 保存或解析第三方 SDK 对象；
- 提供后台调度、并行审查、分布式锁或跨主机执行；
- 自动恢复任务、自动重试不确定调用或自动追加预算；
- 删除 Markdown 报告文件；报告清理由独立的输出管理能力负责。

## 4. 已选方案与核心原则

采用“聚合根 + 版本化记录”的混合持久化方案：

- `Task` 保存当前权威状态、固定条件摘要、当前有效记录引用、聚合版本和租约状态；
- checkpoint、审查结果快照、执行尝试和报告交付尝试采用不可变或只追加记录；
- 每次状态变更使用 `expected_version` 做乐观并发控制；
- 每次执行写入同时校验租约标识和单调递增的 fencing token；
- 跨任务、预算、Trace 和调用状态的一致性由统一持久化工作单元原子提交；
- 不采用单一可变 JSON 快照，也不引入完整事件溯源。

## 5. 模块边界

### 5.1 模块拥有的数据

任务管理模块拥有：

- 任务身份和创建时间；
- 固定任务规格及其摘要；
- 固定输入版本引用；
- 执行控制状态和当前阶段；
- 聚合版本；
- 当前执行租约；
- 当前有效 checkpoint 引用；
- 最新审查结果快照引用；
- 当前报告交付状态及最新交付尝试引用；
- 暂停、终止和不可恢复原因；
- 恢复有效期与清理资格；
- 清理墓碑。

预算流水、Trace 内容、模型调用、工具调用、候选发现、最终发现、报告正文和外部平台响应由相应模块拥有。任务聚合只保存它们的稳定标识、状态摘要和关联引用。

### 5.2 唯一写入规则

其他模块不得直接更新任务记录。它们只能返回带稳定事件标识的 `TaskTransitionIntent`，内容包括：

- 唯一 `intent_id` 和安全内容摘要；
- 预期任务版本；
- 所属租约及 fencing token；
- 已完成动作和目标阶段；
- 建议的执行控制状态；
- 安全处理后的结果引用或错误摘要；
- 应创建的 checkpoint、结果快照或交付尝试引用；
- 需要参与同一事务的预算和 Trace 变更意图。

任务管理模块验证状态迁移和不变量后，通过统一持久化工作单元一次提交。无效、重复或过期的意图不得产生部分写入。

## 6. 领域模型

### 6.1 标识与时间

- `TaskId` 使用 UUIDv4 的规范小写字符串，不从仓库、用户、时间或输入内容推导；
- checkpoint、结果快照、执行尝试、租约和交付尝试均使用独立 UUIDv4；
- 聚合版本 `version` 是从 1 开始严格递增的整数；
- fencing token 是每次成功取得租约时递增的整数，永不复用；
- 领域时间统一使用带 UTC 时区的时间值；持久化格式由 SQLite 适配器确定，但往返后必须保持时序与精度；
- 所有过期判断使用注入的 `Clock`，不在领域逻辑中直接读取系统时间。

### 6.2 TaskSpec：任务固定规格

`TaskSpec` 在创建时产生，包含：

| 字段组 | 内容 | 变更规则 |
| --- | --- | --- |
| 输入意图 | 输入类型、规范化平台对象身份或独立 diff 摘要 | 创建后不可修改 |
| 模型选择 | Provider ID、Provider 版本、模型 ID、规范化 Provider origin、能力摘要 | 创建后不可修改 |
| 审查规则 | 规则集 ID、版本和内容摘要 | 创建后不可修改 |
| 工具声明 | 有序工具清单、各自版本和声明摘要 | 创建后不可修改 |
| 安全策略基线 | 创建时使用的策略 ID、版本和摘要 | 基线不可修改；后续操作可使用兼容且不弱于基线的新策略 |
| 配置快照 | 影响审查语义的配置摘要 | 创建后不可修改 |
| 凭证引用 | keyring 中逻辑引用，不含凭证值 | 引用不可修改，引用指向的值允许由可信用户轮换 |
| 预算账户 | 预算账户 ID、单位 `token` 和初始授权引用 | 总额度由预算账本版本化追加 |

任务创建前由组合入口完成 Provider、规则、工具和安全策略的存在性与基本能力校验。任务管理模块只接收规范化规格，不读取配置文件、keyring 或扩展注册表。安全策略基线用于审计和防止降级，不授权恢复任务继续使用已被撤销的旧策略；每个安全处理产物仍记录实际使用的策略版本。

### 6.3 InputBinding：固定输入版本

输入意图和输入版本分两步固定：

1. 创建任务时固定输入意图，例如规范化 PR/MR 身份或独立 diff 的安全摘要；
2. 输入获取并标准化成功后，仅允许写入一次 `InputBinding`（版本在 `input_acquired` 阶段固定，`InputBinding` 在 `input_normalized` 阶段落盘，见输入模块 §8）。

`InputBinding` 至少包含输入类型、稳定对象身份、base/head SHA 或独立 diff 内容摘要、完整性证明摘要和安全处理后的变更集引用。它只允许从“未绑定”变为“已绑定”，不能原地覆盖。重复提交相同绑定是幂等成功；提交不同绑定返回 `fixed_condition_mismatch`，原任务不得继续。

平台 URL 必须在进入任务模块前移除 userinfo、查询参数和 fragment。独立 diff 原文不保存在 `TaskSpec` 或 `InputBinding` 中。

### 6.4 Task 聚合

`Task` 的动态部分包含：

- `task_id`、`spec_id`、`input_binding_id`；
- `control_state`、`phase`；
- `latest_checkpoint_id`、`latest_result_snapshot_id`；
- `delivery_state`、`latest_delivery_attempt_id`；
- `pause_reason`、`terminal_reason`；
- `created_at`、`updated_at`、`last_checkpoint_at`；
- `recovery_expires_at`、`retention_expires_at`；
- `version`；
- 当前租约引用。

任务聚合不嵌入 diff、prompt、模型响应、工具输出、评论正文或报告正文。

### 6.5 正交状态

### 6.5.1 执行控制状态

| 状态 | 含义 |
| --- | --- |
| `ready` | 已创建、等待执行者取得租约的新任务；不表示"恢复校验已完成但未取租约"的中间态 |
| `running` | 已有审查执行者开始推进任务；进程崩溃后可暂时表现为租约已过期，直到显式恢复核对 |
| `paused` | 因可恢复条件、预算不足、显式中断或结果不明停止推进 |
| `terminated` | 审查流程已经不可逆结束，不再创建新的审查工作 |

### 6.5.2 当前阶段

`created → input_acquired → input_normalized → planned → reviewing → consolidating → result_finalized`

阶段表示已经原子确认的最远业务里程碑，只能前进，不能回退。阶段不能代替工作单元进度；恢复时由审查编排模块读取 checkpoint 和工作单元记录确定下一个动作。

### 6.5.3 审查结果快照状态

| 状态 | 含义 |
| --- | --- |
| `pending` | 任务尚无已交付的结果快照（`latest_result_snapshot_id` 为空时的派生取值，不是某条不可变快照的状态） |
| `no_changes` | 固定输入完整且没有可审查变更 |
| `complete_no_findings` | 审查范围完整完成，没有有效发现 |
| `complete_with_findings` | 审查范围完整完成，存在有效发现 |
| `partial` | 已保存有效结果，但覆盖范围不完整 |
| `failed` | 审查无法形成有效完成结果 |
| `unknown` | 存在结果不明的外部调用，无法确定当前结果是否完整 |

结果状态属于不可变的 `ResultSnapshot`。任务只引用最新快照；恢复后可以生成更高版本的快照，但不得改写旧快照。

### 6.5.4 报告交付状态

| 状态 | 含义 |
| --- | --- |
| `not_ready` | 没有可供报告模块读取的结果快照 |
| `pending` | 已有结果快照，等待或正在生成报告 |
| `succeeded` | 对应结果快照的报告已原子交付 |
| `failed` | 对应结果快照的报告交付失败，可单独重试 |
| `unknown` | 文件操作可能已经完成，但尚未核对最终产物 |

新结果快照成为当前快照时，交付状态重置为 `pending`，但旧交付记录仍保留。报告失败或结果不明不得更改执行控制状态或结果快照状态。

### 6.5.5 可恢复性

可恢复性是查询时的派生结果，不是可由调用方直接设置的状态：

- `recoverable`：控制状态为 `ready`、`paused`，或为 `running` 但租约已过期；同时任务未过期、固定条件有效且持久化完整；
- `blocked`：尚在有效期，但依赖、凭证、预算或用户授权条件不满足；
- `expired`：当前时间已超过恢复有效期；
- `not_applicable`：任务完整结束且没有待重试交付；
- `retry_pending`：任务已进入终态（审查不可恢复），但报告交付状态为 `pending`/`failed`/`unknown`，仍可单独重试报告生成与交付；
- `cleaned`：详细记录已清理，只剩墓碑。

只读查询不得因为时间经过而隐式更新任务。

## 7. 状态迁移

### 7.1 合法主迁移

| 动作 | 前置条件 | 状态变化 |
| --- | --- | --- |
| 创建 | 规格有效、任务不存在 | `ready / created / pending / not_ready` |
| 开始 | `ready`、无有效租约 | 取得租约，控制状态变为 `running` |
| 阶段完成 | `running`、租约和版本有效 | 原子创建 checkpoint，阶段单调前进 |
| 可恢复暂停 | `running` | `paused`，记录安全错误码和恢复动作，原子释放审查租约 |
| 结果不明暂停 | `running`、存在 unknown 尝试 | 禁止新外部调用，先确定性收敛已持久化候选与覆盖，再原子创建 `unknown` 结果快照、转为 `paused` 并释放审查租约 |
| 预算不足暂停 | `running`、预算模块拒绝新预留 | 禁止新外部调用，先确定性收敛已持久化候选与覆盖，再原子创建 `partial` 结果快照、转为 `paused` 并释放审查租约 |
| 不可恢复失败 | `ready`、`running` 或 `paused`，存在不可恢复原因 | 按 7.3 节确定结果快照和交付状态，控制状态变为 `terminated`，设置保留期并释放现有租约 |
| 预算异常冻结 | `running`、实际 usage 超过预留 | 先原子登记实际值和超出量、冻结账户并禁止新调用；随后确定性收敛已持久化候选与覆盖，再创建 `partial` 结果快照、转为 `paused` 并释放租约；足额追加、Provider 能力重新验证和显式恢复后可继续 |
| 审查完成 | `running` | 创建最终结果快照，阶段到 `result_finalized`，控制状态到 `terminated`，设置保留期并释放审查租约 |
| 恢复 | `paused`，或 `running` 且原租约已过期；恢复校验通过 | 取得更高 fencing token 的新租约并变为 `running`；执行新工作前核对中断状态 |
| 报告成功 | 有匹配当前结果版本和交付租约的尝试 | `delivery_state = succeeded`，释放报告租约 |
| 报告失败 | 有匹配当前结果版本和交付租约的尝试 | `delivery_state = failed`，不改审查结果并释放报告租约 |
| 报告结果不明 | 文件操作已开始但无法确认事务结果 | `delivery_state = unknown`，不改审查结果；租约过期后仅允许显式核对或重试 |
| 清理 | 已达到清理时间且无有效租约 | 原子删除详细记录并写入墓碑 |

以下迁移必须拒绝：

- 阶段回退；
- 改写已固定的输入、模型、规则、工具或安全策略；
- 无有效租约推进审查状态；
- 使用旧 fencing token 或旧聚合版本提交；
- 对已终止审查创建新的审查工作，报告交付重试除外；
- 在任务运行时追加预算或清理任务；
- 自动恢复 `unknown` 调用；
- 在保留期结束前清理 checkpoint 或完整 Trace。

### 7.2 暂停和终止原因

原因使用稳定错误码，不依赖第三方异常文本。至少包括：

- 可恢复暂停：`user_interrupted`、`temporary_input_failure`、`temporary_model_failure`、`temporary_tool_failure`、`credential_unavailable`、`budget_exhausted`、`budget_anomaly`、`external_result_unknown`、`lease_lost`；
- 不可恢复终止：`input_rejected`、`input_incomplete`、`fixed_condition_mismatch`、`capability_incompatible`、`security_boundary_failed`、`persistence_integrity_failed`、`recovery_expired`；
- 报告交付失败独立记录为交付错误，不作为任务终止原因。

`fixed_condition_mismatch` 是终止原因：当恢复期间输入、规则、工具、模型或安全策略等固定条件必须变化时，原任务以 `fixed_condition_mismatch`（或等价能力原因）进入不可恢复终止并释放租约，同时向用户返回 `new_task_required` 作为下一步指令，提示创建新任务。`new_task_required` 是给调用方的响应语义，不是任务自己的终止原因；两者配合使用，不重复计数。

`budget_anomaly` 冻结预算账户并暂停原任务。只有本机可信用户追加预算，使授权覆盖当前已知实际、不确定消耗和活动预留，显式恢复，并在不改变固定 Provider、模型和 origin 的前提下重新通过硬预算能力验证，才能解除冻结。下一次模型请求形成后仍须独立通过调用前预留门禁；余额不足时按普通 `budget_exhausted` 再次暂停。若必须改变固定条件才能通过验证，则返回 `new_task_required`。`security_boundary_failed` 和 `persistence_integrity_failed` 不允许在原任务上继续产生外部调用。

### 7.3 不可恢复失败的收敛规则

不可恢复失败必须明确收敛执行状态、结果状态、交付状态和租约：

- 输入尚未固定且没有可安全交付结果时，任务进入 `terminated`，不创建结果快照，交付状态保持 `not_ready`；
- 已有可安全复用的审查结果时，创建 `partial` 快照并把交付状态置为 `pending`；
- 计划创建前发生不可恢复失败时，不创建 ResultSnapshot，交付状态保持 `not_ready`；错误通过任务状态和安全 Trace 展示；
- 计划已经冻结但无法形成有效审查结果时，仍须先生成零发现的 FindingSet、真实 CoverageSnapshot、UnknownAttemptSet、BudgetSummary 和 TraceSummary，随后才可创建 `failed` 快照并把交付状态置为 `pending`；
- `budget_anomaly` 不属于不可恢复失败；其调用完成事务只登记实际消耗、超出量、账户冻结、执行结果和收敛要求。发现处理模块随后在不进行外部调用的前提下生成 FindingSet，再创建披露异常的 `partial` 快照并暂停任务。冻结期间允许已收敛快照的报告交付和预算追加，但禁止新模型调用；解除冻结必须遵循预算模块的显式恢复契约；
- 任何进入 `terminated` 的成功事务都设置统一保留期并释放当前租约；
- 持久化错误仅在数据库仍可安全写入时提交终止状态；若终止事务本身失败，执行者立即停止外部调用，保留原数据并返回持久化错误，不得声称任务已可靠终止。

不可恢复失败不把阶段伪装为 `result_finalized`。阶段保留在最后一个已确认业务里程碑，终止原因和结果快照共同说明完成情况。

## 8. 执行租约与并发控制

### 8.1 租约模型

每个任务最多有一条当前租约：

- `lease_id`：本次租约标识；
- `owner_id`：当前 CLI 进程生成的非敏感随机标识；
- `fencing_token`：取得租约时递增；
- `acquired_at`、`heartbeat_at`、`expires_at`、`released_at`；
- 独立递增的 `lease_revision`；
- `purpose`：`review_execution` 或 `report_delivery`。

默认租约时长为 120 秒，持有者每 30 秒续约。两个值属于本机运行参数，不改变审查语义，因此不写入固定任务规格；必须满足续约间隔小于租约时长的一半。

### 8.2 取得与续约

取得租约使用单个数据库事务和条件更新：

1. 读取任务、聚合版本和当前租约；
2. 若存在未过期租约，返回 `task_already_running`；
3. 普通 `AcquireExecution`（审查执行用途）只允许控制状态为 `ready` 的任务取得执行租约，即新任务首次开始；对 `paused` 任务，或 `running` 但原租约已过期的任务，普通取得租约返回 `resume_required`，必须先通过 `PrepareResume` 完成固定条件、预算解冻和 unknown 重试确认校验后再接管；
4. 若报告租约已过期，仅允许用户发起的显式报告重试接管；
5. 递增 fencing token、写入新租约并更新聚合版本；
6. 返回完整的 `ExecutionPermit`。

续约只匹配当前 `lease_id + fencing_token`，并仅更新 `task_leases` 的 `heartbeat_at`、`expires_at` 和独立 `lease_revision`。心跳不是业务状态迁移，不更新任务聚合版本、`updated_at` 或恢复有效期；租约取得、接管、释放和用途转换仍属于业务写入，必须更新聚合版本。

续约失败后，执行者必须停止发起新的外部调用；正在进行的调用返回后也不能直接提交结果，只能让恢复流程按已持久化调用状态处理。

释放租约时保留历史租约记录和任务最后使用的 fencing token，只清空任务的当前租约引用并写入 `released_at`。后续取得租约必须在最后 token 基础上递增，不能因释放或清理当前引用而复用旧 token。

### 8.3 防止失效执行者写入

所有推进任务的写事务都必须携带：

- `task_id`；
- `expected_version`；
- `lease_id`；
- `fencing_token`。

任一值不匹配即返回并发冲突，不应用任何变更。这样即使旧进程在租约过期后恢复运行，也不能覆盖新执行者的状态。

`expected_version` 约束任务聚合的业务变更，不随租约心跳变化。执行者在每次成功业务提交后使用返回的新版本更新 `ExecutionPermit`；不得自行猜测或递增版本。

状态查询不需要租约。预算追加只允许在 `ready` 或 `paused` 状态执行；运行中追加返回 `task_running`，避免运行时改变预算授权边界。报告交付可以在任务暂停或审查已终止后使用用途为 `report_delivery` 的租约执行；取得报告租约前不得存在任何用途的有效租约。

### 8.4 进程异常退出

进程正常收到中断时，尽力在事务中把任务置为 `paused` 并释放租约。审查完成、可恢复暂停、不可恢复终止和报告交付完成也必须在各自状态事务中释放对应租约，不能依赖租约自然过期后再继续下一阶段。

进程崩溃或机器关机时不依赖清理逻辑：租约自然过期，任务查询显示“运行记录存在但租约已过期”。用户显式恢复可以从 `running + expired lease` 取得更高 fencing token；在发起任何新外部调用前，必须核对中断状态，将未完成外部尝试收敛为 `unknown`，并按第 12.2 节处理。

## 9. 工作单元、执行尝试与 Checkpoint

### 9.1 三者区别

- 工作单元：审查规划模块生成的稳定待办事项；
- 执行尝试：对某个工作单元或外部调用的一次实际执行；本节的 `pending/running/succeeded/failed/unknown` 是任务模块用于恢复判断的最小外部生命周期抽象，`work_item_attempts` 只保存该抽象状态用于恢复决策，不重复记录审查执行模块拥有的详细状态。审查执行模块对 `WorkUnitExecution`（含 `partial`）、`ToolAttempt`（含 `blocked/interrupted`）和 `ModelCallAttempt.provider_state/response_state` 双轴拥有唯一权威定义和状态迁移权，并按下表映射到本节抽象状态：

  | 详细状态来源 | 映射到 `work_item_attempts` 抽象状态 |
  | --- | --- |
  | `WorkUnitExecution: pending` | `pending` |
  | `WorkUnitExecution: running` | `running` |
  | `WorkUnitExecution: succeeded` | `succeeded` |
  | `WorkUnitExecution: partial` | `failed`（覆盖降级信息保留在执行模块，任务模块只记录“未完全成功”） |
  | `WorkUnitExecution: failed` | `failed` |
  | `WorkUnitExecution: unknown` / `ModelCallAttempt.provider_state=unknown` | `unknown` |
  | `ToolAttempt: blocked/interrupted` | `failed` |
  | `ToolAttempt: failed_known` | `failed` |

  任务模块不得在 `work_item_attempts` 中另行推进或覆盖这些详细状态；恢复决策读取执行模块的详细状态源，仅用上表结果驱动第 9.4 节的重做规则；
- checkpoint：一次跨模块事务成功提交后的不可变一致性边界。

Checkpoint 不是任意进度日志，也不保存可变对象副本。它证明某组状态已经共同提交，并引用相应的工作单元、尝试、预算、Trace 和安全处理后产物。

### 9.2 Checkpoint 结构

每条 checkpoint 至少包含：

- `checkpoint_id`、`task_id`、单调递增 `sequence`；
- `kind`、`phase`、`scope_type`、`scope_id`；
- 前一 checkpoint 标识；
- 关联工作单元及尝试标识；
- 安全处理后产物引用与摘要；
- 关联预算账本版本和 Trace 事件范围；
- 创建时间、统一过期时间；
- 创建后的任务聚合版本。

Checkpoint 正文只保存安全包装类型或其引用。`SanitizedArtifactRef` 必须带安全策略版本、内容摘要和安全处理结果；缺少安全凭据的 payload 不能进入事务。

### 9.3 Checkpoint 类型

至少支持：

- `input_acquired`；
- `input_normalized`；
- `plan_created`；
- `review_unit_completed`；
- `tool_attempt_completed`；
- `model_attempt_completed`；
- `unknown_attempt_reconciled`；
- `findings_consolidated`；
- `result_snapshot_created`；
- `report_generated`：报告模型已从结果快照生成并安全固化，尚未完成文件交付的一致性边界；
- `report_delivery_completed`；
- `report_delivery_reconciled`。

模型调用准备、开始和完成事务的具体结构由审查执行、预算和 Trace 模块共同细化，但任务管理必须在同一工作单元中更新对应尝试、checkpoint 和任务引用。

### 9.4 中断后的重做上限

恢复时：

- 已有完成 checkpoint 的工作单元直接复用；
- 尚未开始的工作单元正常执行；
- 本地确定性工作在没有完成 checkpoint 时可重做当前单元；
- 已明确失败的外部尝试可以按策略创建新尝试；
- `running` 且没有完成事务的模型调用转为 `unknown`，不得自动重试；
- 同一恢复过程最多重做一个没有完成 checkpoint 的工作单元。

## 10. 结果快照与报告交付

### 10.1 ResultSnapshot

结果快照不可变并按任务内版本递增。所有派生产物引用统一包含对象类型、稳定 ID、版本、task ID、schema 版本、内容摘要和安全证明引用。快照至少包含：

- `snapshot_id`、`task_id`、`snapshot_version`；
- 结果状态；
- InputBinding 引用和必需的 ReviewPlan 引用；计划创建前的终止不创建 ResultSnapshot；
- CoverageSnapshot 引用，覆盖已审查、未审查、不可审查和 unknown 范围；
- FindingSet 引用及最终发现数量；
- BudgetSummary 引用；
- UnknownAttemptSet 引用；
- TraceSummary 引用；
- 生成该快照的 checkpoint；
- 创建时间和安全策略凭据。

暂停任务可以拥有 `partial` 或 `unknown` 快照并生成报告。快照必须在 CandidateFinding 完成确定性收敛、FindingSet 和逐发现 TraceLink 已提交后创建；调用/预算停止事务不得直接把候选写入快照。恢复成功后创建新快照，旧快照及其交付记录保持不变。

### 10.1.1 快照派生产物所有权与冻结

- `CoverageSnapshot` 与 `FindingSet` 由发现处理模块根据冻结计划和权威执行事实生成；CoverageSnapshot 是详细覆盖范围的唯一事实源，FindingSet 只固定其不可变引用；即使零发现，也必须生成显式空 FindingSet；
- `BudgetSummary` 由预算模块针对确切账本版本生成；
- `UnknownAttemptSet` 由审查编排模块根据权威输入、工具、模型和交付尝试状态生成，空集合也必须有稳定版本和摘要；
- `TraceSummary` 由 Trace 模块根据确切事件序列边界生成，包含任务级 Trace、逐发现 TraceLink 集合和完整性结果；
- 各拥有模块只产生不可变对象及持久化意图，不能自行创建 ResultSnapshot 或修改任务状态；
- 任务管理模块通过统一持久化工作单元核对对象类型、稳定 ID、版本、task ID、schema、摘要和安全证明，并与 ResultSnapshot 在同一事务冻结；
- 报告模块只能按快照引用读取，不能查询各模块的“最新”投影补齐缺失对象。

### 10.2 DeliveryAttempt

每次报告交付尝试绑定确切的 `snapshot_id`，至少包含：

- `delivery_attempt_id`、`task_id`、`snapshot_id`；
- 输出适配器 ID 和版本；
- 确定性的 `delivery_key` 和目标产物标识；
- 期望报告内容摘要；
- `pending/running/succeeded/failed/unknown` 状态；
- 安全错误码、实际产物摘要或核对结果；
- 开始、完成时间。

MVP Markdown 的目标产物由任务 ID 唯一确定，同一任务的新快照始终原子替换同一路径，不创建第二份报告。`delivery_key` 由任务、确切快照、输出适配器 ID/版本、规范化目标产物标识和期望内容摘要稳定派生；同一快照、相同报告内容的重试必须得到相同键，不同快照或不同内容必须得到不同键。任务级目标路径约束独立于快照级交付尝试幂等键。

报告写入前先把尝试置为 `running`。如果进程在文件操作开始后、交付终态提交前退出，恢复时把该尝试视为 `unknown`，不得假定文件不存在或写入成功。恢复流程先通过 Output Adapter 核对规范化目标、任务 ID、快照 ID 和安全内容摘要：

- 最终文件与当前快照及期望摘要一致时，原子补记成功，不再次写入；
- 只存在未完成临时文件时，安全删除临时文件后才允许重试；
- 最终文件属于同一任务的旧快照时，显式重试可以原子替换为当前快照；
- 产物身份或内容无法安全核对时，保持 `unknown` 并返回需要用户处理的错误，不创建另一路径的重复报告。

只有当前快照对应的成功尝试才能把任务的 `delivery_state` 置为 `succeeded`。旧快照的迟到结果不能覆盖新快照状态。报告文件采用临时文件完整写入后原子替换；该文件操作由 Output Adapter 负责。

## 11. 应用用例与公开契约

### 11.1 CreateTask

输入：规范化 `TaskSpec`、初始预算授权结果、调用者生成的 `request_id`。

行为：先计算规范化规格与初始预算授权的安全请求指纹，再按 `request_id` 查询创建记录：

- 请求标识不存在时，生成任务身份，并在单一事务中保存请求标识、请求指纹、任务、固定规格、预算账户引用和创建 Trace 事件；
- 请求标识已存在且指纹相同、且 `task_requests.purged` 为空时，返回原任务或对应墓碑视图和原始创建结果，不重复创建预算账户或 Trace 事件；
- 请求标识已存在但指纹不同时，返回 `request_id_conflict`；
- 请求标识已存在且 `task_requests.purged=true` 时，返回 `task_purged`，不创建新任务，也不复用原 `task_id`。

创建记录不得保存原始 diff、凭证值或其他未安全处理内容。

输出：`TaskView` 和初始聚合版本。

### 11.2 GetTaskStatus

输入：`task_id`。当前时间必须由内部 `Clock` 端口取得，不接受调用方提供的时间。

行为：读取任务或墓碑，组合执行、阶段、结果、交付、租约、预算摘要和派生可恢复性。只读，不续期、不改状态。

输出必须区分：可用、运行中、运行但租约已过期、暂停、审查结果不明、报告交付结果不明、已终止、已过期、清理失败、已清理和不存在。

### 11.3 AcquireExecution

输入：`task_id`、用途、预期版本、进程 owner ID。

行为：校验控制状态和租约，原子取得租约并返回 `ExecutionPermit`。审查执行用途只允许 `ready` 状态的新任务首次取得租约；`paused` 或 `running + 过期租约` 的审查接管返回 `resume_required`，必须先通过 `PrepareResume`（见 11.5）完成恢复校验。报告交付用途只允许在任务暂停或审查已终止后、无任何有效租约时取得。

### 11.4 ApplyTransition

输入：`TaskTransitionIntent` 和 `ExecutionPermit`。

行为：验证迁移、版本、安全包装、关联记录和事务不变量，然后通过统一工作单元提交。

重复提交同一个 `intent_id` 且安全内容摘要一致时返回原结果，不重复创建关联记录；标识相同但内容不同视为完整性错误。

### 11.5 PrepareResume

输入：`ResumeCommand`，包含 `task_id`、`expected_task_version`、类型化本机可信用户操作凭据、`request_id`、安全请求指纹、用户显式恢复标记和可选 unknown 重试确认。

依次校验：

1. 任务存在且未清理；
2. 任务控制状态必须为 `ready`、`paused`，或 `running` 且原租约已过期；不得为 `terminated`（含 `retry_pending`/`not_applicable` 等终态任务，它们只能重试报告交付，不能恢复审查执行）；
3. 当前没有有效租约；`running` 任务仅在原租约已过期时允许继续校验；
4. 未超过恢复有效期；
5. 输入绑定、Provider ID/版本/origin、模型、规则、工具和配置摘要一致，当前安全策略通过兼容性及非降级校验；
6. 持久化引用及摘要完整；
7. 预算账本可继续累计；存在预算异常冻结时，授权必须覆盖当前已知实际、不确定消耗和活动预留，并取得新的 Provider 硬预算能力验证证据；下一次调用仍须在最终请求形成后独立通过预留门禁；
8. 当前阻塞原因已经消除；
9. unknown 调用重试已获得显式确认。

先按 `request_id + 请求指纹` 核对幂等结果，并以预期版本和内部 Clock 原子证明当前无有效租约。校验通过后，若预算账户处于 `frozen_overage`，任务模块必须调用 `BudgetPolicyPort.evaluate_unfreeze`；只有返回与固定 Provider ID、版本、模型和 origin 完全一致的 `UnfreezeBudgetIntent` 时，才能通过同一 `PersistenceUnitOfWork` 原子提交 `freeze_cleared` 账本与账户状态、任务恢复许可、Trace 事件和更高 fencing token 的新执行租约。解冻被拒绝时不得取得执行租约。未冻结任务直接原子提交恢复许可、Trace 和新租约。对于 `running + expired lease`，上下文必须标明需要先核对未完成尝试；完成核对前不得发起新外部调用。任务管理模块不决定具体从哪个工作单元开始，该决定由审查编排模块根据上下文作出。

### 11.6 TerminateReview

输入：`TerminateCommand`，包含 `task_id`、`expected_task_version`、类型化本机可信用户操作凭据、`request_id`、安全请求指纹和稳定终止原因。

前置条件：任务尚未清理，且当前没有有效租约；`running` 任务先由编排在安全停止边界完成当前事务并释放租约后，才能提交终止意图。

行为：先按 `request_id + 请求指纹` 核对幂等结果。终止是协作式控制，不强杀进程、不取消进行中事务、不篡改已发生事实。任务管理模块按 7.3 节收敛规则确定结果快照与交付状态（已有可安全复用结果时创建 `partial` 快照并置 `pending`，否则保持 `not_ready`），把控制状态置为 `terminated`、记录终止原因、设置统一保留期并释放现有租约，通过统一工作单元原子提交。终止后审查不再创建新工作，但报告仍可独立交付；`terminated` 任务的 `pending/failed/unknown` 交付可通过 `RetryReportDelivery` 重试。

### 11.7 AddBudget

输入：`AddBudgetCommand`，包含 `task_id`、正整数 token 增量、`expected_task_version`、类型化本机可信用户操作凭据、`request_id`、安全请求指纹和用户显式操作标记。

前置条件：任务为 `ready` 或 `paused`，未过期，未清理，没有任何有效租约，且不是不可恢复终止状态。`budget_anomaly` 暂停任务允许追加预算，但追加本身不自动解除冻结或恢复执行。

行为：先按 `request_id + 请求指纹` 核对幂等结果，再调用预算模块产生追加授权意图，并通过统一工作单元条件检查预期版本和无有效租约，写入预算流水、任务聚合版本和 Trace 事件。累计实际消耗、活动预留、超额和 unknown 消耗均不清零。预算异常任务须另行执行显式恢复，并以 TaskSpec 固定的 Provider ID、版本、模型和 origin 重新验证能力。

### 11.8 RetryReportDelivery

输入：`RetryReportCommand`，包含 `task_id`、`expected_task_version`、类型化本机可信用户操作凭据、`request_id`、安全请求指纹和用户显式重试标记。

前置条件：存在当前结果快照，当前交付状态为 `pending`、`failed` 或 `unknown`，且没有任何用途的有效租约。

行为：先按 `request_id + 请求指纹` 核对幂等结果，并以预期版本原子证明没有任何有效租约，再取得 `report_delivery` 租约。随后按当前 `snapshot_id + expected_content_digest` 派生的 `delivery_key` 核对已有的 `running`、`pending` 或 `unknown` 尝试及目标文件。已有文件可证明交付成功时只补记成功；需要重写时才创建当前快照的新交付尝试，并原子替换同一任务路径。旧快照的尝试只能用于识别和替换旧产物，不能阻止当前快照创建尝试或推进当前交付状态。不得重新执行审查、改变结果快照或创建第二个报告路径。

### 11.9 CleanupTask

输入：`task_id`、`expected_task_version`、类型化本机可信用户操作凭据、`request_id` 和安全请求指纹。当前时间必须由内部 `Clock` 端口取得，不接受调用方提供的时间。

前置条件：没有有效租约，且未结束任务的恢复期已过，或终态任务的保留期已过。

行为：先按 `request_id + 请求指纹` 执行幂等校验，再用内部可信时间、预期版本和条件查询原子证明当前无有效租约及已达到清理资格；随后在单一数据库事务中删除 checkpoint、调用、预算流水、Trace 和中间状态，写入墓碑。用于创建幂等的 `task_requests` 身份记录随墓碑保留，报告文件不删除。重复相同清理请求或清理墓碑任务返回原成功结果且不产生额外副作用；同一请求标识携带不同指纹时返回冲突。

### 11.10 PurgeTombstone

输入：`PurgeTombstoneCommand`，包含 `task_id`、`expected_tombstone_version`、类型化本机可信用户操作凭据、`request_id`、安全请求指纹，以及与任务 ID 完全匹配的显式确认。

行为：先按 `request_id + 请求指纹` 核对幂等结果；相同请求返回原结果，同一请求标识携带不同指纹时返回冲突。随后在单一工作单元中校验可信操作、墓碑存在、预期墓碑版本、任务详细记录已经清理且确认值匹配，再条件删除墓碑正文及关联安全/Trace/发现明细，但保留 `task_requests` 中 `request_id -> task_id` 的最小映射记录及一个永久性 `purged` 标记，使原始 `CreateTask` 请求重放时返回 `task_purged`（而非重新创建任务），并保存不含任务内容的最小 purge 审计事实。该操作不可恢复，不删除报告文件；任一条件不满足时不产生部分删除。

## 12. 恢复规则

### 12.1 固定条件

恢复期间：

- 平台输入必须仍指向任务已绑定的 base/head SHA；
- 独立 diff 必须匹配固定摘要；
- Provider、Provider 版本、规范化 origin、模型、规则集、工具声明和影响审查语义的配置必须匹配；
- 当前安全策略必须与任务基线兼容且不弱于基线；策略升级后，相关持久化安全产物必须按新策略重新校验，无法安全复用时暂停或形成部分结果；
- 凭证引用保持不变，但可信用户可轮换其值；新凭证只影响尚未发起的外部请求；
- 输出适配器版本变化不能改写旧交付记录；重试时创建新交付尝试并记录实际版本。

输入、模型/Provider、规则或工具版本变化返回 `new_task_required`。凭证暂不可用返回可恢复阻塞。访问权限变化导致上下文不足时，由编排和结果模块形成部分结果，不把旧证据与新条件拼成完整结果。

### 12.2 结果不明

恢复核对发现外部调用处于 `running` 且没有完成事务时：

1. 原尝试转为 `unknown`；
2. 对应预留量按预算模块规则计入不确定消耗；
3. 原子创建核对 checkpoint、Trace 事件和“需要确定性收敛”的意图，禁止新的外部调用；
4. 发现处理模块基于已持久化候选、冻结计划和执行事实生成 CoverageSnapshot、FindingSet 与逐发现 TraceLink；预算、编排和 Trace 模块分别生成固定版本的 BudgetSummary、UnknownAttemptSet 与 TraceSummary；
5. 任务管理模块核对全部不可变引用后，在统一事务创建 `unknown` 快照；如果本次恢复没有携带重试确认，则同时把任务转为 `paused` 并释放核对租约；
6. 只有本次恢复已携带显式确认且预算允许时，任务才能在收敛与快照事务成功后保持 `running` 并创建新的 WorkUnitExecution 和 ModelCallAttempt。

新尝试具有新标识、新预算预留和新 Trace，不覆盖原尝试。

### 12.3 报告交付结果不明

恢复发现交付尝试为 `running`，但不存在对应的完成事务时，将尝试和任务交付状态标记为 `unknown`。显式报告重试取得新 fencing token 后，必须先按第 10.2 节核对确定性目标文件；核对成功只补记交付成功，核对失败才允许对同一路径进行原子重写。

报告核对和重写不得改变任务执行控制状态、审查结果快照或预算账本，也不得产生第二个报告路径。

### 12.4 创建后尚无业务 Checkpoint

任务创建记录本身是持久化恢复根，但不冒充输入完成 checkpoint。输入获取前发生临时失败时，可以从 `created` 阶段恢复；其恢复有效期以任务最近一次合法状态更新时间为基准。输入获取成功后，恢复有效期改由最近有效 checkpoint 驱动。

## 13. 保留、过期与清理

### 13.1 时间规则

- 未结束任务：`recovery_expires_at = latest_checkpoint_at + 7 天`；尚无业务 checkpoint 时使用最近一次合法任务状态更新时间；
- 任务每次创建有效 checkpoint 后更新恢复有效期；普通状态查询和租约心跳不延长恢复期；
- 任务进入终态时设置统一 `retention_expires_at = terminated_at + 7 天`，供 checkpoint 和完整 Trace 共同使用；
- 7 天按连续 168 小时计算，所有判断使用 UTC；
- 到期只改变派生可恢复性，不在读取时修改数据。

### 13.2 清理事务

清理操作先创建或读取 `CleanupAttempt`。核心删除事务必须做到全有或全无，按 `retention_group_id` 删除该任务在基础设施 schema 中定义的全部任务级详细集合（至少含 checkpoint、work item attempt、执行/工具/模型调用、候选发现、`coverage_snapshots`/`coverage_snapshot_scopes`、`finding_sets`/`findings`/`finding_sources`、预算流水与冻结记录、Trace 事件/边/链接、`security_attestations`/`sanitized_artifacts`/`artifact_provenance`/`security_events`、输入产物与完整性证明），不得遗留任一集合：

1. 再次校验任务版本、租约和清理资格；
2. 写入最小墓碑；
3. 按 `retention_group_id` 删除全部任务级详细集合（含安全证明、Trace、发现与覆盖快照、执行与工具/模型调用、输入产物）；
4. 删除任务聚合与固定规格；
5. 提交清理结果。

事务失败必须回滚全部删除。随后使用独立的安全运维记录保存 `cleanup_failed`；如果数据库本身不可写，CLI 返回持久化错误且不得声称已经清理。

### 13.3 墓碑

墓碑仅包含：

- `task_id`；
- 创建 `request_id` 和安全请求指纹；
- 最终执行状态和结果状态；
- 最终安全状态摘要（如 `safe`/`blocked`/`indeterminate` 相关终止原因）及最后使用策略 ID/版本/摘要（不含命中类别明细）；
- 任务结束时间、原过期时间和清理时间；
- 报告产物标识及安全规范化路径；
- 最近清理结果。

墓碑默认长期保留，用于区分“已清理”和“从不存在”，并避免任务身份被误解为可复用。只有 `PurgeTombstone` 可以显式删除墓碑。

## 14. 持久化逻辑结构

SQLite 适配器至少需要实现以下逻辑集合，物理表拆分可在基础设施详细设计中调整：

| 集合 | 写入模式 | 关键约束 |
| --- | --- | --- |
| `task_requests` | 创建后只读，随墓碑保留 | `request_id` 唯一；映射固定 `task_id` 和请求指纹；`PurgeTombstone` 时保留 `request_id -> task_id` 映射并置 `purged=true`，不删除该行 |
| `tasks` | 条件更新 | `task_id` 唯一，`version` 乐观锁 |
| `task_specs` | 创建后只读 | 固定摘要不可覆盖 |
| `input_bindings` | 一次绑定 | 同任务至多一个有效绑定 |
| `task_leases` | 条件更新 | 同任务一个当前租约，fencing token 单调递增；心跳只递增独立 `lease_revision` |
| `work_item_attempts` | 只追加尝试、状态受控迁移 | 尝试标识唯一 |
| `checkpoints` | 只追加 | `(task_id, sequence)` 唯一，前驱链一致 |
| `result_snapshots` | 只追加 | `(task_id, snapshot_version)` 唯一 |
| `delivery_attempts` | 只追加尝试、状态受控迁移 | 必须绑定结果快照、稳定 `delivery_key` 和期望内容摘要 |
| `cleanup_attempts` | 版本化 | 可区分开始、失败和成功 |
| `task_tombstones` | 默认只创建 | `task_id` 唯一 |

预算、Trace、调用和发现相关集合由对应模块定义，但必须能加入同一个 SQLite 事务。所有外键启用，正常运行禁止依靠孤儿记录恢复关系。

## 15. 端口

任务管理核心依赖以下抽象端口：

- `TaskRepository`：读取创建请求记录、聚合、固定规格、租约、快照、交付尝试和墓碑；
- `PersistenceUnitOfWork`：原子提交任务、预算、Trace、调用和 checkpoint 变更；
- `Clock`：提供可测试的 UTC 时间；
- `IdGenerator`：生成不可预测且不复用的标识；
- `BudgetPolicyPort`：验证初始预算、追加预算和冻结解除条件；
- `ResumeConditionPort`：获取已安装 Provider、规则、工具和配置的当前非敏感摘要；
- `SecurityLogPort`：记录结构化、已脱敏的任务管理事件。

任务管理模块不依赖 SQLite、keyring、Typer、Rich、LangChain、平台 SDK、HTTPX、Jinja2 或具体安全扫描器。

## 16. 错误模型

公开错误统一包含：

- 稳定 `code`；
- 发生阶段；
- 影响范围；
- `recoverable` 标记；
- 用户可执行的下一步；
- 安全处理后的关联标识。

不得包含原始异常栈、凭证、未脱敏 URL、代码、prompt、模型回复或工具输出。

主要错误码包括：

- `task_not_found`、`task_cleaned`、`task_expired`；
- `task_already_running`、`lease_lost`、`version_conflict`；
- `illegal_state_transition`、`fixed_condition_mismatch`、`new_task_required`；
- `request_id_conflict`、`task_purged`；
- `resume_condition_blocked`、`unknown_retry_confirmation_required`；
- `budget_update_rejected`、`task_running`；
- `delivery_result_unknown`、`delivery_artifact_mismatch`；
- `checkpoint_integrity_error`、`persistence_integrity_error`；
- `cleanup_not_due`、`cleanup_failed`、`purge_confirmation_mismatch`。

领域冲突和业务拒绝是预期结果，不记录无关调用栈。持久化完整性错误必须停止新的外部调用。

## 17. 安全约束

1. 任务模块只接受经过安全模块处理的 payload 或 `SanitizedArtifactRef`；
2. 原始 diff、源码、模型响应和工具输出不进入任务聚合、checkpoint 或错误信息；
3. 凭证只保存逻辑引用，禁止保存 keyring 值、环境变量值或认证头；
4. 平台 URL 必须先移除 userinfo、query 和 fragment，再形成输入身份；
5. 第三方异常必须在适配器边界映射成白名单字段；
6. 仓库内容不能构造任务命令、追加预算、改变固定规格、触发恢复、取得租约或清理数据；
7. 安全扫描器不可用或处理结果不确定时，不得创建包含相关 payload 的 checkpoint；
8. 墓碑和状态查询只暴露本机可信用户所需的最小信息。

## 18. 关键不变量

实现和测试必须持续证明：

1. 一个任务只有一个身份、一个固定规格和至多一个固定输入绑定；
2. 任务状态只能通过任务管理模块改变；
3. 聚合版本每次成功的业务状态变更严格递增；租约心跳只递增独立 `lease_revision`；
4. 同一任务同一时刻最多一个有效执行租约；
5. 旧 fencing token 永远不能提交新状态；
6. 阶段只前进，不回退；
7. checkpoint 序号严格递增且前驱链不分叉；
8. 已完成工作单元不会因恢复而重复执行；
9. unknown 外部调用不会自动重试；
10. 新结果快照不改写旧快照，交付尝试必须绑定具体快照；
11. 报告交付失败不改变审查结果；
12. 追加预算不清零或重写历史预算流水；
13. 预算异常只暂停任务并冻结预算账户，不进入终态；冻结期间禁止新模型调用；
14. 预算异常只有在授权覆盖已有承诺、显式恢复和 Provider 硬预算能力重新验证后才能解除；下一调用仍须独立通过预留门禁；
15. 未达到统一保留期限不得清理 checkpoint 或完整 Trace；
16. 清理要么完整成功并留下墓碑，要么保留全部原数据；
17. 所有持久化业务 payload 均具有安全处理凭据；
18. 相同 `request_id` 和请求指纹只创建一个任务；同标识不同指纹必须冲突；
19. 同一任务的本地报告始终使用同一规范化目标，交付结果不明时先核对再重写。

## 19. 测试设计

### 19.1 领域单元测试

- 覆盖每个合法和非法状态迁移；
- 使用 Hypothesis 生成命令序列，证明阶段单调、终态不可重新审查和版本严格递增；
- 验证结果状态、执行控制状态和交付状态互不覆盖；
- 验证重复 checkpoint、快照和转换意图的幂等行为；
- 验证 `CreateTask` 在提交后丢失响应并以相同请求标识重试时返回原任务，不重复创建预算或 Trace；
- 验证任务清理后重放相同创建请求返回原任务的墓碑视图，不创建新任务；
- 验证 `PurgeTombstone` 后重放原创建请求返回 `task_purged`，不创建新任务，也不复用原 `task_id`；
- 验证相同请求标识携带不同请求指纹时返回冲突；
- 使用 fake clock 覆盖恢复期、保留期和边界时刻。

### 19.2 租约与并发测试

- 两个 SQLite 连接同时取得同一任务租约，必须恰好一个成功；
- 有效租约阻止第二执行者；
- 只有显式恢复可以接管过期租约；
- `running` 任务在租约过期后可由显式恢复接管；
- 旧执行者使用旧 fencing token 写入时被拒绝；
- 心跳失败后不再发起外部调用；
- 心跳续约不改变任务聚合版本，业务提交不会因自身心跳产生版本冲突；
- 暂停、终止和交付完成原子释放各自租约；
- 审查租约和报告交付租约不会互相错误覆盖。

### 19.3 恢复与故障注入

在以下边界模拟进程退出和事务失败：

- 任务创建前后；
- 输入获取与固定前后；
- 工作单元置为 running 后、checkpoint 前；
- 模型调用开始标记后、完成事务前；
- checkpoint 和任务引用共同提交时；
- 结果快照创建时；
- 报告文件写入后、交付状态提交前；
- 清理事务中途。

验证已完成单元被复用、最多重做一个未完成单元、unknown 不自动重试、预算与 Trace 不失配、清理不会留下残缺集合。报告文件写入后中断的样例必须证明恢复会先核对同一路径及内容摘要，已成功交付的报告不重复写入，旧快照报告只被当前快照原子替换。

另覆盖预算模块返回实际 usage 超过预留的样例，证明原任务进入 `paused`、预算账户冻结、已有结果进入 `partial` 快照且报告仍可独立交付；不足额追加、未显式恢复或 Provider 能力重新验证失败时继续拒绝新调用，三项条件全部满足后同一任务可以恢复，历史流水不得清零。

### 19.4 持久化合约测试

所有持久化适配器必须通过共享合约：

- expected version 条件更新；
- 任务创建请求标识唯一及重放幂等；
- 租约和 fencing 校验；
- checkpoint 只追加和链完整；
- 跨模块工作单元全有或全无；
- 清理幂等及回滚；
- 清理保留创建请求身份映射，显式清除墓碑时与映射共同删除；
- 外键和唯一约束生效；
- 同一任务恢复后历史记录仍可核对；
- 报告交付按稳定键和内容摘要核对，结果不明不会创建重复产物。

### 19.5 安全测试

- 向输入身份、错误、checkpoint、快照和墓碑注入模拟 secret；
- 验证未包装 payload 被拒绝；
- 验证 URL 凭证和查询参数不进入任务记录；
- 验证第三方异常原文不进入状态、日志或 CLI 错误；
- 验证仓库文本不能触发预算追加、恢复、清理或状态迁移。

## 20. 后续模块必须遵守的契约

- 安全模块必须提供不可伪造的安全包装结果或等价领域类型；
- 预算模块必须输出可加入统一工作单元的预算变更意图；
- Trace 模块必须使用稳定事件标识并能与 checkpoint 同事务提交；
- 输入模块只能一次性提交 `InputBinding`，不得直接修改任务；
- 审查规划和执行模块必须为工作单元与尝试提供稳定标识；
- 报告模块必须从不可变结果快照读取，并把交付尝试绑定到确切快照版本、稳定交付键和期望内容摘要；
- Output Adapter 必须支持按规范化目标、任务、快照和安全内容摘要核对本地产物；
- 审查编排模块只能提交转换意图，不能绕过租约、版本和状态机；
- SQLite 适配器必须实现乐观锁、租约 fencing 和跨模块原子工作单元。

若后续模块无法满足这些契约，应先修订本设计并记录影响，不得在适配器中以隐藏副作用绕过。

## 21. 设计结论

任务管理模块以 `Task` 聚合根维护权威生命周期，以正交状态表达执行、结果和交付，以版本化 checkpoint 与结果快照支持恢复和核对，以持久化租约、乐观锁和 fencing token 阻止并发重复执行。任务数据与预算、Trace、调用和交付状态通过统一工作单元原子提交；过期数据按统一七天策略清理，并长期保留最小脱敏墓碑。

该设计满足本地 CLI MVP 的异常恢复、结果一致性、预算累计、评论追溯和安全留痕要求，同时不引入后台调度、分布式锁或完整事件溯源。
