# Code Review Agent 报告模块详细设计

## 1. 文档状态

- 日期：2026-09-10
- 状态：设计完成，待复审
- 上游依据：《架构设计.md》及任务、安全、输入、规划、执行、发现模块设计
- 输出范围：本地 Markdown，不向远程平台回评

## 2. 设计结论

报告采用三段式边界：

```text
不可变 ResultSnapshot → 格式无关 ReportModel
→ Markdown 确定性渲染 → 完整字节安全复扫
→ 临时文件完整写入 → 原子替换 → 产物核对
```

`ResultSnapshot`（标准 ReviewResultSnapshot 或最小 FailureResultSnapshot）是唯一业务事实来源；模板不做状态判断、预算计算、发现筛选或排序；报告交付失败不改变审查结果。

## 3. 目标与非目标

目标：明确审查对象、固定版本、完成状态、覆盖、发现、置信度、预算、unknown 和 Trace；零发现/部分/失败仍可报告；同一任务固定路径；快照升级后原子更新；安全、确定、可核对恢复。

非目标：生成或重新验证发现、计算预算、补写 Trace、读取原始 diff/模型响应、重新执行审查、远程回评、消息发送或删除长期报告。

## 4. 唯一事实来源

标准审查报告只读取确切 `ReviewResultSnapshot` 及其固定引用：InputBinding、ReviewPlan、CoverageSnapshot、FindingSet、BudgetSummary、UnknownAttemptSet 和 TraceSummary。失败报告只读取确切 `FailureResultSnapshot` 及其固定失败阶段、稳定错误、安全输入身份、BudgetSummary 和 TraceSummary；不存在的审查引用必须保持缺失，不得合成空计划、空覆盖或空 FindingSet。每个已有引用统一包含对象类型、稳定 ID、版本、task ID、schema 版本、内容摘要和安全证明引用。不得把 tasks 当前状态、findings 最新表、预算当前汇总等可变查询拼成报告。

任一引用缺失、跨任务、摘要不符、schema 不支持或安全证明无效时，报告生成失败，不回退到“最新数据”。

ReviewResultSnapshot 必须在 FindingSet 已完成确定性收敛后创建，并完整固定上述七类引用。仅有 CandidateFinding、调用停止事实或覆盖影响时尚不可生成标准审查报告；预算不足、预算异常和 unknown 也必须先完成纯确定性发现收敛。FailureResultSnapshot 只允许用于输入固定前或计划冻结前的可靠终止，不含候选、覆盖或审查完成声明。

## 5. ReportModel

`ReportModel` 是格式无关、不可变、已完成业务判断的展示模型，schema 初始版本为 1，并以 `review/failure` 判别。review 变体至少包含：

- identity：task、snapshot、版本和 checkpoint；
- subject：输入类型、安全显示身份、仓库/对象、base/head 或 diff 摘要；
- completion：`no_changes`、`complete_no_findings`、`complete_with_findings`、`partial`、`failed`、`unknown`，以及完整性、限制和下一步；
- coverage：reviewed、unreviewed、unreviewable、unknown 范围和统计；
- findings：稳定 ID、位置、问题、证据、影响、建议、severity、两级 confidence、trace；
- budget：token 总授权 `A`、已知实际 `K`、不确定消耗 `U`、活动预留 `R_active`、已释放预留、超出量 `O`、剩余预算、授权赤字 `D`、账户/冻结状态及原因、usage 可信度（`missing`/`untrusted` 预留计数与 `pending_revalidation` 阻塞标记）和账本版本；`U` 与 `R_active` 禁止合并展示；
- unknowns：尝试类型、范围、保守消耗、原因和用户动作；
- trace：任务 trace、发现级 trace 数、checkpoint 和保留说明；
- security：策略版本和报告用途证明元数据。

failure 变体只包含 identity、已知 subject、`completion=failed`、失败阶段、稳定原因、限制、预算、Trace、安全元数据和下一步；coverage/findings 必须标记为“不适用/未形成”，不能展示为零覆盖或零发现。

“完整且无发现”必须写成“未发现有效问题”，不得保证没有缺陷。`pending` ResultSnapshot 不可生成报告。

ReportModel 中每条 finding 即一条最终评论，其 `finding_id` 同时是 TraceLink 的评论身份；报告不得生成第二套 comment ID。

## 6. 信息架构

Markdown 固定顺序：

1. 标题与任务/快照标识；
2. 结论和限制；
3. 审查对象与固定版本；
4. 覆盖摘要及未审查/不可审查范围；
5. 发现（按 FindingSet 已预置的稳定顺序展示：严重度优先，再按置信度、规范路径、位置种类、行号、category、fingerprint 稳定排序；模板不做重排）；
6. 预算；
7. unknown 调用或交付说明；
8. Trace 与生成元数据。

每条发现必须完整展示位置、问题、证据/触发条件、影响、建议、置信度依据和 trace ID。模板只能循环和显示已提供字段，不能重新分类或隐藏 partial/unknown。

## 7. 确定性与摘要

ReportModel 使用规范 JSON 计算 `report_model_digest`。Markdown 适配器固定模板版本、UTF-8、LF 换行、单个尾随换行、转义规则和排序；候选字节计算 `expected_content_digest`。

时间只展示快照中已有事实，不注入“当前时间”。路径、换行、locale 或字典迭代顺序不得改变内容。相同快照、模型 schema、模板/适配器和安全策略必须生成相同摘要。

## 8. 安全边界

报告模型只接受可用于 `report_rendering` 的安全字段。完整 Markdown UTF-8 字节在落盘前再次以 `report_delivery` 用途扫描。扫描成功后产生最终安全产物引用、策略证明和内容摘要；扫描不可用、不确定或发现无法安全处理的内容时禁止写入。

模板禁用任意表达式、动态 include、仓库模板和未注册过滤器；只加载应用内固定模板。错误、路径和 Trace 摘要均使用白名单安全字段。

## 9. 交付模型

`DeliveryAttempt` 绑定 task、确切 snapshot、适配器 ID/版本、稳定 `delivery_key`、规范化目标、期望内容摘要、状态、实际摘要/核对结果和时间。

MVP 路径由 task ID 唯一确定；同任务新快照替换同一路径，不创建第二份报告。`delivery_key` 由 task、确切 snapshot、适配器 ID/版本、规范化目标和期望内容摘要稳定派生；同快照同内容重试得到相同键，不同快照或不同内容必须得到不同键。目标路径唯一性与交付尝试幂等性是两项独立约束，不能用跨快照唯一的 `delivery_key` 代替路径约束。

## 10. 原子写入与 unknown 核对

1. 取得 `report_delivery` 租约；
2. 构建、渲染和安全复扫；渲染与安全复扫成功后、交付尝试置 running 前，创建 `report_generated` checkpoint（见任务模块 9.3），作为"报告模型已从结果快照生成并安全固化、尚未完成文件交付"的一致性边界；
3. 按绑定当前 snapshot 和期望摘要的 `delivery_key` 原子创建/推进 DeliveryAttempt 为 running；
4. 以规范化目标为键取得跨执行者排他文件交付锁；该锁覆盖检查、替换、核对和数据库终态提交，不能只依赖进程内 mutex；
5. 在持锁状态下重新读取任务版本、当前 snapshot、交付租约 ID/fencing token 和 DeliveryAttempt；任一变化都放弃写入；
6. 在目标同目录创建任务专属临时文件，完整写入并 `fsync` 文件；
7. `os.replace` 紧邻执行前再次核对交付租约未过期、fencing token 仍为当前值、当前 snapshot 和期望摘要未变化；核对与替换必须处于同一文件锁临界区；
8. 原子替换固定目标，再打开并 `fsync` 目标父目录，使目录项持久化；
9. 重读并核对 task/snapshot 身份和内容摘要；
10. 仅在持锁、父目录同步与核对均成功，且数据库条件更新再次匹配任务版本、当前 snapshot、租约和 fencing token 时，原子提交 succeeded、Trace、checkpoint 和任务交付转换；提交后释放文件锁。

文件系统与 SQLite 不能共同事务化。若写入开始后未提交终态，或原子替换后的父目录同步结果不明，尝试为 unknown。父目录同步明确失败时不得提交 succeeded；恢复必须先核对：

- 最终文件与当前快照和摘要一致：只补记成功；
- 仅有本任务未完成临时文件：安全删除后重试；
- 最终文件是同任务旧快照：显式重试原子替换；
- 身份或摘要无法核对：保持 unknown，不另建路径。

旧快照迟到结果不能覆盖当前交付状态。报告失败/unknown 不修改控制状态、结果快照或预算。

## 11. 快照与 schema 演进

读取器声明支持的 ResultSnapshot 版本；纯数据升级产生不可变 `SnapshotView`，不改写原快照。ReportModel 主版本不兼容时适配器拒绝；新增输出格式只实现 Output Adapter 合约。

模板或适配器升级创建新交付尝试并记录实际版本；不得把新内容冒充旧尝试结果。远程发布不属于 Output Adapter，未来必须单独设计授权和副作用幂等。

## 13. 错误模型

生成错误：`snapshot_not_reportable`、`snapshot_reference_missing`、`snapshot_integrity_error`、`report_schema_incompatible`、`report_model_invalid`、`report_security_failed`。

交付错误：`delivery_target_invalid`、`delivery_permission_denied`、`delivery_write_failed`、`delivery_result_unknown`、`delivery_artifact_mismatch`、`delivery_lease_lost`、`persistence_integrity_failed`。

错误只包含阶段、影响、可恢复性、下一步和安全关联 ID。

## 14. 关键不变量

1. 报告只来自一个确切不可变快照；
2. 模板不实现业务规则；
3. partial/failed/unknown 不得显示为 complete；
4. 每条发现都有置信度和 trace；
5. 预算已知值与不确定值分开；
6. 完整字节安全复扫后才能写入；
7. 同一任务只有一个规范目标路径；
8. 交付尝试绑定确切快照和内容摘要；
9. unknown 先核对再重写；
10. 交付失败不改变审查结果；
11. Output Adapter 不获得远程发布能力。
12. ResultSnapshot 必须固定其快照种类要求的完整不可变引用及摘要，报告不得查询“最新”派生产物补缺；
13. CandidateFinding 永远不能直接进入 ReportModel。
14. 原子替换后必须同步目标父目录，成功状态只能在持久化屏障和产物核对完成后提交。
15. 同一规范化目标的检查、替换、核对和终态提交必须串行化，失去租约或持有旧 fencing token 的执行者不得执行 `os.replace`。
16. FailureResultSnapshot 报告不得伪造 InputBinding、ReviewPlan、CoverageSnapshot、FindingSet 或“零发现”结论。

## 15. 测试与需求映射

- ReportModel 决策表覆盖六种结果状态、零发现和所有覆盖组合；
- golden tests 固定 Markdown 字节、排序、转义和摘要；
- 合约测试验证目标隔离、同任务替换、旧快照迟到和产物核对；
- 故障注入覆盖临时文件、替换后、SQLite 完成事务前；
- 安全测试覆盖发现、错误、路径、Trace 和模型/工具回显；
- 性质测试证明不同任务不覆盖、相同输入确定输出。

主要覆盖 FR-004、FR-006～FR-009、FR-014～FR-016、FR-018、FR-022～FR-026。

## 16. 设计决策与结论

选择 Snapshot→ReportModel→Adapter 分层，使业务事实、展示语义和文件副作用分离；选择确定性重建而非保存可变报告正文；选择“尝试 + 核对”处理文件系统与数据库间崩溃窗口。

报告模块忠实投影不可变审查结果，以稳定模型和安全模板生成 Markdown，并通过固定路径、内容摘要、原子替换和 unknown 核对提供可恢复且不重复的本地交付。
